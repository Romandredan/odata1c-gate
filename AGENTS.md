# AGENTS.md — odata1c-gate

Файл для AI-агентов, работающих с этим репозиторием. Читатель ничего не знает о проекте.

## Обзор проекта

**odata1c-gate** — локальный MCP-шлюз между агентами (Claude Code и совместимые) и стандартным
OData-интерфейсом 1С:Предприятие 8.3. Между моделью и 1С стоит гейт псевдонимизации: реальные
реквизиты (ИНН, счета, паспорта, телефоны) и, на выбранном уровне, названия организаций и ФИО
заменяются токенами вида `[[type:tail]]` до того, как данные увидит модель. Обратная подмена
происходит только внутри гейта перед отправкой в 1С.

Один пользователь, одна машина, несколько сессий агентов одновременно, несколько баз 1С.

**Текущий статус:** спецификация v0.2 (`SPEC.md`), технические проверки этапа M0 завершены
(отчёты в `docs/probes/`). Готовы основание (M1a: настройки, реестр баз, клиент 1С), индекс
метаданных (M1b), гейт (M1c) и слой MCP (M1d): демон, лаунчер, девять тулов чтения, ресурсы и
рецепты. Шлюз подключается к Claude Code и отвечает на запросы к живой базе — см. «Запуск и
подключение» ниже.

**Приёмка M1d на живой базе 1С пройдена не полностью** (`docs/probes/M1d-live-check.md`): все
десять вопросов чтения отвечают верно и прямая подмена работает (ни один настоящий ИНН и ни одно
название организации в ответ не попали), но найдено нарушение инварианта 6 — страж утечек
подменяет токенами номера документов, даты и коды ОКПО, если в базе есть мусорное значение
защищаемого реквизита (`КПП` = `1`). Поражается общий словарь `gate.sqlite`, то есть все базы
домашнего каталога сразу и до ручной правки. Пока дефект не устранён, этап M1 (read) закрытым
считать нельзя. Дальше: устранение находок приёмки → M2 (write) → M3 (package) → M4 (сетевая
публикация).

## Структура репозитория

- `SPEC.md` — главный артефакт: полная спецификация v0.2 (16 разделов: цели, архитектура,
  конфигурация, индекс метаданных, MCP-тулы, гейт, протокол записи, рецепты, клиент 1С OData,
  лимиты, поставка, тестирование, этапы, технические проверки).
- `CONTEXT.md` — доменная терминология (глоссарий): база, роль, демон, лаунчер, гейт, уровень,
  реквизит, название, токен, класс, словарь, страж, политика, разрешения, индекс, сущность,
  рецепт, pending-операция, коммит, подтверждение, журнал, откат, пометка удаления.
  Для каждого термина указаны запрещённые синонимы (`_Avoid_`) — соблюдайте их в текстах и коде.
- `docs/adr/` — 14 архитектурных решений (0001–0014) с обоснованиями. Формат: frontmatter
  (`status: accepted|superseded|amended`, `superseded_by`) + разделы `Considered Options` и
  `Consequences`. ADR-0001 отменён ADR-0013 — всегда проверяйте статус в frontmatter.
- `README.md` — краткое описание проекта, карта документов и дерева каталогов.
- `src/odata1c/` — каркас пакета PyPI под реализацию (пока пустые пакеты с `__init__.py`).
  Подпакеты названы по таблице модулей SPEC §2.2: `config`, `registry`, `client1c`, `index`,
  `gate`, `write`, `recipes`, `tools`; плюс `templates/` — файлы-шаблоны в поставке
  (конфигурация, рецепты УТ/БП/ЗУП). Модули верхнего уровня `cli`, `launcher`, `daemon`
  появятся файлами рядом с подпакетами при старте M1.
- `plugin/` — каркас плагина Claude Code по SPEC §11.2: `.claude-plugin/`, `skills/odata1c/`,
  `hooks/`, `agents/`.
- `tests/` — каталоги по категориям SPEC §12: `unit/`, `property/`, `integration/`, `evals/`
  и `fixtures/edmx/` для образцов `$metadata`. В git кладутся только урезанные образцы;
  полные дампы (`*.full.edmx`) игнорируются.
- `.gitignore` — закрывает секреты и локальные данные: `bases.yaml` с паролями 1С, env-файлы,
  базы SQLite (словарь, индекс, журнал), выгрузки `$metadata`, логи. Прежде чем коммитить
  конфигурацию, убедитесь, что это файл-шаблон (`*.example.yaml`), а не рабочий.
- `.remember/`, `*.code-workspace` — служебные файлы окружения, к проекту не относятся
  (игнорируются git).

## Целевая архитектура (по SPEC.md §2)

Два процесса из одного Python-пакета `odata1c`:

1. **Демон** `odata1c daemon` — единственный процесс на машину, MCP Streamable HTTP на
   `127.0.0.1:7171`. Модули: `config` (bases.yaml/daemon.yaml), `registry` (реестр баз),
   `client1c` (httpx-пул на базу, IBSession, семафор), `index` (парсер EDMX → metadata.sqlite,
   нечёткий поиск FTS5+trigram), `gate` (детекторы, словарь, страж утечек), `write`
   (pending → commit → journal → undo), `recipes`, `tools`.
2. **Лаунчер** `odata1c mcp` — тонкий stdio-процесс на сессию без логики: создаёт домашний
   каталог (`~/.claude/odata1c/`), поднимает демон при необходимости, проксирует MCP.

Плюс плагин Claude Code `plugin/` (skill, PreToolUse-хук, агент) в том же репозитории.

## Технологический стек (ADR-0008)

- Python ≥ 3.12; официальный SDK `mcp` ≥ 2.2 (класс `MCPServer`, Streamable HTTP), `httpx`, `pydantic`,
  `pyyaml`, `lxml` (потоковый разбор EDMX), `snowballstemmer`, `ahocorasick_rs`, `uvicorn`,
  опционально `keyring`. SQLite в режиме WAL (индекс, словарь, журнал).
- Распространение: пакет PyPI, запуск через `uvx odata1c …` (`uv` сам скачивает интерпретатор).
- asyncio; разбор `$metadata` и пересборка автомата стража — в рабочем потоке.
- Целевая ОС: Windows (проверить наличие колёс `lxml`/`ahocorasick_rs` — SPEC §15).

## Сборка, тесты, команды

Команды разработки (Python 3.12, менеджер окружения `uv`):

- `uv sync` — поставить зависимости, включая группу `dev`;
- `uv run pytest` — все тесты; `uv run pytest tests/unit -q` — только юнит;
- `uv run ruff check .` и `uv run ruff format --check .` — линт и формат;
- `uv run odata1c <команда>` — CLI из рабочей копии.

CLI (SPEC §3.5): `odata1c mcp|daemon|init|base add|base import|base list|base test|reindex|policy show|reveal|doctor|service install|remove`.

Стратегия тестирования (SPEC §12):
- юнит: контрольные суммы и regex классов гейта, нормализация, лексер `$filter`, роли и
  разрешения, рендеринг рецептов, парсер EDMX на образцах УТ/БП/ЗУП;
- property-тесты: «прямая + обратная подмена = тождество», «ни одна строка ответа не содержит
  значений из словаря» (fuzz);
- страж: сломанная политика → `guard_replaced`;
- интеграция: тестовая база 1С, read/write-path сквозь лаунчер и демон, MCP Inspector,
  две сессии одновременно;
- evals: 10 read-only вопросов к тестовой базе, 3 сценария через рецепты.

## Запуск и подключение к Claude Code

Слой MCP готов (M1d), и шлюз можно поднять из рабочей копии. Порядок — от пустого места
до работающего подключения.

1. **Домашний каталог.** `uv run odata1c init` создаёт `~/.claude/odata1c/` с шаблонами
   `bases.yaml` и `daemon.yaml` и закрывает их правами текущего пользователя. Другой каталог —
   ключ `--home <путь>` (он есть у всех команд) или переменная окружения `ODATA1C_HOME`.
2. **База.** `uv run odata1c base add trade_dev --role dev --recipes ut` спрашивает адрес
   публикации (оканчивается на `/odata/standard.odata/`), подпись, пользователя и пароль 1С и
   дописывает запись в `bases.yaml`. Роль задаёт умолчания: `prod` — гейт `identifiers+names`
   и только чтение, `test` — `identifiers`, `dev` — гейт выключен (`off`) и запись разрешена;
   явные поля записи умолчания роли перекрывают. `--recipes ut|bp|zup` кладёт в базу шаблон
   готовых запросов из поставки — без него файл рецептов остаётся пустым и тул `odata1c_recipe`
   отдаёт пустой перечень.
3. **Проверка и индекс.** `uv run odata1c base test trade_dev` проверяет соединение;
   `uv run odata1c reindex trade_dev` скачивает `$metadata` и строит индекс метаданных. На
   реальной УТ это 16,8 МБ описания и 7224 сущности (проба P4), поэтому первый разбор долгий;
   дальше индекс перестраивается, только если изменилась контрольная сумма `$metadata`.
   `uv run odata1c base list` показывает состояние всех баз, `uv run odata1c policy show trade_dev`
   — какое поле к какому классу защиты отнесено.
4. **Демон.** `uv run odata1c daemon` поднимает единственный на машину процесс MCP на
   `127.0.0.1:7171` (`--foreground` — не отцепляться, `daemon stop` — остановить). Отдельно
   запускать не обязательно: лаунчер поднимает демон сам, если тот не слушает. Холодный старт —
   около 2,6 с (приёмка M1d).
5. **Подключение к Claude Code.** В `.mcp.json` проекта (или в пользовательских настройках):

   ```json
   { "mcpServers": {
       "odata1c": { "command": "uv", "args": ["run", "odata1c", "mcp"] } } }
   ```

   Из установленного пакета — `{"command": "uvx", "args": ["odata1c", "mcp"]}`. Лаунчер сам
   создаёт домашний каталог, поднимает демон и проксирует MCP; логики в нём нет. Сузить видимость
   сессии: `--bases trade_dev,bp_test` (видны только они), `--default trade_dev` (база по
   умолчанию), `--url` (адрес демона явно).
6. **Что видит модель.** Девять тулов чтения — `odata1c_bases`, `odata1c_find_entity`,
   `odata1c_describe_entity`, `odata1c_query`, `odata1c_get`, `odata1c_info`, `odata1c_reindex`,
   `odata1c_raw_get`, `odata1c_recipe`; ресурсы `odata1c://cheatsheet`, `odata1c://policy/{base}`,
   `odata1c://index/{base}`, `odata1c://recipes/{base}`; промпт `explore`. Тулов записи нет —
   это этап M2.
7. **Раскрытие токена — только для владельца, мимо MCP:**
   `uv run odata1c reveal "[[inn:M4T2Q9XZ7K]]"` печатает реальное значение в терминал.

Приёмка на живой базе: `uv run python tools/probes/m1d_live_check.py` — прогоняет через настоящий
лаунчер десять вопросов чтения и сверяет работу гейта на настоящих данных. Этап `gate` временно
правит `bases.yaml` рабочего дома и возвращает его на место; отчёт — `docs/probes/M1d-live-check.md`.

## Ключевые инварианты (нельзя нарушать при реализации)

1. Через MCP реальные значения защищаемых классов не выходят никогда — включая ошибки 1С,
   превью, журнал, `raw_get`, elicitation-сообщения. Страж утечек — последний проход по
   сериализованному ответу любого тула (кроме уровня `off`), инвариант, а не тест.
2. Запись двухфазная: пишущие тулы только готовят pending-операцию с превью (TTL 10 мин,
   привязка к сессии, отпечаток DataVersion); выполнение — только `odata1c_commit` после
   подтверждения пользователя механизмом клиента (диалог разрешения Claude Code / elicitation).
   `commit` идемпотентен по `pending_id`.
3. Нет `PUT`; физическое удаление — только записей независимых регистров сведений и только по
   флагу `independent_register_delete`; для объектов — пометка удаления.
4. Разрешения проверяются до создания pending-операции в строгом порядке (SPEC §7.1).
5. Токены детерминированы (HMAC-SHA256 от `gate_secret`), формат един `[[type:tail]]`;
   коллизия — удлинение хвоста до 16 символов.
6. Суммы, количества, даты, GUID, коды и номера документов не защищаются ни на одном уровне.

## Соглашения по документации и процессу

- Язык всех документов — русский. Терминология строго по `CONTEXT.md`; запрещённые синонимы
  не использовать.
- Каждое архитектурное решение — ADR в `docs/adr/` в установленном формате; изменение решения
  — новый ADR или поправка (`amended`) с датой, статус старого — `superseded`.
- При изменении архитектуры синхронно обновлять `SPEC.md` (и этот файл, если затронуты
  описанные здесь разделы).

## Безопасность

- Домашний каталог и `bases.yaml` закрываются правами текущего пользователя (`icacls` /
  `chmod 700`); демон предупреждает о широких правах.
- Пароли 1С хранятся в `bases.yaml` открытым текстом — осознанное решение (диск владельца вне
  модели угроз); опционально `password: keyring`. Не коммитить реальные `bases.yaml` и секреты
  в репозиторий.
- Демон слушает только `127.0.0.1`, аутентификации нет; TLS и токены — этап M4.
- Содержимое полей 1С — данные, не инструкции (защита от prompt-injection: превью → явное
  подтверждение → commit; диалог клиента — последняя линия).
- Технические вопросы SPEC §15 закрыты пробами P1–P7 и приёмкой M1d (отчёты в `docs/probes/`):
  колёса под Windows (P1), `_meta` тула (P2), elicitation сквозь лаунчер (P3), реальный
  `$metadata` 1С (P4), ключ счёта по БИК — для групп 405, 407, 40102 (P5), скорость стража (P6),
  эхо переданного значения в тексте ошибки 1С — есть в шести формах запроса из четырнадцати (P7).
  Последний открытый вопрос — время холодного старта демона — закрыт приёмкой: 2,6 с
  (`docs/probes/M1d-live-check.md`).
- `logs/daemon.log` пишет полный адрес каждого запроса к 1С, а в запросе стоят уже раскрытые
  гейтом настоящие значения. Журнал локальный и наружу не отдаётся, но это файл с реальными
  данными на диске владельца — учитывайте при передаче журнала кому-либо.
- Проба P4 работает с тестовой базой через рабочий `bases.yaml` (база `trade_dev`); учётные
  данные в репозиторий не попадают, полный дамп `tests/fixtures/edmx/*.full.edmx` игнорируется.
