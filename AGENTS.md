# AGENTS.md — odata1c-gate

Файл для AI-агентов, работающих с этим репозиторием. Читатель ничего не знает о проекте.

## Обзор проекта

**odata1c-gate** — локальный MCP-шлюз между агентами (Claude Code и совместимые) и стандартным
OData-интерфейсом 1С:Предприятие 8.3. Между моделью и 1С стоит гейт псевдонимизации: реальные
реквизиты (ИНН, счета, паспорта, телефоны) и, на выбранном уровне, названия организаций и ФИО
заменяются токенами вида `[[type:tail]]` до того, как данные увидит модель. Обратная подмена
происходит только внутри гейта перед отправкой в 1С.

Один пользователь, одна машина, несколько сессий агентов одновременно, несколько баз 1С.

**Текущий статус:** спецификация v0.2 (`SPEC.md`), технические проверки этапа M0 завершены
(отчёты в `docs/probes/`). Готовы основание (M1a: настройки, реестр баз, клиент 1С), индекс
метаданных (M1b), гейт (M1c) и слой MCP (M1d): демон, лаунчер, девять тулов чтения, ресурсы и
рецепты. Шлюз подключается к Claude Code и отвечает на запросы к живой базе — см. «Запуск и
подключение» ниже. Этап M2 (запись) реализован: семь тулов записи, приёмка скриптом на живой базе
пройдена дважды, ручная проверка диалога Claude Code — за владельцем (раздел «Этап M2» ниже).

**Этап M1 (read) закрыт 2026-09-12.** Приёмка M1d на живой базе 1С пройдена через настоящие
инструменты шлюза в сессии Claude Code — 15 проверок из 15 (`docs/probes/M1d-live-check.md`):
названия, ИНН и КПП приходят токенами, раскрытие связей маскируется по политике своей сущности,
отбор по токену возвращает тот же токен, номера, даты и суммы не трогаются. Итоговое ревью
атакующим: на 400 случайных телах ответа и 29 487 сравнениях полей живой базы — ни одного
расхождения и ни одного раскрытого значения.

**После закрытия этап переоткрыт находкой владельца (2026-09-12).** Контактная информация
(табличная часть `…_КонтактнаяИнформация` любого справочника) отдавала телефоны и адреса открытыми:
номер лежал в JSON поля `Значение` и XML `ЗначенияПолей` без класса защиты, а адреса физлиц,
контрагентов-ИП и доставки не закрывались правилом адресов. Исправлено решениями Ruling 33
(контактная информация закрывается по типу строки, SPEC §6.4) и Ruling 34 (адреса физлиц, ИП и
доставки, SPEC §6.9); приёмка на живой базе — `tools/probes/contact_info_live_check.py`:
телефоны 224 из 670 → 0, адреса физлиц, ИП и доставки → 0, адреса юрлиц в карточке открыты.
Раунд 2 той же правки: отбор по полям контактной информации — только токеном из ответа
(Ruling 35, SPEC §6.7; открытый литерал отклоняется до обращения к 1С), справочники людей сверены
с индексом УТ (Ruling 36, SPEC §6.5: `Catalog_КонтактныеЛицаПартнеров` и ещё шесть), `masked_fields`
называет только поля, закрытые целиком, частичные — `partially_masked_fields` (SPEC §5.1).
Новые справочники людей попадают в раздел `auto` политики реиндексом, а в `defaults.addr.mask_for`
существующей политики — только правкой владельца: раздел `defaults` реиндекс не переписывает
(авторазметка, включая список справочников людей, живёт в `policy.auto.yaml`, а
`defaults.addr.mask_for` в `policy.yaml` владельца дополняет его).
Раунд 3: отбор через путь от владельца (`substringof('495', КонтактнаяИнформация/Представление)`
по контрагентам) тоже только токеном — входной путь разрешает конечную сущность пути по навигациям
и табличным частям (Ruling 37); одно значение контактной информации получает один токен при любом
наборе полей (гейт сам добавляет `Тип` в выборку). **Этап закрыт повторно 2026-09-12:** итоговое
ревью атакующим Approved, приёмка чтения 15 из 15 и приёмка контактной информации 11 из 11 на живой
базе `trade_dev`.
Повторное закрытие этапа — после ревью этой правки.

Известные ограничения этапа (записаны в SPEC): сокращённое название клиента в свободном тексте
(«…в ЦСКА по упд 711…» при полном названии в справочнике) не ловится — решение владельца; пустой
ответ на отбор по токену не доказывает отсутствия записи в написании, которого шлюз ещё не видел.

Блокеры M2 из хвоста плана M1d (`docs/plans/2026-09-10-m1d-mcp-surface.md`, раздел «Вне плана»)
закрыты 2026-09-12: отбор по токену ищет все известные написания значения, туда, где нужно одно
написание (ключ, параметр, тело записи), без однозначного шлюз не подставляет ничего
(`token_ambiguous`); строка 1С с токеном шлюза выдаётся токеном `lit`; ответ на запись проходит
ранний проход; пересекающиеся названия закрываются целиком. Контракт гейта для пишущих тулов
(`BaseGate.inbound_write`, `Client1C.post/patch/delete(scrub=…)`) — раздел «Интерфейс для M2»
отчёта о блокерах. Дальше: M2 (write) → M3 (package) → M4 (сетевая публикация).

**Этап M2 (write) закрыт 2026-09-13:** приёмка на живой базе пройдена дважды скриптом (163 из 163,
249 из 249) и вручную владельцем в Claude Code 2.1.267 в автоматическом режиме — диалог разрешения
на `odata1c_commit` появляется, отказ в нём ничего не пишет, согласие пишет, механизм в журнале
`claude_code`, откат работает (`docs/probes/M2-live-check.md`). План —
`docs/plans/2026-09-12-m2-write.md`, задачи 1–10. Первая поставка записи: `odata1c_create`,
`odata1c_update`, `odata1c_mark_for_deletion` (физического удаления объектов нет),
`odata1c_action` (`Post`/`Unpost`), `odata1c_undo`, `odata1c_commit`, `odata1c_journal`;
`odata1c_delete_record` (удаление записей независимых регистров) в неё не входит — решение 1 плана,
флаг `independent_register_delete` в разрешениях остаётся без тула. Запись в регистры, подчинённые
регистратору, закрыта при любом флаге (Ruling 57). Приёмка скриптом на `trade_dev` пройдена —
163 проверки из 163 (`docs/probes/M2-live-check.md`): создание, изменение по токену (в 1С —
реальное значение, модели — тот же токен), пометка и снятие, проведение и отмена, откат каждой
операции со сверкой с журналом, отказы до обращения к 1С, `pending_stale`, ошибка 1С на `commit`
без текста на уровне `identifiers+names` (Ruling 52), подпись лаунчера (Ruling 59); ни одного
реального значения в 65 ответах тулов и 18 вопросах подтверждения. Не проверено скриптом —
диалог разрешения настоящего Claude Code на `odata1c_commit` и механизм `claude_code` в журнале
(Н9-1): инструкция для владельца — в том же отчёте. Статус «закрыт» — после неё.

**Повторная приёмка 2026-09-13 (после итогового ревью ветки, `528ccf9`) — 249 проверок из 249.**
Прежние сценарии прогнаны заново, добавлены: запись табличной части (И-3), числовые поля (И-8),
запись регистра (Ruling 60), пометка литерала в превью (Ruling 62, 63), заверение родителя
лаунчера (Ruling 61) и неизвестный исход записи (И-4, ФП-2: прокси приёмки отвечает 502 сам, в 1С
не уходит ничего, шлюз отвечает `commit_outcome_unknown` и запрещает повтор вслепую) — всё на живой
`trade_dev`. Известные ограничения записи, найденные приёмкой:
строка табличной части в теле `create` **должна нести `LineNumber`** — без него 1С отвечает HTTP 500
«внутренняя ошибка OData сервиса», и шлюз этого не проверяет; поле `Edm.Int64` публикация отдаёт
строкой (так его сериализует JSON OData v3), а шлюз на запись требует число — такую запись 1С молча
не выполняет, и видно это только по предупреждению о расхождении, которое шлюз выдаёт, перечитав
объект. Часть числовых реквизитов типовая конфигурация сбрасывает при записи сама (`Крепость`,
`ВесЧислитель`) — там же и тем же предупреждением.

**ADR-0015 реализован 2026-09-14** (план `docs/plans/2026-09-14-owner-policy-constructor.md`,
ветка `m2b-owner-policy`, задачи 1–7). Точки управления владельца — два файла: `bases.yaml` на
машину («кто база, как с ней работать, скрывать ли»: `gate.mode`) и `bases/<база>/policy.yaml` на
базу («что скрывать и что открыть»: только владельцу, из самодокументированного шаблона со всеми
классами). Авторазметка реиндекса лежит в `policy.auto.yaml` (файл помечен «не редактировать»);
`bases.yaml` перечитывается по изменению файла без перезапуска демона; правила в политику
добавляет конструктор `odata1c policy show | check | hide | open | set` (пишет через `ruamel.yaml`,
комментарии сохраняются; `custom` и `copy` — следующая итерация) и навык плагина `odata1c-policy`;
тула MCP для изменения политики нет. Модели то же самое объясняет тема `odata1c_info("policy")`.
Поведение ниже в разделе «Запуск и подключение» описывает уже реализованный код.

- `.remember/`, `*.code-workspace` — служебные файлы окружения, к проекту не относятся
  (игнорируются git).

## Целевая архитектура (по SPEC.md §2)

Два процесса из одного Python-пакета `odata1c`:

1. **Демон** `odata1c daemon` — единственный процесс на машину, MCP Streamable HTTP на
   `127.0.0.1:7171`. Модули: `config` (bases.yaml/daemon.yaml), `registry` (реестр баз),
   `client1c` (httpx-пул на базу, IBSession, семафор), `index` (парсер EDMX → metadata.sqlite,
   нечёткий поиск FTS5+trigram), `gate` (детекторы, словарь, страж утечек), `write`
   (pending → commit → journal → undo), `recipes`, `tools`.
2. **Лаунчер** `odata1c mcp` — тонкий stdio-процесс на сессию без логики: создаёт домашний
   каталог (`~/.claude/odata1c/`), поднимает демон при необходимости, проксирует MCP.

Плюс плагин Claude Code `plugin/` (skill, PreToolUse-хук, агент) в том же репозитории.

## Технологический стек (ADR-0008)

- Python ≥ 3.12; официальный SDK `mcp` ≥ 2.2 (класс `MCPServer`, Streamable HTTP), `httpx`, `pydantic`,
  `pyyaml`, `lxml` (потоковый разбор EDMX), `snowballstemmer`, `ahocorasick_rs`, `uvicorn`,
  опционально `keyring`. SQLite в режиме WAL (индекс, словарь, журнал).
- Распространение: пакет PyPI, запуск через `uvx odata1c …` (`uv` сам скачивает интерпретатор).
- asyncio; разбор `$metadata` и пересборка автомата стража — в рабочем потоке.
- Целевая ОС: Windows (проверить наличие колёс `lxml`/`ahocorasick_rs` — SPEC §15).

## Сборка, тесты, команды

Команды разработки (Python 3.12, менеджер окружения `uv`):

- `uv sync` — поставить зависимости, включая группу `dev`;
- `uv run pytest` — все тесты; `uv run pytest tests/unit -q` — только юнит;
- `uv run ruff check .` и `uv run ruff format --check .` — линт и формат;
- `uv run odata1c <команда>` — CLI из рабочей копии.

CLI (SPEC §3.5): `odata1c mcp|daemon|init|base add|base import|base list|base test|reindex|policy show|check|hide|open|set|reveal|doctor|service install|remove`.

Стратегия тестирования (SPEC §12):
- юнит: контрольные суммы и regex классов гейта, нормализация, лексер `$filter`, роли и
  разрешения, рендеринг рецептов, парсер EDMX на образцах УТ/БП/ЗУП;
- property-тесты: «прямая + обратная подмена = тождество», «ни одна строка ответа не содержит
  значений из словаря» (fuzz);
- страж: сломанная политика → `guard_replaced`;
- интеграция: тестовая база 1С, read/write-path сквозь лаунчер и демон, MCP Inspector,
  две сессии одновременно;
- evals: 10 read-only вопросов к тестовой базе, 3 сценария через рецепты.

## Запуск и подключение к Claude Code

Слой MCP готов (M1d), и шлюз можно поднять из рабочей копии. Порядок — от пустого места
до работающего подключения.

1. **Домашний каталог.** `uv run odata1c init` создаёт `~/.claude/odata1c/` с шаблонами
   `bases.yaml` и `daemon.yaml` и закрывает их правами текущего пользователя. Другой каталог —
   ключ `--home <путь>` (он есть у всех команд) или переменная окружения `ODATA1C_HOME`.
2. **База.** `uv run odata1c base add trade_dev --role dev --recipes ut` спрашивает адрес
   публикации (оканчивается на `/odata/standard.odata/`), подпись, пользователя и пароль 1С и
   дописывает запись в `bases.yaml`. Роль задаёт умолчания: `prod` — гейт `identifiers+names`
   и только чтение, `test` — `identifiers`, `dev` — гейт выключен (`off`) и запись разрешена;
   явные поля записи умолчания роли перекрывают. `--recipes ut|bp|zup` кладёт в базу шаблон
   готовых запросов из поставки — без него файл рецептов остаётся пустым и тул `odata1c_recipe`
   отдаёт пустой перечень.
3. **Проверка и индекс.** `uv run odata1c base test trade_dev` проверяет соединение;
   `uv run odata1c reindex trade_dev` скачивает `$metadata` и строит индекс метаданных. На
   реальной УТ это 16,8 МБ описания и 7224 сущности (проба P4), поэтому первый разбор долгий;
   дальше индекс перестраивается, только если изменилась контрольная сумма `$metadata`.
   `uv run odata1c base list` показывает состояние всех баз, `uv run odata1c policy show trade_dev`
   — действующая политика с источником каждой строки (`владелец` | `авто`). Править её вручную не
   нужно: `odata1c policy check trade_dev` сверяет `policy.yaml` по индексу (имена, классы,
   противоречия), `odata1c policy hide trade_dev <Сущность>` закрывает сущность целиком,
   `odata1c policy open trade_dev <Сущность.Поле>` открывает поле, `odata1c policy set trade_dev
   <Сущность.Поле> <класс>` назначает класс — каждая команда пишет `policy.yaml` с сохранением
   комментариев (`ruamel.yaml`) и сама выполняет `check` после записи.
4. **Демон.** `uv run odata1c daemon` поднимает единственный на машину процесс MCP на
   `127.0.0.1:7171` (`--foreground` — не отцепляться, `daemon stop` — остановить). Отдельно
   запускать не обязательно: лаунчер поднимает демон сам, если тот не слушает. Холодный старт —
   около 2,6 с (приёмка M1d).
5. **Подключение к Claude Code.** В `.mcp.json` проекта (или в пользовательских настройках):

   ```json
   { "mcpServers": {
       "odata1c": { "command": "uv", "args": ["run", "odata1c", "mcp"] } } }
   ```

   Из установленного пакета — `{"command": "uvx", "args": ["odata1c", "mcp"]}`. Лаунчер сам
   создаёт домашний каталог, поднимает демон и проксирует MCP; логики в нём нет. Сузить видимость
   сессии: `--bases trade_dev,bp_test` (видны только они), `--default trade_dev` (база по
   умолчанию), `--url` (адрес демона явно).
6. **Что видит модель.** Девять тулов чтения: `odata1c_bases`, `odata1c_find_entity`,
   `odata1c_describe_entity`, `odata1c_query`, `odata1c_get`, `odata1c_info`, `odata1c_reindex`,
   `odata1c_raw_get`, `odata1c_recipe`; ресурсы `odata1c://cheatsheet`, `odata1c://policy/{base}`,
   `odata1c://index/{base}`, `odata1c://recipes/{base}`; промпт `explore`. Семь тулов записи
   (этап M2): подготовка `odata1c_create`, `odata1c_update`,
   `odata1c_mark_for_deletion`, `odata1c_action`, `odata1c_undo` — в 1С не пишут, возвращают превью
   в токенах и `pending_id`; `odata1c_commit` выполняет после подтверждения клиента (Claude Code —
   диалог разрешения, клиент с elicitation — вопрос демона, прочие — `write_confirm_fallback`);
   `odata1c_journal` — последние записи. Порядок записи для модели — `odata1c_info("write_protocol")`.
7. **Запись у базы.** Включает её поле `write` записи базы в `bases.yaml`; умолчание задаёт роль
   (SPEC §3.2): `prod` — `write: false`, `test` и `dev` — `true`; явное поле роль перекрывает
   (`role: prod` + `write: true` — продуктив с записью, `role: dev` + `write: false` — разработка
   только для чтения). Раздел `permissions` той же записи сужает разрешённое: `post_documents`
   (проведение и отмена), `mark_deletion` (пометка удаления), `allow_entities` / `deny_entities`
   (в какие сущности писать), `deny_fields` (поля в форме `Сущность.Поле`, которые не пишутся ни
   одним тулом), `commit_limit` (коммитов за 10 минут на сессию: `prod` 20, `test` 50, `dev` без
   лимита). `bases.yaml` демон перечитывает по изменению файла перед вызовом тула — правка `write`,
   `permissions`, `gate.mode` или `policy.yaml` действует на следующий вызов без перезапуска
   демона; смена уровня гейта или правил политики посреди сессии даёт строку в `warnings` ответа.
   Файл, который не разбирается или не проходит проверку, закрывает все тулы `config_invalid` с
   путём и строкой, пока владелец его не починит — прежняя конфигурация не используется. `commit`
   перепроверяет разрешения по текущему файлу: подготовлено при разрешённой записи, а к моменту
   `commit` запрещено — `permission_denied`, операция снята. Перезапуска (`odata1c daemon stop`,
   следующий лаунчер поднимет демон заново) по-прежнему требует только `daemon.yaml`: порт и
   секрет на ходу не сменить. Кто
   подтверждает запись, решает клиент сессии (SPEC §7.2): Claude Code — своим диалогом разрешения
   на `odata1c_commit`, клиент с elicitation — вопросом демона; прочим клиентам `daemon.yaml` →
   `write_confirm_fallback: deny` (умолчание, запись недоступна) или `trust_client` (без
   подтверждения, на ответственность владельца). Механизм Claude Code демон выдаёт только клиенту,
   чьи заголовки подписал лаунчер ключом `launcher.key` (Ruling 59): ключ создают `odata1c init` и
   лаунчер при первом запуске, демон читает его только при старте — если ключ появился после
   старта демона (дом создан до Ruling 59), демон нужно перезапустить (`odata1c daemon stop`),
   иначе Claude Code получит второй вопрос — от демона. После обновления кода — перезапустить
   демон и в Claude Code `/mcp` → переподключить `odata1c` (перезапустится лаунчер).
8. **Раскрытие токена — только для владельца, мимо MCP:**
   `uv run odata1c reveal "[[inn:M4T2Q9XZ7K]]"` печатает реальное значение в терминал.

Приёмка на живой базе: `uv run python tools/probes/m1d_live_check.py` — прогоняет через настоящий
лаунчер десять вопросов чтения и сверяет работу гейта на настоящих данных; отчёт —
`docs/probes/M1d-live-check.md`. Этап `gate` правит рабочий дом: временные записи в `bases.yaml`
он возвращает на место сам, но обращение к защищённым полям кладёт токены в общий словарь
`gate.sqlite`, и **это не откатывается**. На базе с мусорным значением реквизита (`КПП` = `1`)
такая запись портит ответы всех баз домашнего каталога до ручной чистки словаря — см. находку 1
отчёта. Перед прогоном на чужом окружении сделайте копию `gate.sqlite`.

Этап `read` тоже на время прогона дописывает в `bases.yaml` одну запись — базу-ловушку для
вопроса 8 («отказ до обращения к 1С»): копию индекса базы по умолчанию с адресом локального
порта, который считает соединения, без учётных данных. Файл возвращается на место, каталог копии
удаляется; словаря `gate.sqlite` ловушка не касается (соединения закрываются без ответа). При
грубом обрыве прогона — вернуть `bases.yaml` из `bases.yaml.m1d-backup` и удалить
`bases/trade_dev_trap`. Прежний признак этого вопроса — строки httpx в `daemon.log` — после
Ruling 31 не работает: журнал адресов запросов не пишет.

Приёмка контактной информации и адресов (Ruling 33, 34):
`uv run python tools/probes/contact_info_live_check.py --label after`. Рабочий дом не трогает:
поднимает свой демон на временном домашнем каталоге (порт 7191) с копией индекса и политики и
пустым словарём, по завершении останавливает его и удаляет каталог. Печатает только счётчики,
имена полей и формы значений (цифра → 9, буква → a). Ключ `--only` запускает отдельные разделы
через запятую (`телефоны`, `почта`, `строки_без_типа`, `адреса`, `путь_владельца`, `оракул`,
`люди`, `инвариант_6`, `словарь`). Раздел `оракул` пускает демон к 1С через прокси-счётчик на
127.0.0.1:7192 и проверяет, что отказ случился до обращения к 1С (с положительным контролем).
`--reindex-policy` пересобирает раздел `auto` политики во временном доме текущим кодом — так, как
это сделает реиндекс владельца.

Приёмка записи M2: `PYTHONUTF8=1 uv run python tools/probes/m2_live_check.py --out итог.json`;
отчёт — `docs/probes/M2-live-check.md`. **Пишет в живую базу** `trade_dev` — только в объекты,
которые создаёт сам (маркер `odata1c-приёмка M2 <время>` в `Description` элемента
`Catalog_Номенклатура` и `Комментарий` документа `Document_ПересчетТоваров`), и откатывает их;
существующие объекты только читает. Рабочий дом не трогает: временный дом с копией записи базы и
двумя её копиями для отказов (`write: false`, `deny_fields`), свой демон на 7195. Между демоном и 1С
— прокси-счётчик на 127.0.0.1:7196: считает запросы по методам и не пропускает POST/PATCH ни к чему,
кроме объектов прогона, DELETE и PUT — никогда. Уборка в `finally`: проведённым — `Unpost`, всем —
`DeletionMark=true`, через шлюз, при его сбое — напрямую; поиск по маркеру подбирает объект, который
1С приняла, а прогон не записал. Один раз за прогон прокси отвечает `502` сам, не пересылая POST
в 1С, — так проверяется неизвестный исход записи (`commit_outcome_unknown`), и в базе от этого не
появляется ничего. `--only` запускает разделы (`тулы`, `создание`, `токен`, `пометка`,
`устаревание`, `числа`, `запреты`, `документ`, `часть`, `регистр`, `литерал`, `исход`, `ошибка_1с`,
`клиент`, `подпись`, `журнал`); `--only уборка` — только уборка по общему маркеру всех прогонов.

## Ключевые инварианты (нельзя нарушать при реализации)

1. Через MCP реальные значения защищаемых классов не выходят никогда — включая ошибки 1С,
   превью, журнал, `raw_get`, elicitation-сообщения. Значения, которые модель сама прислала в
   этом вызове, — тело записи («станет» в превью) и `key`, — повторяются как прислано (Ruling 44,
   45). Оговорка не касается ничего, что вывел сам шлюз: данных 1С, написания, выбранного по
   словарю, значений журнала, «станет» у `undo` — всё это маскируется. Страж утечек — последний
   проход по сериализованному ответу любого тула (кроме уровня `off`), инвариант, а не тест.
2. Запись двухфазная: пишущие тулы только готовят pending-операцию с превью (TTL 10 мин,
   привязка к сессии, отпечаток DataVersion); выполнение — только `odata1c_commit` после
   подтверждения пользователя механизмом клиента (диалог разрешения Claude Code / elicitation).
   `commit` идемпотентен по `pending_id`.
3. Нет `PUT`; физическое удаление — только записей независимых регистров сведений и только по
   флагу `independent_register_delete`; для объектов — пометка удаления.
4. Разрешения проверяются до создания pending-операции в строгом порядке (SPEC §7.1).
5. Токены детерминированы (HMAC-SHA256 от `gate_secret`), формат един `[[type:tail]]`;
   коллизия — удлинение хвоста до 16 символов.
6. Суммы, количества, даты, GUID, коды и номера документов не защищаются ни на одном уровне.

## Безопасность

- Домашний каталог и `bases.yaml` закрываются правами текущего пользователя (`icacls` /
  `chmod 700`); демон предупреждает о широких правах.
- Пароли 1С хранятся в `bases.yaml` открытым текстом — осознанное решение (диск владельца вне
  модели угроз); опционально `password: keyring`. Не коммитить реальные `bases.yaml` и секреты
  в репозиторий.
- Демон слушает только `127.0.0.1`, аутентификации нет; TLS и токены — этап M4. Механизм
  подтверждения Claude Code (запись без вопроса демона) демон выдаёт клиенту при двух условиях:
  лаунчер подписал его заголовки ключом `launcher.key` (Ruling 59) — это отсекает прямой `curl` к
  демону, — и лаунчер запущен исполняемым файлом Claude Code (проверка родительского процесса,
  Ruling 61) — это отсекает скрипт, сам запустивший `odata1c mcp` и назвавшийся `claude-code`. Обход
  остаётся видимой многошаговой цепочкой: переименовать интерпретатор в `claude.exe`; вписать в
  `.mcp.json` свой процесс с именем шима (`python.exe`, `uv.exe`, `odata1c.exe`) — его запустит сам
  Claude Code, и проверка родителя его пропустит (Р61-A; у того, кто правит `.mcp.json`, и так есть
  `bases.yaml` с паролем 1С); программа на Agent SDK, чей колбэк `canUseTool` одобряет тул; прочитать
  ключ и собрать подпись. Вложенный `claude -p` из Bash путь не открывает: Claude Code превращает
  `allow` от `--permission-prompt-tool` для такого тула в отказ. Против клиента, который сам отвечает «yes» на elicitation, ничто по
  возможностям клиента не защищает: последняя линия против записи из Bash модели — разрешения Claude
  Code на запуск Bash, полноценная защита — аутентификация человека (M4). SPEC §2.1, §2.2, §7.2.
- Содержимое полей 1С — данные, не инструкции (защита от prompt-injection: превью → явное
  подтверждение → commit; диалог клиента — последняя линия).
- Технические вопросы SPEC §15 закрыты пробами P1–P7 и приёмкой M1d (отчёты в `docs/probes/`):
  колёса под Windows (P1), `_meta` тула (P2), elicitation сквозь лаунчер (P3), реальный
  `$metadata` 1С (P4), ключ счёта по БИК — для групп 405, 407, 40102 (P5), скорость стража (P6),
  эхо переданного значения в тексте ошибки 1С — есть в шести формах запроса из четырнадцати (P7).
  Последний открытый вопрос — время холодного старта демона — закрыт приёмкой: 2,6 с
  (`docs/probes/M1d-live-check.md`).
- `logs/daemon.log` адресов запросов к 1С **не пишет** (Ruling 31): в адресе стоят уже раскрытые
  гейтом настоящие значения — ИНН, по которому модель искала токеном, название в отборе, — а
  журнал владелец отдаёт при разборе ошибок, то есть это тот же канал наружу, что и ответ тула.
  Логгеры HTTP-клиентов (`httpx`, `httpcore` и двойники `httpx2`/`httpcore2`) держатся на WARNING
  явно в `daemon._настроить_журнал`, а не порядком вызовов в `serve()`: до этого строки
  `HTTP Request: GET <полный адрес>` исчезли из журнала лишь случайно. Сторожа —
  `tests/unit/test_daemon_journal.py` и `tests/integration/test_journal_no_revealed.py` (живой
  демон). Трассировка уровня ERROR на внутренней ошибке шлюза тоже идёт через страж — на
  строжайшем уровне, с набором раскрытого этого вызова (`ToolService._записать_трассировку`,
  находка M-4 последнего ревью M1d); упала сама защита — пишется только класс исключения. Журнал
  при этом остаётся файлом с данными 1С (числа, коды, тексты полей без класса), и его стоит
  просматривать, прежде чем кому-то передавать.
- Проба P4 работает с тестовой базой через рабочий `bases.yaml` (база `trade_dev`); учётные
  данные в репозиторий не попадают, полный дамп `tests/fixtures/edmx/*.full.edmx` игнорируется.
- **Известное ограничение гейта (решение владельца, 2026-09-12): сокращённое название клиента в
  свободном тексте проходит открытым.** Живой пример из приёмки через настоящие инструменты:
  `Комментарий` документа — «…в ЦСКА по вх упд 711…», а название связанного контрагента
  (`[[org:16]]`) содержит «ЦСКА»; комментарий уходит модели как есть. Словарь знает только полные
  варианты названия (как есть и без формы собственности), и сокращение, которым люди пишут
  комментарии, ни одним из них не является. Ловить «ядро» названия без формы собственности
  отвергнуто: ядра — обычные слова («Альфа», «Вектор»), их замена в любом тексте портила бы данные
  ложными срабатываниями. Уровень `identifiers+names` скрывает названия в полях и их полные
  написания в тексте, но не гарантирует отсутствия узнаваемого сокращения в комментариях
  (SPEC §6.5, слой 3).
