# Плагин для OpenCode 2.x

Плагин `odata1c` поставляется в том же репозитории и работает на OpenCode V2:
модель получает те же девять тулов чтения и семь тулов записи MCP-шлюза, навыки,
агента-следователя и защиту файлов каталога шлюза, что и плагин Claude Code,
но через механизм плагинов OpenCode. Файлы навыков, агента и MCP-конфигурации —
те же самые (`plugin/`); отдельной копии под OpenCode нет намеренно: копии
расходятся при первой правке, и расходятся молча.

## Подключение

Требуются OpenCode V2 и установленная командная строка владельца:

```sh
uv tool install odata1c-gate
```

В конфиге OpenCode (`opencode.jsonc` проекта или пользователя):

```jsonc
{
  "plugins": ["odata1c-gate@git+https://github.com/Romandredan/odata1c-gate.git#v0.3.1"]
}
```

Тег `#v0.3.1` — первый выпуск с поддержкой OpenCode; закрепляйте версию явно,
а не `main`: в ветке разработки между выпусками может лежать промежуточное
состояние, не согласованное с версией пакета на PyPI.

Базы подключаются той же командной строкой, что и без OpenCode
(`uvx --from odata1c-gate odata1c base add …`, `reindex …`, разделы README
«Быстрый старт» и `docs/install.md`); навык `odata1c-setup` ведёт модель
по подключению базы диалогом, пароль модель не видит.

## Подтверждение записи

Подтверждение коммитов в OpenCode — нативный диалог разрешения на тул
`odata1c_commit`; его включает permission-правило плагина (правило 1):
пока пользователь не согласился, действие не разрешается. Отказ в вопросе
ничего не пишет.

Двухфазная запись остаётся прежней: пишущие тула возвращают превью в токенах
и `pending_id`, выполняет — только `odata1c_commit` после подтверждения. Диалога
от самого демона (elicitation) в OpenCode нет: `write_confirm_fallback`
в `daemon.yaml` для OpenCode-сессий нужно поднять до `trust_client`, иначе шлюз
блокирует запись за «нет механизма подтверждения» — теперь подтверждение
делает клиент, и это осознанно:

```yaml
# daemon.yaml в домашнем каталоге шлюза (~/.claude/odata1c)
write_confirm_fallback: trust_client
```

Если с OpenCode работает и Claude Code на той же машине, помните: `trust_client`
действует для любого клиента без elicitation — у Claude Code остаётся его
собственный вопрос, а у скриптов, запущенных моделью через оболочку, вопроса
попросту нет. Permission-аск на `odata1c_commit` закрывает прямой вызов тула
моделью, но не оболочку. Подробности о том, что это даёт и чего не даёт, —
в разделе «Безопасность» AGENTS.md репозитория.

## Ручной шаг: модель агента

Файл агента `odata1c-investigator` несёт `model: haiku` в frontmatter —
Claude-специфичное поле; OpenCode его отбрасывает безвредно, и по умолчанию
следователь работает на модели сессии. Выделить ему дешёвую модель — записать
имя агента в конфиг OpenCode ключом `agents` (свойство `model`), решение —
за владельцем машины:

```jsonc
{
  "agents": { "odata1c-investigator": { "model": "opencode/glm-5-free" } }
}
```

## Что плагин регистрирует

- **Четыре навыка** из `plugin/skills/` (`odata1c`, `odata1c-policy`,
  `odata1c-recipe`, `odata1c-setup`) — программно через `ctx.skill.transform`:
  каталог `.opencode/skills/…` сканируется только в проекте и в конфигурационном
  каталоге пользователя, до кэша установленного пакета сканер не достаёт.
- **Агента `odata1c-investigator`** — через `ctx.agent.transform`; строка
  `tools:` frontmatter Claude-специфична и не переносится, её заменяют
  permissions: читательский канонический набор тулов шлюза разрешён, тулы записи,
  `reindex`, `journal`, правка файлов, оболочка и запуск субагентов закрыты.
- **MCP-сервер гейта** — через `ctx.mcp.transform` с закреплённой версией пакета;
  команду плагин читает из `plugin/.mcp.json` (её формирует
  `tools/bump_version.py`), у точки входа OpenCode отдельной копии версии нет.
- **Хуки защиты** — `ctx.tool.hook("execute.before")` и
  `ctx.permission.hook("evaluate")`.

## Защита каталога шлюза

Правила хука `PreToolUse` Claude Code перенесены один в один, то же алгоритм,
порядок проверок и причины:

- чтение и правка защищённых файлов домашнего каталога шлюза (`bases.yaml`
  с паролем 1С, `daemon.yaml`, `launcher.key`, `gate.sqlite` и `journal.sqlite`
  с реальными значениями, вместе с `-wal`/`-shm` и резервными копиями) —
  закрыты для `read`, `edit`, `write`, `multiedit`, `notebookedit`;
- поиск по дому целиком (`grep`, `glob` с путём на дом или его предок,
  `glob` с абсолютным шаблоном на дом) — закрыт;
- команды оболочки, называющие защищённые файлы, `reveal`, `sqlite3` рядом
  с базами, шаблон в каталоге шлюза и массовое чтение дома — закрыты.

Правило 1 (`odata1c_commit` → подтверждение) — нативный permission-аск,
замена механизма, а не порт (см. раздел «Подтверждение записи»).

Известная граница: тул `patch` OpenCode в число покрываемых тулов правила 2
не входит — правка им защищённого файла шлюза не перехватывается. Пока правило
не покрывает `patch` отдельно, закройте его правилом permissions проекта
(`{ "action": "patch", "resource": "<путь дома>/**", "effect": "deny" }`).

## Отличия от плагина Claude Code

- Подтверждение записи — permission-аск с фиксированной причиной; `pending_id`
  у события нет и диалога демона (elicitation) этот вопрос не заменяет —
  решение владельца в ишью #2 от 2026-11-03.
- Тул-хук OpenCode прерывает вызов исключением: сообщение ошибки = причина
  запрета, тот же фиксированный текст.
- Версия `X.Y.Z.devN` между выпусками пишется в `package.json` npm-семвером
  `X.Y.Z-devN`; `package.json` — пятое место поставки, правит его
  `bump_version.py`, отдельной копии версии у точки входа OpenCode нет.
- Домашний каталог — общий с Claude Code: дефолтный `~/.claude/odata1c`
  в обоих харнессах закрывается одинаково, `ODATA1C_HOME` сессии — своё.

## Проверка и разработка плагина

- `node tests/opencode-odata1c.test.mjs` — все сценарии защиты и состав
  плагина (`ctx` — мок); шаг включён в CI.
- `opencode/plugin/odata1c.js` — точка входа `{ id, setup }`, импортирует
  только `node:*` и свои модули; `opencode/plugin/guard-core.mjs` — ядро
  правил 2–3; `opencode/plugin/registry.mjs` — разбор файлов плагина
  (навыки, агент с permissions).
- Python-тесты репозитория JS-часть не касаются; `pytest` остаётся прежним,
  приёмка плагина на живой базе — вживую, по сценариям M2.
