# Разрешения на запись задаются ролью базы и флагами; физическое удаление только в независимых регистрах сведений

В v0.1 у базы был один флаг `read_only`, а физического удаления не было вовсе. Этого недостаточно: у записей регистров нет `DeletionMark`, и ошибочную запись независимого регистра сведений иначе не убрать; прямая запись в регистры накопления и бухгалтерии обходит логику документов и должна быть закрыта по умолчанию; для боевой, тестовой и отладочной базы нужны разные умолчания без десятка флагов в каждой записи. Введены роли `prod | test | dev` как профили умолчаний и явные флаги `write`, `post_documents`, `mark_deletion`, `independent_register_delete`, `register_direct_write`, `deny_entities`, `deny_fields`.

## Considered Options

- **`DELETE` для любых регистров.** Отвергнуто пользователем: зависимые регистры меняются только через документ-регистратор, удаление их записей напрямую рассогласовывает учёт.
- **`DELETE` для документов и справочников за тем же подтверждением.** Отвергнуто: 1С удаляет без контроля ссылочной целостности, пометка удаления обратима, а удаление нет.
- **Только `read_only` без ролей.** Каждая база требовала бы полного набора флагов; ошибка в одном флаге боевой базы дорого стоит.

## Consequences

- Тул `odata1c_delete_record` существует, но доступен только для сущностей с `is_independent_register` и только при включённом флаге; `undo` для него — повторный `POST` записи из журнала.
- Роль печатается в `odata1c_bases()` и в каждом ответе пишущего тула: модель и пользователь всегда видят, боевая ли это база.
- Лимит коммитов за 10 минут тоже задаётся ролью: `prod` 20, `test` 50, `dev` без лимита.
- Отказ по разрешению возвращает имя флага и файл, где его включить; модель не должна искать обходной путь.
