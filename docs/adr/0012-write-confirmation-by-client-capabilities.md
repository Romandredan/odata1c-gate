# Подтверждение записи выбирается по возможностям клиента; Claude Desktop и Cowork не поддерживаются

ADR-0005 опирался на `_meta["anthropic/requiresUserInteraction"]`, которую понимает только Claude Code. Шлюз должен подключаться и к другим агентам, а подтверждение обязано оставаться действием пользователя, которое модель не может выполнить сама. Проверено по документации на 2026-09-07: `requiresUserInteraction` задокументирована в Claude Code (диалог на каждый вызов, без «не спрашивать больше», отказ в `dontAsk`); elicitation поддерживает Claude Code с 2.1.238; Claude Desktop elicitation не поддерживает; Cowork возвращает `cancelled` и исполняет серверы в VM без доступа к loopback хоста. Выбрано: демон на `initialize` читает имя клиента и `capabilities.elicitation` и назначает механизм сессии — `requiresUserInteraction` плюс хук для Claude Code, elicitation-диалог для клиентов с его поддержкой, отказ в записи для остальных.

## Considered Options

- **Локальное окно подтверждения от демона** для клиентов без elicitation. Отвергнуто: пользователь не хочет окон вне чата, а после отказа от Desktop и Cowork клиентов без elicitation среди целевых не осталось.
- **Поддержка Desktop и Cowork через stdio и окна.** Отвергнута пользователем: Desktop без elicitation, Cowork без доступа к демону; стоимость поддержки не окупается.
- **Доверять диалогу разрешения любого клиента.** Клиент может разрешить тул «навсегда», и подтверждение исчезнет; оставлено как явная опция `write_confirm_fallback: trust_client` на ответственность пользователя.

## Consequences

- Претензии к транспорту сняты: оба механизма живут в `tools/list` и в протоколе, а не в stdio или HTTP.
- Лаунчер обязан пробрасывать elicitation от демона к stdio-клиенту и ответ обратно (SPEC §15, проверка 2).
- Для Claude Code elicitation не дублируется: два диалога подряд на один `commit` утомляют и обесценивают подтверждение.
- Текст elicitation-запроса проходит гейт, как любой ответ: реальные значения в диалог не попадают.
