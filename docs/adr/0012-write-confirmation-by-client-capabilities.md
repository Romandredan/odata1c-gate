# Подтверждение записи выбирается по возможностям клиента; Claude Desktop и Cowork не поддерживаются

ADR-0005 опирался на `_meta["anthropic/requiresUserInteraction"]`, которую понимает только Claude Code. Шлюз должен подключаться и к другим агентам, а подтверждение обязано оставаться действием пользователя, которое модель не может выполнить сама. Проверено по документации на 2026-09-07: `requiresUserInteraction` задокументирована в Claude Code (диалог на каждый вызов, без «не спрашивать больше», отказ в `dontAsk`); elicitation поддерживает Claude Code с 2.1.238; Claude Desktop elicitation не поддерживает; Cowork возвращает `cancelled` и исполняет серверы в VM без доступа к loopback хоста. Выбрано: демон на `initialize` читает имя клиента и `capabilities.elicitation` и назначает механизм сессии — `requiresUserInteraction` плюс хук для Claude Code, elicitation-диалог для клиентов с его поддержкой, отказ в записи для остальных.

Поправка 2026-09-13 (план M2, задача 9): решение не меняется, уточнено, как демон узнаёт клиента.
Через лаунчер `initialize` демону шлёт сам лаунчер (имя `mcp`, elicitation всегда), поэтому клиента
лаунчер пересылает заголовками HTTP, а механизм выбирается первым пишущим вызовом сессии, не на
`initialize` (SPEC §2.1, §7.2). Claude Code узнаётся по имени `claude-code` дословно, по перечню, и
версии не ниже 2.1.246: похожее имя другого клиента получило бы запись без подтверждения, а до
2.1.246 диалог разрешения можно было снять навсегда.

Поправка 2026-09-13 (Ruling 59, раунд 2 задачи 9): механизм Claude Code — только клиенту, заверенному
подписью лаунчера. Имя клиента не заверено ничем, и любой локальный процесс — в том числе `curl` из
Bash модели после prompt-injection в данных 1С — назывался `claude-code` и получал запись без
единого диалога (ревью задачи 9). Лаунчер подписывает заголовки своего клиента HMAC-SHA256 ключом
`launcher.key` домашнего каталога с привязкой к `mcp-session-id`; демон проверяет подпись при выборе
механизма и на каждом пишущем запросе сессии Claude Code (идентификатор сессии не секрет — SDK пишет
его в журнал демона). Без верной подписи клиент — обычный: с elicitation демон спрашивает сам, без
неё — `deny`/`trust` по `write_confirm_fallback`; неподписанный запрос в сессии Claude Code к любому
пишущему тулу (подготовка, откат, `commit`) — отказ до сервиса: всё пишущее в такой сессии — только
от её лаунчера (Р59-А).

Поправка 2026-09-13 (Ruling 61, итоговое ревью M2): подпись доказывает «через лаунчер», а не «это
Claude Code» — любой скрипт может сам запустить `odata1c mcp` и назваться `claude-code` (находка И-2,
ревьюер это исполнил). Поэтому механизм Claude Code требует и второго условия: лаунчер при старте
заверяет имя `claude-code` по своему родительскому процессу (поднимаясь мимо шимов запуска —
`uv`/`python`/`odata1c.exe` — до первого значимого предка) и передаёт результат заголовком в составе
подписи; демон даёт `claude_code`, только когда `verified and parent_is_claude_code`. Подпись
отсекает прямое обращение к демону, родитель — скрипт, запустивший лаунчер. Граница честная: обход
остаётся (переименовать интерпретатор в `claude.exe` и запустить лаунчер от него, либо прочитать
`launcher.key` и собрать подпись — видимая многошаговая цепочка), и подтверждение от враждебного
процесса под тем же пользователем держится на разрешениях Claude Code на запуск Bash. Полноценная
защита — аутентификация человека; сетевая аутентификация M4 её не заменяет (SPEC §2.1, §2.2, §7.2).

## Considered Options

- **Локальное окно подтверждения от демона** для клиентов без elicitation. Отвергнуто: пользователь не хочет окон вне чата, а после отказа от Desktop и Cowork клиентов без elicitation среди целевых не осталось.
- **Поддержка Desktop и Cowork через stdio и окна.** Отвергнута пользователем: Desktop без elicitation, Cowork без доступа к демону; стоимость поддержки не окупается.
- **Доверять диалогу разрешения любого клиента.** Клиент может разрешить тул «навсегда», и подтверждение исчезнет; оставлено как явная опция `write_confirm_fallback: trust_client` на ответственность пользователя.
- **Оставить имя клиента без проверки до M4** (поправка 2026-09-13). Отвергнуто владельцем (Ruling 59): обход — одна команда `curl`, ровно тот сценарий prompt-injection, ради которого подтверждение и существует. Подпись лаунчера стоит одной правки лаунчера и демона и прозрачна для настоящего Claude Code.
- **Ограничиться подписью лаунчера, не проверяя родителя** (поправка 2026-09-13, Ruling 61). Отвергнуто: подпись заверяет «через лаунчер», и скрипт, сам запустивший `odata1c mcp` с именем `claude-code`, её проходит (И-2). Проверка родителя закрывает этот путь той же ценой — правкой лаунчера, прозрачной для настоящего Claude Code; кодовую хрупкость (опрос дерева процессов) приняли ради честной границы.
- **Требовать от Claude Code объявленной elicitation** (Н9-1 ревью). Не принято в этом раунде: в протоколе 2026-07-28 запросы сервера к клиенту запрещены, и настоящий Claude Code на нём elicitation для демона не имеет; каким протоколом он договаривается с лаунчером — вопрос приёмки.

## Consequences

- Претензии к транспорту сняты: оба механизма живут в `tools/list` и в протоколе, а не в stdio или HTTP.
- Лаунчер обязан пробрасывать elicitation от демона к stdio-клиенту и ответ обратно (SPEC §15, проверка 2).
- Для Claude Code elicitation не дублируется: два диалога подряд на один `commit` утомляют и обесценивают подтверждение.
- Текст elicitation-запроса проходит гейт, как любой ответ: реальные значения в диалог не попадают.
