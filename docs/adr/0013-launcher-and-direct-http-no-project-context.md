# Лаунчер stdio ради установки без действий, HTTP того же демона для прямых подключений; проектный контекст не передаётся

ADR-0001 держал stdio-прокси ради одной задачи: передать демону путь проекта из `CLAUDE_PROJECT_DIR`, чтобы прочитать `.odata1c.yaml`. Обсуждение показало, что проектный файл не нужен: базы описываются один раз на машину, а модель выбирает базу по имени и подписи. Без проектного контекста прокси мог бы исчезнуть в пользу прямого HTTP, но тогда установка перестаёт быть автоматической: плагин Claude Code умеет объявить сервер, а не поставить службу, и демон пришлось бы запускать вручную. Выбрано: плагин объявляет stdio-лаунчер `uvx odata1c mcp`, который создаёт домашний каталог, поднимает демон при необходимости и проксирует MCP; HTTP-адрес демона одновременно открыт для агентов, подключающихся по URL. Сужение видимых баз для проекта — необязательные аргументы лаунчера `--bases` и `--default`.

## Considered Options

- **Только HTTP, базы в URL** (`/mcp/ut,buh?default=ut`). Отвергнуто пользователем: при едином файле настроек список баз в URL избыточен, а демон без лаунчера требует ручного запуска или службы.
- **Только stdio, полный сервер на сессию.** N сеансов 1С, словарь и журнал через файловые блокировки, семафор на базу между процессами; отвергнуто ещё в ADR-0001.
- **Прокси с `CLAUDE_PROJECT_DIR` и `.odata1c.yaml`** (ADR-0001). Отвергнуто: лишний файл на проект и зависимость от одного клиента.

## Consequences

- `CLAUDE_PROJECT_DIR`, заголовки с путём проекта, подстановка `${VAR}` в `headers` и их баги из дизайна ушли.
- Домашний каталог по умолчанию `~/.claude/odata1c/`, переопределяется `--home` или `ODATA1C_HOME`, чтобы не зависеть от папки Claude.
- На loopback аутентификации нет: локальные процессы вне модели угроз. Публикация по сети (M4) добавит TLS и токены, не меняя транспорта.
- Демон живёт до остановки или перезагрузки; служба Windows — опция `service install`, не требование.
