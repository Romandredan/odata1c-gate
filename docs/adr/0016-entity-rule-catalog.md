# Правила отдельных сущностей и имён полей — в каталоге YAML по происхождению сущностей, сопоставление по наличию сущности в индексе, каталог владельца для доработок

Авторазметка гейта (`policy.auto.yaml`, ADR-0015) строится классификатором полей по имени (`field_rules.py`): общие правила — регулярные выражения по имени поля — и явные списки, сверенные с `$metadata` конфигурации: справочники людей и организаций (Ruling 36), исключения полными именами полей (`ЮрФизЛицо`, `ДолжностьРуководителя`). Списки жили константами в коде. Разведка Бухгалтерии предприятия (`docs/probes/BP-recon.md`, 2026-09-24) показала, что с каждой новой конфигурацией таких правил прибавляется десятками: номер документа физлица закрывается только в регистре документов физлиц (общее `^номер$` закрыло бы номера всех документов, инвариант 6), имя в поле `ИмяРебенка` — только полным именем (с «Имя» начинаются сотни служебных полей), справочник родственников — справочник людей. Выбрано: такие правила лежат файлами YAML в едином формате — каталогом правил сущностей; каталог поставки разложен по происхождению сущностей (платформа и общие библиотеки, зарплата и кадры, УТ, БП), каталог владельца в домашнем каталоге шлюза держит правила доработанных конфигураций; правило действует на любой базе, в индексе которой есть его сущность.

## Considered Options

- **Оставить правила константами в коде.** Каждое правило — правка кода и выпуск; списки растут вместе с числом конфигураций, а код классификатора превращается в справочник имён. Отвергнуто владельцем: нужна унификация под пополнение.
- **Профиль правил по полю `config` базы** (`templates/gate/<config>.yaml`, как библиотека рецептов). База без `config` или с опечаткой в нём молча осталась бы без правил — защита отказывает в открытую сторону; правила общих сущностей (регистр документов физлиц есть в УТ, БП и ЗУП) копировались бы в каждый профиль. К тому же конфигурацию и так видно по индексу: перечислять её в `bases.yaml` незачем (довод владельца).
- **Каталог, сопоставляемый по наличию сущности в индексе** — выбран. Имена сущностей типовых библиотек (БСП, БЗК, БЭД) одинаковы во всех конфигурациях, куда библиотека встроена; правило на отсутствующую сущность ничего не делает. Раскладка по файлам служит сопровождению и на сопоставление не влияет.
- **Каталог владельца отдельным слоем или правила доработок в `policy.yaml` базы.** `policy.yaml` принадлежит одной базе, а у доработанной конфигурации бывает несколько баз (боевая, тестовая, разработки). Каталог владельца в том же формате пишется один раз на конфигурацию; `policy.yaml` остаётся для исключений одной базы.
- **`keep` в каталоге.** Отвергнуто: открыть поле целиком, без поиска реквизитов, вправе только владелец в `policy.yaml` (ADR-0015). Каталогу доступно `scan` — «по имени не классифицировать»: реквизиты в значении ищут детекторы, как в любом тексте.

## Consequences

- Формат файла (`version: 1`): `people` и `orgs` — справочники людей и организаций (слой 1 SPEC §6.5), `addr_mask_for` — сущности не-справочники, чьи адреса принадлежат физлицам (SPEC §6.9), `fields` — `Сущность.Поле: класс` (для регистра действует и на набор записей и виртуальные таблицы), `names` — `ИмяПоля: класс` в любой сущности. Класс — любой класс гейта, кроме `keep`, или `scan`.
- Порядок классификации поля: служебное поле → `fields` → `names` → реквизиты по имени поля → слой 1 → слой 2. Каталог владельца главнее каталога поставки на совпадающем ключе; `policy.yaml` главнее авторазметки, как прежде.
- Каталог поставки — `odata1c/templates/gate/*.yaml`, каталог владельца — `<дом>/gate/*.yaml`. Каталог несёт действующая политика базы: реиндекс, запасные пути классификации маскировщика и обратной подмены видят одни правила. Каталог владельца перечитывается по изменению файлов, как `policy.yaml`; авторазметка по новым правилам строится реиндексом (`odata1c reindex <база>`, без `--force`).
- Негодный файл каталога владельца (неизвестный раздел, класс вне списка, `keep`, одно правило с разными классами в двух файлах) закрывает тулы базы ошибкой `policy_invalid` с путём файла и местом, без значений, пока владелец не починит, — как негодный `policy.yaml`. Каталог поставки проверяют тесты: разбор, сторож справочников людей (Ruling 36) и обратный сторож «каждое имя каталога есть в полном `$metadata` хотя бы одной конфигурации» на дампах УТ и БП.
- Команды конструктора для каталога владельца в этой поставке нет: файл пишется по шапке любого файла каталога поставки.
- Синхронно меняются: SPEC §4.3, §6.4, §6.5, §6.9, §16; `CONTEXT.md` (термины «каталог правил сущностей», класс `sfr`); `AGENTS.md` (структура репозитория и домашнего каталога). Принято владельцем 2026-09-24 (Ruling 106–109); проект — `docs/superpowers/specs/2026-09-24-bp-gate-rules-design.md`.
