# Решения владельца в двух файлах: `bases.yaml` на машину и `policy.yaml` на базу; авторазметка в отдельном порождённом файле; настройки действуют без перезапуска; политика собирается конструктором, а не руками

ADR-0014 сделал `bases.yaml` единственным файлом настроек на машину, но у владельца всё равно три точки: `bases.yaml` (читается только при старте демона), `policy.yaml` базы, где его правила лежат вперемешку с разделом `auto` на тысячи строк, который переписывает реиндекс и который при каждой перезаписи стирает комментарии владельца, и `daemon.yaml`. Для распространяемого продукта это барьер: непонятно, где что задавать, чем правка включается и что вообще можно задать. Выбрано: `bases.yaml` держит, кто база и как с ней работать (реквизиты, роль, соединение, запись, уровень гейта); `bases/<база>/policy.yaml` держит, что именно скрывать и что открыть, и принадлежит только владельцу: создаётся при `base add` из самодокументированного шаблона, где перечислены все классы и разделы, и машиной не переписывается никогда; всё, что вычислил реиндекс, уходит в `bases/<база>/policy.auto.yaml`; `bases.yaml` демон перечитывает при изменении файла, как уже перечитывает политику; правила в `policy.yaml` владелец добавляет не вручную, а конструктором: командами `odata1c policy …` из терминала под руководством навыка плагина. `daemon.yaml` остаётся техническим файлом на машину.

## Considered Options

- **Перенести правила гейта в `bases.yaml`, раздел `gate`** (первая редакция этого ADR). Один файл вместо двух, но нужна миграция существующих политик, а раздел на десятки строк с примерами всех классов раздувает запись каждой базы. Отвергнуто владельцем: отдельный файл политики на базу удобен и понятен.
- **Оставить один `policy.yaml` с разделом `auto` внутри.** Тогда шаблон с пояснениями невозможен: реиндекс переписывает файл через YAML и теряет комментарии, а правила владельца тонут в тысячах строк авторазметки.
- **Без порождённого файла, авторазметка только в памяти.** Владелец не видит, что машина отнесла к защищаемому, и реиндекс не может показать «новые поля на проверку» сравнением со старой авторазметкой (SPEC §4.3).
- **Модель правит политику сама через тул MCP.** Отвергнуто: данные 1С могут подтолкнуть модель открыть поле (`keep`). Политику меняет только команда CLI в терминале владельца, как `reveal`; навык лишь ведёт по шагам и готовит команду.
- **Подтверждение записи на базу** («для `dev` не спрашивать»). Спрашивает клиент, а не шлюз; флаг стоит на определении тула, один на все базы сессии. Инвариант 2 не меняется.

## Consequences

- `bases.yaml` → `gate` сокращается до `mode`. `names_for` и `scan_free_text` переезжают в `policy.yaml`: это «что скрывать», а не «скрывать ли». Мёртвый дубль `gate.scan_free_text` исчезает.
- `policy.yaml` создаётся при `base add` из шаблона с перечнем классов и примерами каждого раздела; формат разделов прежний (`version`, `scan_free_text`, `names_for`, `defaults`, `entities`, `fields`, `custom`). Реиндекс перестаёт его трогать и пишет только `policy.auto.yaml`; раздел `auto` из существующих политик он уносит туда сам при первом же реиндексе. Действий владельца не нужно.
- Действующая политика собирается в памяти: правила владельца поверх авторазметки, приоритет прежний: `fields` > `custom` > `defaults` > авторазметка. `odata1c policy show` и ресурс `odata1c://policy/{base}` печатают итог с источником каждой строки, с фильтрацией скрытых имён (Ruling 29).
- Конструктор: `odata1c policy check` (проверка файла по индексу: имена сущностей и полей, классы, regex, противоречия, что затронет каждое правило), `policy hide | open | set | custom` (запись правила с сохранением комментариев файла). Навык плагина ведёт владельца: что скрыть или открыть → найти сущность и поле тулами чтения → команда → проверка → контрольный запрос. Запись в файл с сохранением комментариев требует обратимого разбора YAML (`ruamel.yaml`): новая зависимость оправдана постоянной функцией, а не разовой миграцией.
- `bases.yaml` перечитывается по изменению файла перед вызовом тула. Непригодный файл закрывает все тулы кодом `config_invalid` с путём и строкой, пока владелец не починит. Разрешения перепроверяются при `commit` по текущему файлу. Смена уровня гейта посреди сессии сообщается моделью строкой в `warnings`.
- Правила, общие для нескольких баз одной конфигурации, задаются якорями YAML внутри `bases.yaml`; для политик двух баз одной конфигурации файл копируется (`policy copy <из> <в>`), общего слоя нет.
- Синхронно меняются: SPEC §2.3, §3.1, §3.5, §4.3, §6.5, §6.9, §7.1, §11.2, §14, §16; `CONTEXT.md` (термин «политика», новые термины «авторазметка» и «конструктор политики»); `AGENTS.md` (запуск, реиндекс, перезапуск демона). Проектных файлов настроек по-прежнему нет (§14.8).

План реализации — `docs/plans/2026-09-14-owner-policy-constructor.md`.
