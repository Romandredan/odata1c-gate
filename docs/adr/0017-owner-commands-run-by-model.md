# Команды владельца выполняет модель через CLI; снижение защиты проходит через подтверждение человека

ADR-0015 отдал правку политики конструктору `odata1c policy …` и закрепил, что команду набирает и запускает владелец в своём терминале, а модель лишь печатает её: содержимое полей 1С может подтолкнуть модель открыть поле, которое открывать не просили. Полей записи базы — уровня гейта, записи, подписи, роли, разрешений — это не касалось вовсе: команды для них не было, владелец правил `bases.yaml` руками, а файл закрыт от модели хуком (в нём пароль 1С). Владелец решил 2026-10-01 (проект `docs/superpowers/specs/2026-10-01-base-set-design.md`): он управляет базами шлюза в диалоге с моделью — «сделай `trade_dev` только для чтения с полным гейтом», — и модель делает это сама; в терминал он не ходит, файл с паролем модель по-прежнему не видит. Выбрано: появляется команда `odata1c base set` для полей записи базы и скалярных разрешений; модель выполняет её и команды конструктора политики сама по навыкам плагина; команда, которая **снижает защиту** (уровень гейта ниже `identifiers+names`, включение записи, роль `test`/`dev`, включение разрешения, любой лимит коммитов, возврат поля к умолчанию роли, любой ключ, которого хук не знает, `policy open` и `policy set … keep|scan`, равнозначный `open`), выполняется только после явного согласия владельца в отдельном сообщении, и хук плагина переводит её в диалог разрешения Claude Code — тот же человеческий барьер, что страхует `odata1c_commit`. Тула MCP для настроек и политики по-прежнему нет.

## Considered Options

- **Оставить терминал владельца** (ADR-0015 как есть, `base set` — тоже команда для терминала). Отвергнуто владельцем: цель — управлять шлюзом в диалоге, а не диктовать команды; модель и так видит всё, что печатает команда (реквизитов там нет).
- **Тул MCP с подтверждением по `_meta`**, как у `odata1c_commit`: работает в любом клиенте, не зависит от хука и от `PATH`. Отвергнуто: демону не нужен путь записи в собственную конфигурацию; конструктор политики остался бы отдельным механизмом с другим правилом, а решение ADR-0015 «тула MCP для политики нет» сохраняется — данные 1С не должны иметь прямой дороги к настройкам защиты через протокол модели.
- **Собственное интерактивное подтверждение команды** (вопрос в терминале при снижении защиты). Отвергнуто: у Bash модели нет терминала, `--yes` или `yes |` обходят вопрос одной строкой; человеческий барьер должен лежать вне канала, которым распоряжается модель.
- **Модель выполняет всё без разделения** на снижающие и повышающие команды, последняя линия — разрешения Claude Code на Bash. Отвергнуто: в автоматическом режиме Bash текст из данных 1С с инъекцией выключил бы гейт одной командой; разделение стоит одного лишнего диалога.
- **Правка файла баз через `ruamel.yaml`, как у конструктора политики.** Отвергнуто: новый ключ обратимый разбор дописал бы в конец записи, закомментированный образец с прежним значением остался бы выше и вводил бы в заблуждение, а заголовки «умолчание роли prod» после смены роли устаревали бы. Файл правится текстом по разметке разбора PyYAML (`yaml.compose` даёт номер строки каждого ключа), строки рисуют те же помощники, что у `base add`.
- **Узнавать снижающую команду регулярным выражением по всей строке** (первоначальный проект, §3.3). Отвергнуто при реализации: ключ `--home` перед `base`, кавычки, переносы строки и цепочки команд ломали образец в обе стороны — пропускали снижение и принимали за него безобидное. Правило 4 разбирает команду по токенам.

## Consequences

Нормативный текст — SPEC §3.1 (команда и правка файла) и §11.2 (хук); здесь решения и их доводы.

- `odata1c base set <база>` меняет `gate.mode`, `write`, `label`, `role`, `permissions.post_documents`, `permissions.mark_deletion`, `permissions.independent_register_delete`, `permissions.commit_limit`; значение `default` снимает явное поле. Строки не затронутых полей и комментарии владельца сохраняются байт в байт, запись атомарна. Явное значение пишется явно и при совпадении с умолчанием роли (как `base add --gate`): так оно не зависит от последующей смены роли. Адрес, пользователь и пароль командой не меняются и не печатаются. Списки сущностей и полей и флаг `register_direct_write` — вне первой поставки.
- Правка файла. Записи в нестандартной форме (поточные, с ключом слияния, с повторами ключей, с разделом `gate` или `permissions` в одну строку) не правятся, потому что по ним нет однозначной строки. Файл с якорями или ссылками YAML (`&имя`, `*имя`) не правится: разметка разбора указывала бы на строки чужой записи, а правка записи-источника молча меняла бы ссылающиеся. Каждая активная строка после разбора сверяется со строкой файла: разделители строк `U+2028`, `U+2029`, `U+0085` и одиночный `\r` сдвигают номера строк PyYAML относительно деления по `\n`, и без сверки правка попала бы в чужую строку. Схема настроек (pydantic-модель загрузчика) проверяет исходный текст до правки, новый — до построения результата, а контрольное чтение после правки сверяет каждое запрошенное поле с тем, что прочтёт демон: файл, который демон отверг бы, не правится и не пишется; `password: keyring` при проверке не разрешается, чтобы не трогать хранилище ОС. Пустой или отсутствующий раздел `bases` — нет баз (`base_unknown`), как у загрузчика. Окончания строк берутся по первой строке файла, чтобы байты файла после правки были предсказуемы. Поле, запрошенное с теми же значением и источником, не переписывается, чтобы сохранить комментарий владельца. `--role` переписывает (или вставляет) собственную строку `role`, прочие активные строки не трогает, кроме стандартного хвоста `# по роли — true|false` у активной `write`; образцы и заголовки «умолчание роли …» обновляются только известных форм, комментарии владельца других форм остаются как есть. Подпись пишется одной строкой (`width=inf`, и в `base add`) ради правила «одно поле — одна строка»; уже многострочную команда не правит. Сбой `os.replace` (на Windows файл занят демоном) — до десяти попыток, затем временный файл удаляется и команда отказывает без следов. Тексты отказов не содержат значений из файла, цепочка исключений обрезана (`from None`): в файле пароль.
- CLI. `--label` — одна строка: управляющие символы и разделители строк (категории Unicode `Cc`, `Zl`, `Zp`) недопустимы в однострочной подписи, прочие пробелы допустимы; пробелы по краям обрезаются, пустая подпись отклоняется. `cmd_base_set` не читает `load_config`: пароль и хранилище ключей команде не нужны. Все парсеры CLI — `allow_abbrev=False`: иначе сокращение (`--gat`) выполнилось бы, а хук ключ не узнал бы. Вывод всех команд в канале — UTF-8, включая справку и отказы `argparse`; перевод касается всех команд, включая `mcp` (её сообщения в stderr), а канал JSON-RPC лаунчера не затрагивает, потому что тот идёт через двоичный дескриптор SDK. Причина: вывод читает модель через Bash, а на Windows поток в канале кодировался бы кодовой страницей. Строка «задано явно, роль не влияет: …» печатается только при действительной смене роли, колонки выровнены по данным, строки идут в порядке полей записи.
- Хук `PreToolUse`, правило 4 (SPEC §11.2). Команда разбирается по токенам, а не одним регулярным выражением: для каждого слова `odata1c` или `odata1c.exe` в любой форме запуска ключи с дефисом пропускаются, у `--home` — вместе со значением, до `base set`, `policy open` или `policy set`; переносы строки склеиваются до разбора, хвост ограничен разделителем цепочки. Снижают защиту `--gate` кроме `identifiers+names`, `--write on`, `--role test|dev`, включение трёх разрешений, любой `--commit-limit`, любой `default` и любой неизвестный хуку ключ (`-h` и `--help` нейтральны); неразобранный хвост (незакрытая кавычка, `\"` и любая обратная кавычка в PowerShell, `$'…'` в Bash) — тоже снижение. Раскрытие оболочки закрыто вопросом, а не разбором: слово в позиции имени ключа, группы, подкоманды или класса `policy set` либо распознано, либо целиком состоит из букв, цифр и символов `_ . - :` (разрешительный список), иначе — `ask` «команда odata1c не разобрана»; так закрыты `ba$()se`, `$s`, `@a`, `%VAR%`, `^`, glob (`s?t`, `ba[s]e`), а в PowerShell — команда с `--%`. В хвосте `base set` токен с `$`, обратной кавычкой, `(`, `{`, `@` или `%` — снижение с пометкой «(раскрытие оболочки)», в том числе значение `--label` и `--home` (переменная может хранить `--gate off`); значение `--home` с такими символами до подкоманды — «не разобрана», в `policy set` — открытие. Слово `odata1c` с `/`, `\` или `-` сразу за ним — путь или имя пакета, не вызов. Хук не знает текущих значений и роли, поэтому ошибается в сторону вопроса. `policy open` и `policy set … keep|scan` дают `ask` «открывает поле модели»: классы `keep` и `scan` снимают закрытие так же, как `open`; закрывающие классы, `custom:<имя>`, `hide`, `show`, `check` проходят молча. Несколько команд в одной строке дают один `ask` с объединённой причиной; имена баз и ключи в причине — значения из события, не из файла. `deny` правила 3 (`reveal`, файлы дома) старше.
- Навыки: новый `odata1c-base`. `hide` (с `--yes`: у Bash модели нет терминала, вопрос о дочерних сущностях переезжает в сообщение модели) и `set` с закрывающим классом модель выполняет сама. `open` и `set … keep|scan` — только после согласия владельца в отдельном сообщении и с подтверждением диалогом. `odata1c-setup` отсылает к `odata1c-base`; `odata1c` снимает запрет «не выполнять `odata1c policy …`» (запретов остаётся четыре: файлы дома, `reveal`, `doctor`, `base add`). Тема `odata1c_info("policy")` говорит то же.
- Пределы (SPEC §11.2 «Границы хука», CONTEXT.md «Хук»): хук — защита в глубину, не барьер. Правило 4 не видит косвенного вызова (`$o='odata1c'; & $o base set …`, `iex` над строкой из частей, `Start-Process`, `python -c "from odata1c.cli import main…"`), `cmd /c …` и других косвенных вызовов, кавычек, экранирования и раскрытия внутри слова `odata1c` (`od$()ata1c …`), а также glob с заранее созданными файлами; в позициях ключа, группы, подкоманды и класса раскрытие закрыто вопросом (разрешительный список символов), внутри слова `odata1c` — предел. Цена — лишний `ask` на безобидной команде с фразой `odata1c base set` или `odata1c policy open` в тексте (`echo`, `grep`, `git commit -m "… odata1c base set …"`), на `--label $'a'` в Bash, на `odata1c $cmd …`, на `--home=$HOME/h base set …`, на подписи с `(`, `{`, `@` или `%` (`shlex` кавычек не помнит) и на `;`, `&`, `|` или переводе строки внутри подписи (в кавычках, буквальном, `$'…\n…'`, ``"…`n…"``): хвост режется по ним до разбора кавычек и считается неразобранным — вопрос задаётся раньше, чем CLI откажет в многострочной подписи. Поведение `ask` в режимах `bypassPermissions` и `dontAsk` документацией Claude Code не описано; клиент без хуков диалога не покажет. Последняя линия — согласие владельца в отдельном сообщении по навыку и разрешения Claude Code на Bash; полноценная защита — аутентификация человека (M4). Согласие в сообщении подтверждением по CONTEXT.md не является — подтверждение здесь только диалог разрешения. `uvx` без закрепления ставит последнюю версию пакета, а плагин закрепляет версию демона: `base set` пишет только давно существующие поля, расхождение версий файл не портит; навык предпочитает `odata1c` с `PATH`.
- Синхронно меняются: SPEC §3.1, §3.5, §6.9, §11.2, §11.3, §11.4, §14 (строка 14.9), §16; `CONTEXT.md` (статьи «Конструктор политики», «Разрешения», «Навык», «Хук», новый термин «Снижение защиты»); ADR-0015 (поправка, `status: amended`); проект `docs/superpowers/specs/2026-10-01-base-set-design.md` (подраздел 3.6 «Поправки по итогам реализации»).
