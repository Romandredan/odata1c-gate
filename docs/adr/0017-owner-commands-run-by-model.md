# Команды владельца выполняет модель через CLI; снижение защиты проходит через подтверждение человека

ADR-0015 отдал правку политики конструктору `odata1c policy …` и закрепил, что команду набирает и запускает владелец в своём терминале, а модель лишь печатает её: содержимое полей 1С может подтолкнуть модель открыть поле, которое открывать не просили. Полей записи базы — уровня гейта, записи, подписи, роли, разрешений — это не касалось вовсе: команды для них не было, владелец правил `bases.yaml` руками, а файл закрыт от модели хуком (в нём пароль 1С). Владелец решил 2026-10-01 (проект `docs/superpowers/specs/2026-10-01-base-set-design.md`): он управляет базами шлюза в диалоге с моделью — «сделай `trade_dev` только для чтения с полным гейтом», — и модель делает это сама; в терминал он не ходит, файл с паролем модель по-прежнему не видит. Выбрано: появляется команда `odata1c base set` для полей записи базы и скалярных разрешений; модель выполняет её и команды конструктора политики сама по навыкам плагина; команда, которая **снижает защиту** (уровень гейта ниже `identifiers+names`, включение записи, роль `test`/`dev`, включение разрешения, любой лимит коммитов, возврат поля к умолчанию роли, любой ключ, которого хук не знает, `policy open` и `policy set … keep|scan`, равнозначный `open`), выполняется только после явного согласия владельца в отдельном сообщении, и хук плагина переводит её в диалог разрешения Claude Code — тот же человеческий барьер, что страхует `odata1c_commit`. Тула MCP для настроек и политики по-прежнему нет.

## Considered Options

- **Оставить терминал владельца** (ADR-0015 как есть, `base set` — тоже команда для терминала). Отвергнуто владельцем: цель — управлять шлюзом в диалоге, а не диктовать команды; модель и так видит всё, что печатает команда (реквизитов там нет).
- **Тул MCP с подтверждением по `_meta`**, как у `odata1c_commit`: работает в любом клиенте, не зависит от хука и от `PATH`. Отвергнуто: демону не нужен путь записи в собственную конфигурацию; конструктор политики остался бы отдельным механизмом с другим правилом, а решение ADR-0015 «тула MCP для политики нет» сохраняется — данные 1С не должны иметь прямой дороги к настройкам защиты через протокол модели.
- **Собственное интерактивное подтверждение команды** (вопрос в терминале при снижении защиты). Отвергнуто: у Bash модели нет терминала, `--yes` или `yes |` обходят вопрос одной строкой; человеческий барьер должен лежать вне канала, которым распоряжается модель.
- **Модель выполняет всё без разделения** на снижающие и повышающие команды, последняя линия — разрешения Claude Code на Bash. Отвергнуто: в автоматическом режиме Bash текст из данных 1С с инъекцией выключил бы гейт одной командой; разделение стоит одного лишнего диалога.
- **Правка файла баз через `ruamel.yaml`, как у конструктора политики.** Отвергнуто: новый ключ обратимый разбор дописал бы в конец записи, закомментированный образец с прежним значением остался бы выше и вводил бы в заблуждение, а заголовки «умолчание роли prod» после смены роли устаревали бы. Файл правится текстом по разметке разбора PyYAML (`yaml.compose` даёт номер строки каждого ключа), строки рисуют те же помощники, что у `base add`.
- **Узнавать снижающую команду регулярным выражением по всей строке** (первоначальный проект, §3.3). Отвергнуто при реализации: ключ `--home` перед `base`, кавычки, переносы строки и цепочки команд ломали образец в обе стороны — пропускали снижение и принимали за него безобидное. Правило 4 разбирает команду по токенам.

## Consequences

- `odata1c base set <база>` меняет `gate.mode`, `write`, `label`, `role`, `permissions.post_documents`, `permissions.mark_deletion`, `permissions.independent_register_delete`, `permissions.commit_limit`; значение `default` снимает явное поле. Строки не затронутых полей и комментарии владельца сохраняются байт в байт, образцы умолчаний остаются верными и после смены роли, запись атомарна. Явное значение пишется явно и при совпадении с умолчанием роли (как `base add --gate`); поле, запрошенное с теми же значением и источником, не переписывается, и комментарий владельца при нём остаётся на месте. Адрес, пользователь и пароль командой не меняются и не печатаются. Списки сущностей и полей и флаг `register_direct_write` — вне первой поставки.
- Правка файла (SPEC §3.1). Запись в нестандартной форме — поточная, с ключом слияния, с повторами ключей, с разделом `gate` или `permissions` в одну строку — не правится, как и любой файл с якорями или ссылками YAML (`&имя`, `*имя`): разметка разбора указывала бы на строки чужой записи, а правка записи-источника якоря молча меняла бы ссылающиеся. После разбора каждая активная строка сверяется со строками файла: расхождение (разделители строк Unicode `U+2028`, `U+2029`, `U+0085` в подписи сдвигают номера строк PyYAML относительно деления по `\n`) — отказ «разметка записи не совпала со строками файла». Исходный текст проверяется моделью настроек демона до правки (файл, который демон отверг бы, команда не правит; `password: keyring` при этом не разрешается, хранилище ОС не трогается), новый — до построения результата; после правки контрольное чтение сверяет каждое запрошенное поле с тем, что прочтёт демон (значение и источник), и при расхождении файл остаётся нетронутым. Пустой или отсутствующий раздел `bases` — нет баз (`base_unknown`), как у загрузчика. Окончания строк берутся по первой строке файла. `--role` не трогает активные строки, кроме стандартного хвоста `# по роли — true|false` у активной `write` (его пишет `base add`), и перерисовывает все образцы зависимых ключей и заголовки «умолчание роли …» — только для ролей `prod|test|dev` и уровней `off|identifiers|identifiers+names`, комментарии владельца других форм остаются как есть. Подпись пишется одной строкой (`width=inf`; касается и `base add`); подпись, уже занимающая несколько строк, команда не правит. Сбой `os.replace` (на Windows файл занят демоном) повторяется до десяти раз, затем временный файл удаляется и команда отказывает без следов. Тексты отказов не содержат значений из файла, цепочка исключений обрезана (`from None`): фрагмент файла с паролем не попадает в трассировку.
- CLI. `--label` — одна строка без управляющих символов (категории Unicode `Cc`, `Zl`, `Zp`), пробелы по краям обрезаются, пустая подпись отклоняется; значения `default`, `on`, `off` как подписи допустимы. `cmd_base_set` не читает `load_config`: пароль и хранилище ключей команде не нужны, отказы `config_invalid` и `base_unknown` даёт сама правка. Все парсеры CLI — `allow_abbrev=False`: сокращения ключей (`--gat`, `--w`) не принимаются ни одной командой, иначе хук не узнал бы ключ. Вывод всех команд CLI в канале — UTF-8, включая справку и отказы `argparse` (потоки переводятся до разбора аргументов с сохранением режима ошибок; его читает модель через Bash, а на Windows поток в канале кодировался бы кодовой страницей); команды `mcp` это не касается — канал JSON-RPC лаунчера идёт через двоичный дескриптор SDK, её сообщения в stderr теперь тоже UTF-8. Строка «задано явно, роль не влияет: …» печатается, только когда роль действительно изменилась; колонки таблицы выровнены по ширине данных; строки идут в порядке полей записи (`label`, `role`, `write`, `gate.mode`, `permissions.*`).
- Хук `PreToolUse` получает правило 4 (SPEC §11.2). Команда разбирается по токенам: для каждого слова `odata1c` или `odata1c.exe` в любой форме запуска (`uvx --from odata1c-gate odata1c`, `uv run odata1c`, путь к исполняемому файлу, `python -m odata1c`) пропускаются ключи с дефисом и их значения, `--home` в любой позиции, до `base set`, `policy open` или `policy set`; переносы `\` и `` ` `` с переводом строки склеиваются до разбора; хвост ограничен разделителем цепочки (`&&`, `||`, `;`, `|` не после `>`, одиночный `&` вне перенаправления, перевод строки). Снижают защиту: `--gate` кроме `identifiers+names`, `--write on`, `--role test|dev`, включение `--post-documents`, `--mark-deletion`, `--register-delete`, любой `--commit-limit`, любой `default` и любой неизвестный хуку ключ (`-h` и `--help` нейтральны); неразобранный хвост — незакрытая кавычка, `` `" `` и `\"` в PowerShell, `$'…'` в Bash — тоже снижение. Хук не знает текущих значений и роли, поэтому `--gate identifiers`, `default` и лимит считает снижением. `policy open` и `policy set … keep|scan` (класс ищется среди позиционных токенов без учёта регистра) → `ask` «открывает поле модели»; `custom:<имя>`, закрывающие классы, `hide`, `show`, `check` проходят молча. Несколько команд в одной строке дают один `ask` с объединённой причиной; имена баз и ключи попадают в причину — это значения из события, не из файла. `deny` правила 3 (`reveal`, файлы дома) старше.
- Навыки: новый `odata1c-base`; `odata1c-policy` разрешает модели запускать `hide` (с `--yes`: у Bash модели нет терминала, вопрос о дочерних сущностях переезжает в сообщение модели) и `set`, `open` и `set … keep|scan` — после согласия и с диалогом; `odata1c-setup` отсылает к `odata1c-base`; `odata1c` снимает запрет «не выполнять `odata1c policy …`». `base add` (пароль), `reveal` и `doctor` остаются за человеком. Тема `odata1c_info("policy")` говорит то же.
- Пределы (SPEC §11.2 «Границы хука», CONTEXT.md «Хук»): хук — защита в глубину, не барьер. Правило 4 не видит косвенного вызова (`$o='odata1c'; & $o base set …`, `iex` над строкой из частей, `Start-Process`, `python -c "from odata1c.cli import main…"`) и кавычек внутри самого слова `odata1c` — слово ищется буквально. Цена правила — лишний `ask` на безобидной команде с фразой `odata1c base set` или `odata1c policy open` в тексте (`echo`, `grep`, `git commit -m "… odata1c base set …"`), на `--label $'a'` в Bash и на базе с именем `keep` или `scan`. Поведение `ask` в режимах `bypassPermissions` и `dontAsk` документацией Claude Code не описано; клиент без хуков диалога не покажет. Последняя линия — согласие владельца в отдельном сообщении по навыку и разрешения Claude Code на Bash; полноценная защита — аутентификация человека (M4). Согласие в сообщении подтверждением по CONTEXT.md не является — подтверждение здесь только диалог разрешения. `uvx` без закрепления ставит последнюю версию пакета, а плагин закрепляет версию демона: `base set` пишет только давно существующие поля, расхождение версий файл не портит; навык предпочитает `odata1c` с `PATH`.
- Синхронно меняются: SPEC §3.1, §3.5, §6.9, §11.2, §11.3, §14 (строка 14.9), §16; `CONTEXT.md` (статьи «Конструктор политики», «Разрешения», «Навык», «Хук», новый термин «Снижение защиты»); ADR-0015 (поправка, `status: amended`); проект `docs/superpowers/specs/2026-10-01-base-set-design.md` (подраздел 3.6 «Поправки по итогам реализации»).
