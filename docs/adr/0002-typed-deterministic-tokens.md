# Реквизиты заменяются детерминированными типизированными токенами, а не маскируются

Модель должна уметь сверять реквизиты между объектами и ссылаться на уже виденные значения в фильтрах и записях, не видя их. Маска `***` это ломает, частичная маска (`7707******`) не даёт ни равенства, ни обратимости. Выбран токен `[[type:tail]]` = HMAC(секрет, тип + нормализованное значение): равенство сохраняется, обратная подмена возможна только внутри гейта, а токен нельзя спутать с настоящим значением.

## Considered Options

- **Format-preserving алиасы** (правдоподобный чужой ИНН с верной контрольной суммой; прежний вариант дизайна). Отвергнуты: алиас может совпасть с реальной организацией, требует морфологии и подстрочного поиска для строк, а главное — добавляет в путь записи риск тихой правки не того объекта при ошибке обратного отображения. Для одних только реквизитов (сравнение по равенству) эти издержки не окупаются.
- **Необратимая маска.** Нет пути записи по виденному значению и нет сверки; отвергнута.
- **Случайные сессионные токены с TTL** (как в LLM-gateway). Один и тот же ИНН в разных беседах получал бы разные токены; отчёты и файлы, написанные моделью, теряли бы связь с данными. Отвергнуты в пользу детерминизма.

## Consequences

- Секрет HMAC — единственная невосстановимая часть системы: при его потере словарь пересобирается, но старые чаты ссылаются на другие токены. Резервная копия — по явной команде.
- Токены не format-preserving, поэтому реальные значения при записи приходят либо из словаря (подмена), либо из промпта пользователя (проверка контрольной суммы). Модель никогда не «генерирует» реквизит.
- Частичные и выдуманные токены — ошибка, а не пропуск: гейт лучше откажет, чем угадает.
