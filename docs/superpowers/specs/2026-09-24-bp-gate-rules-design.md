# Гейт для БП: каталог правил сущностей и новые правила — проект

Дата: 2026-09-24. Ветка `worktree-bp-gate`. Основание — разведка `docs/probes/BP-recon.md` и
решения владельца в сессии 2026-09-24.

## 1. Цель и критерий готовности

Гейт должен закрывать на Бухгалтерии предприятия (БП КОРП 3.0) то же, что закрывает на УТ:
реквизиты, ФИО и адреса физлиц — без открытых полей, найденных разведкой, и без новых ложных
срабатываний. Правила, которые касаются одной сущности или одного необычного имени поля,
хранятся в едином формате, который пополняется файлом на конфигурацию, а не правкой кода.

Готово, когда:

1. повторный прогон `tools/probes/bp_recon.py` на дампах БП и УТ не показывает полей из разделов
   1 и 3 отчёта разведки без класса, а сверка «было → стало» по обоим дампам не содержит
   изменений, кроме перечисленных в этом проекте;
2. сторож справочников людей (Ruling 36) проходит на обоих дампах;
3. все тесты проходят, `ruff check` и `ruff format --check` чисты;
4. живая приёмка чтения на `bp_test` во временном доме подтверждает закрытие на данных (шаг 2
   этапа, отдельный отчёт).

## 2. Решения владельца (2026-09-24)

- Регистрационные номера страхователя в фондах закрываются **новым классом наравне с ОГРН**.
- **Ложные срабатывания убрать.**
- Номер документа физлица закрывается **узким правилом на сущность**, а не общим `^номер$`
  (инвариант 6). Такие правила — в **едином формате с расчётом на пополнение**: с ростом числа
  конфигураций их станет больше.
- Каталог правил **сопоставляется по наличию сущности в индексе**, без привязки к полю `config`
  базы; для доработанных конфигураций — **слой владельца** в домашнем каталоге в том же формате.
- СНИЛС с неверной контрольной суммой — не утечка: такое значение — мусор. Правило по имени
  `СтраховойНомерПФР` добавляется ради единообразия (поле закрыто целиком одним токеном).

## 3. Каталог правил сущностей

### 3.1 Слои

| Слой | Где | Что | Кто пишет |
|---|---|---|---|
| каталог поставки | `src/odata1c/templates/gate/*.yaml` | правила типовых библиотек и конфигураций | разработчик, выпуском |
| каталог владельца | `~/.claude/odata1c/gate/*.yaml` | правила доработок, общие для всех баз доработанной конфигурации | владелец, руками по шаблону |
| политика базы | `bases/<база>/policy.yaml` | исключения одной базы | владелец, `odata1c policy …` |

Каталог — вход классификатора полей по имени (`field_rules.classify_field`), то есть авторазметки.
Каталог владельца главнее каталога поставки на совпадающем ключе. Политика базы главнее
авторазметки, как и прежде (ADR-0015): правило каталога попадает в `policy.auto.yaml`, и
`policy.yaml` → `fields` его перекрывает.

Каталог не привязан к конфигурации: правило действует на любой базе, в индексе которой есть его
сущность. Имена сущностей типовых библиотек (БСП, БЗК, БЭД) одинаковы во всех конфигурациях, где
библиотека встроена: `InformationRegister_ДокументыФизическихЛиц` есть и в УТ, и в БП. Файлы
разложены по происхождению сущностей ради сопровождения, на сопоставление раскладка не влияет.

### 3.2 Формат файла

```yaml
version: 1
about: Библиотека зарплаты и кадров — кадровые и зарплатные сущности   # для человека

people:                 # справочники людей: Description и поля ФИО — person (SPEC §6.5, слой 1),
  - Catalog_ФизическиеЛица          # адрес — адрес физлица (SPEC §6.9)
orgs:                   # справочники организаций: Description и наименования — org
  - Catalog_Организации
addr_mask_for:          # сущности не-справочники, чьи адреса принадлежат физлицам (SPEC §6.9)
  - Document_СведенияДляОплатыОтпускаСФР
fields:                 # класс поля одной сущности
  InformationRegister_ДокументыФизическихЛиц.Номер: doc
names:                  # класс поля с таким именем в любой сущности
  СерияПаспорта: doc
  ТипЗаявкиКабинетСотрудника: scan
```

Значение в `fields` и `names` — класс из `CLASSES` (кроме `keep`) или `scan`. `scan` означает «по
имени не классифицировать»: поле остаётся без класса, и реквизиты в нём ищут детекторы, как в
любом тексте. Это способ снять ложное срабатывание общего правила. `keep` каталогу не доступен:
открыть поле целиком, без поиска реквизитов, вправе только владелец в `policy.yaml`.

Все разделы необязательны. Ключи `fields` — `Сущность.Поле`, ключи `names` — имя поля; регистр
букв в `names` не важен.

### 3.3 Порядок классификации

`classify_field(entity, field, edm_type, *, names_for=None, rules=None)`:

1. нестроковый тип, служебное поле (`Ref_Key`, `Code`, `Number`, `DataVersion`, `…_Type`),
   счёт плана счетов — без класса (как прежде, инвариант 6);
2. `fields` каталога по `entity.field`; для регистров — и по сущности-регистру, если `entity` —
   его набор записей или виртуальная таблица (`<регистр>_…`);
3. `names` каталога по имени поля;
4. правила реквизитов по имени (`ПРАВИЛА_РЕКВИЗИТОВ`);
5. слой 1: `Description` и поля ФИО у справочника из `names_for` (по умолчанию `people ∪ orgs`
   каталога); класс `person`, если справочник в `people`, иначе `org`;
6. слой 2: ФИО и названия в чужой сущности (`_имя_в_чужой_сущности`).

Шаги 2–3 возвращают `None` для `scan`. Наследование в шаге 2 ограничено регистрами
(`InformationRegister`, `AccumulationRegister`, `AccountingRegister`, `CalculationRegister`): у
справочника и документа дочерние сущности — табличные части с другим составом полей.

### 3.4 Кто читает каталог

- `rules.load_rules(home)` — каталог поставки и каталог владельца, собранные в один `RuleCatalog`.
  Каталог поставки читается один раз на процесс; каталог владельца — по времени изменения файлов
  (как `bases.yaml` и `policy.yaml`).
- Реиндекс (`generate_policy`, `classifier_for`) получает собранный каталог: `auto` и
  `defaults.addr.mask_for = people ∪ addr_mask_for` строятся по нему.
- Действующая политика базы (`Policy`) несёт каталог (`policy.rules`); запасные пути
  классификации маскировщика и обратной подмены (`_базовый_класс_поля_политики`,
  `Unmasker._класс_поля`) передают его в `classify_field`. Так реиндекс, маскировка и отбор видят
  одни и те же правила.
- `classify_field` без `rules` пользуется каталогом поставки — для тестов и вызовов без дома.
- Константы `СУЩНОСТИ_ФИЗЛИЦ` и `DEFAULT_NAMES_FOR` остаются как производные каталога поставки
  (обратная совместимость импорта).

### 3.5 Ошибки

Файл каталога владельца, который не разбирается или не проходит проверку (неизвестный раздел,
класс вне списка, `keep`, ключ `fields` без точки), даёт `PolicyError` с путём файла и строкой, без
значений: как негодный `policy.yaml`, он закрывает тулы базы `policy_invalid`, пока владелец не
починит. Два файла одного слоя с разными значениями одного ключа — та же ошибка («правило задано
дважды»). Каталог поставки проверяется тестами; его ошибка — дефект выпуска.

## 4. Новый класс `sfr` — регистрационный номер страхователя

- Имя — `sfr`: с 2023 года ПФР и ФСС объединены в Социальный фонд (СФР), номер страхователя
  в СФР и прежние номера ПФР и ФСС — один вид реквизита.
- Правило по имени поля: `рег(истрационный)?номер(пфр|фсс|сфр)|номерстрахователя`. Сверено по
  обоим дампам: `РегистрационныйНомерПФР/ФСС/СФР`, `РегНомер…`, `ИПРегистрационныйНомер…`,
  `ПрежнийСтраховательРегистрационныйНомерПФР`, `ИнаяОрганизацияРегистрационныйНомерСФР`,
  `РегистрационныйНомерПФРвКорректируемыйПериод`, `ОператорРегНомерПФР`,
  `РегномерСФРГоловнойОрганизации`, `НомерСтрахователяФСС`,
  `ДоверительФЛ_РегистрационныйНомерФСС`. `ИнаяОрганизацияРегистрационныйНомер` (без названия
  фонда, документы СФР) — правило каталога `names`.
- Не закрываются: `КодПодчиненностиФСС`, `ДополнительныйКодФСС` — код отделения фонда, а не
  номер страхователя; `РегистрационныйНомер` без фонда — это номер ГТД, справки ЕГАИС,
  регистрации иностранной организации и прочее.
- Нормализация — только цифры (`ТОЛЬКО_ЦИФРЫ`): номер ПФР пишут `999-999-999999`, номер ФСС и
  СФР — десять цифр подряд. Минимальная длина поиска в тексте — 10 цифр.
- Детектора по виду значения нет: контрольной суммы у номера нет, а десять цифр подряд
  неотличимы от ИНН и прочих чисел (инвариант 6). В свободном тексте номер закрывает страж — по
  словарю, когда значение уже пришло полем.

## 5. Правила по имени поля (код)

Каждое правило сверено по полным дампам УТ и БП; перечень затронутых имён — в `build/names.txt`
прогона `bp_recon.py`.

| Правило | Было | Стало | Что добавляется |
|---|---|---|---|
| `snils` | `снилс` | + `страховойномер(пфр\|сфр)` | `СтраховойНомерПФР`, `…СФР`, `…ПФРВСвидетельстве` |
| `acc` | `лицевойсчет` | + `номерлицевогосчета` | `НомерЛицевогоСчета`; `ТипЛицевогоСчета`, `РазделЛицевогоСчета` не задеты |
| `email` | `^email`, `^email$`… | + `email`, `емейл` в любом месте | `АдресEmail`, `РабочийEmail`, `МенеджерEmail`, `ЕмейлКлиента`, `см_EmailTo`… |
| `sfr` | — | раздел 4 | раздел 4 |
| `addr` | `^адрес`, … | + `месторожд` | место рождения (см. ниже) |
| слой 2, `person` | `фио`, `сотрудник`… | + `фамили`, `отчеств`, `имя$` и `имялатиниц` кроме служебных (`файлимя`, `полноеимя`, `табличнаячастьимя`); `сотрудник` только как всё поле (`сотрудник(и\|строкой)?$`, `сотрудниковстрокой`) | ФИО составными именами — 47 имён; снимает 12 ложных срабатываний `…Сотрудника`, `…Сотрудников` |
| слой 2, `org` | `наименованиеорганизации`… | + `наиморг` | `ДоверительЮЛ_НаимОрг` и сокращения форматов ФНС |

**Адреса физлиц по имени поля.** В документах БП адреса проживания и регистрации работника лежат
в полях документа, а не в справочнике людей: `Document_СведенияДляОплатыОтпускаСФР.АдресПроживания…`,
`…АдресРегистрацииПоМестуЖительства` и подобные. Класс `addr` у них есть, но адрес вне
`mask_for` открыт. Правило адресов (`Policy.addr_masked`, SPEC §6.9) дополняется пунктом
«адрес физлица по имени поля — закрыт всегда», рядом с адресом движения товара (Ruling 34, п. 3):
`адрес(регистрации|проживания|фактическогопроживания|местажительства|местапребывания|попрописке|зарубежом)`
кроме `адресрегистрацииустройства`, и `месторожд` — место рождения. Поле места рождения получает
класс `addr` по имени (правило адреса дополняется `месторожд`): это текст о физлице, который,
как адрес, не должен искаться в чужом тексте; класс `person` для него отвергнут — ФИО ищутся по
всему свободному тексту, и «г. Москва» начал бы заменяться в адресах организаций. Было:
`МестоРожденияПредставление` — `person` по подстроке «представление».

**Ложные срабатывания `addr`.** Сетевые адреса (`АдресПриложения`, `АдресСервиса`, `АдресСервера`,
`АдресСайта`, `АдресРесурса…`, `АдресАвторизации` и подобные) получают класс `addr`, но вне
`mask_for` открыты и данных не портят. Раздел `names` каталога переводит их в `scan`, чтобы
авторазметка не называла их адресами; перечень — по дампам.

## 6. Первое наполнение каталога поставки

- `common.yaml` — перенос из кода: исключения слоя 2 (`ЮрФизЛицо`, `ГрафикРаботыСотрудников`,
  `ДоговорЗаймаСотруднику`, `ДолжностьРуководителя`, `РешениеРуководителя` → `scan`);
  справочники организаций `Catalog_Контрагенты`, `Catalog_Организации`, `Catalog_Партнеры`;
  справочники людей платформы и БСП (`Пользователи`, `КонтактныеЛица`, подписанты, сертификаты).
- `bzk.yaml` (зарплата и кадры, есть в БП, ЗУП, частично в УТ): `people` — `ФизическиеЛица`,
  `Сотрудники`, `РодственникиФизическихЛиц`; `fields` — `ДокументыФизическихЛиц.Номер`,
  `.Представление` → `doc`, `.ИмяЛатиницей` → `person`, серия и номер справки об инвалидности,
  удостоверения об отсрочке → `doc`, `ЭмбоссированныйТекст1–3` → `person`; `names` — документы о
  рождении, удостоверения личности, миграционные карты, `СерияПаспорта`, `СотрудникПаспорт` →
  `doc`; `addr_mask_for` — документы и заявления о работниках, чьи адреса — адреса физлиц.
- `ut.yaml` — справочники людей УТ (`КонтактныеЛицаПартнеров`, `ОтветственныеЛицаОрганизаций`,
  `ПользователиВЕТИС`) и ложные срабатывания, найденные только на УТ.
- `bp.yaml` — сетевые адреса и прочее, найденное только на БП.

Раскладка по файлам вторична; тест проверяет, что каждое имя сущности каталога есть хотя бы в
одном дампе или стоит в явном перечне «из конфигураций без дампа» (ЗУП).

## 7. Проверки

- Юнит: разбор каталога (разделы, классы, `keep` запрещён, дубли, ошибки с путём без значений);
  порядок классификации (§3.3), наследование `fields` регистров, `scan`, слой владельца поверх
  поставки; класс `sfr` (нормализация, токен, длина поиска); правила по имени из раздела 5;
  адрес физлица по имени поля закрыт вне `mask_for`.
- На дампах (пропуск без дампа, как у Ruling 36): сторож справочников людей параметризован по
  УТ и БП; сверка «было → стало» классов всех строковых полей обоих дампов против эталона
  изменений этого проекта; каждое имя каталога есть в дампе или в перечне «без дампа».
- Действующее поведение: политика с каталогом владельца; негодный файл каталога → `config_invalid`.
- Живая приёмка — отдельным шагом после слияния правок гейта.
