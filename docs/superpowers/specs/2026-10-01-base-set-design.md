# Команда `odata1c base set` и запуск команд владельца моделью: проект

Дата: 2026-10-01. Ветка `worktree-cli-base-set`. Решения владельца 2026-10-01 в диалоге
проектирования: цикл `0.3.1` открывает команда `base set`; команды владельца выполняет сама модель
через CLI, а не владелец в терминале; команды, снижающие защиту, проходят через подтверждение
человека; объём — поля базы и скалярные разрешения; файл правится текстом по разметке разбора.

## 1. Задача

Владелец управляет базами шлюза в диалоге с моделью. Сегодня у него две точки управления
(ADR-0015): `bases.yaml` на машину — «кто база и как с ней работать» — и `policy.yaml` на базу —
«что скрывать». Политику собирает конструктор `odata1c policy …`, но его команды, по правилу навыка
`odata1c-policy` и ADR-0015, печатает модель, а набирает и запускает владелец в своём терминале.
Поля же записи базы — уровень гейта, разрешение записи, подпись, роль, разрешения — меняются только
правкой `bases.yaml` руками: команды для них нет вовсе, а файл закрыт от модели хуком (в нём пароль
1С).

Владелец хочет иного: «сделай `trade_dev` только для чтения с полным гейтом» — и модель делает это
сама, показывает, что изменилось, и подтверждает результат; файл с паролем модель по-прежнему не
видит, в терминал владелец не ходит. То же — для конструктора политики: «скрой справочник
пользователей» выполняется моделью, а не диктуется ей в терминал.

Прямое противоречие с ADR-0015: там правка политики моделью отвергнута из-за опасности подсказки из
данных 1С («данные 1С могут подтолкнуть модель открыть поле; политику меняет только команда CLI в
терминале владельца, как `reveal`»). Для `base set` риск той же природы и крупнее: одна команда
`--gate off` снимает защиту со всей базы. Решение владельца 2026-10-01 переносит границу: модель
выполняет любые команды владельца, но та из них, что **снижает защиту**, проходит через
подтверждение человека — диалог разрешения Claude Code по решению `ask` хука, тот же механизм, что
страхует `odata1c_commit`, — после явного согласия владельца в отдельном сообщении. Тул MCP для
настроек по-прежнему не вводится.

## 2. Критерий готовности

1. `odata1c base set <база>` меняет уровень гейта, разрешение записи, подпись, роль и скалярные
   разрешения (`post_documents`, `mark_deletion`, `independent_register_delete`, `commit_limit`)
   записи базы; значение `default` возвращает поле к умолчанию роли. Комментарии файла и строки,
   не затронутые правкой, сохраняются байт в байт; файл после команды выглядит так, как будто его
   написал `base add`. Адрес, пользователь и пароль в выводе не появляются.
2. Демон подхватывает изменение без перезапуска (перечитывание `bases.yaml` по изменению файла уже
   есть, SPEC §3.1); `odata1c_bases` в следующем вызове показывает новые уровень и запись.
3. Хук переводит в `ask` команду `base set`, снижающую защиту, и `policy open`; повышающие и
   нейтральные команды проходят без диалога. Причина в диалоге называет снижающие ключи.
4. Навык `odata1c-base` ведёт модель от просьбы владельца до проверенного результата; навык
   `odata1c-policy` разрешает модели запускать `hide` и `set` самой; ADR-0017 закрепляет принцип,
   ADR-0015 помечен поправленным; SPEC, CONTEXT.md, AGENTS.md, README, `docs/install.md` согласованы.
5. Все тесты и `ruff`; `claude plugin validate plugin/`; живая проверка владельцем в Claude Code:
   понижение защиты даёт диалог, повышение — нет, результат виден в `odata1c_bases`.

## 3. Решение

### 3.1 Команда

```text
odata1c base set <база> [--gate off|identifiers|identifiers+names|default]
                        [--write on|off|default]
                        [--label <текст>]
                        [--role prod|test|dev]
                        [--post-documents on|off|default]
                        [--mark-deletion on|off|default]
                        [--register-delete on|off|default]
                        [--commit-limit <N>|default]
```

- Без единого ключа — отказ с подсказкой, какие ключи есть. Неизвестная база — отказ с перечнем
  имён описанных баз (только имена). Неверное значение — отказ `argparse` до чтения файла.
- `--register-delete` пишет поле `permissions.independent_register_delete`; имя ключа короче имени
  поля ради строки команды, вывод называет поле полностью. `--commit-limit` принимает целое ≥ 0;
  `0` — без лимита, как в файле.
- Флаг `permissions.register_direct_write` командой не выставляется: запись регистров, подчинённых
  регистратору, закрыта при любом его значении (Ruling 57, `write/permissions.py`), флаг для модели
  мёртв. Списки `allow_entities`, `deny_entities`, `deny_fields` — вне проекта (§7).
- Явное значение пишется явно, даже если совпадает с умолчанием роли: так же поступает
  `base add --gate` («задан для этой базы явно — не зависит от последующей смены роли»). Поэтому
  «изменений нет» команда говорит только тогда, когда у каждого запрошенного поля совпали и
  значение, и источник (явно / по роли); иначе файл меняется и это отражено в выводе.
- `default` снимает явное поле: строка возвращается в закомментированный образец с умолчанием
  роли. Поле, которое и так по роли, от `default` не меняется.
- `--role` меняет роль и перерисовывает закомментированные образцы умолчаний под новую роль.
  Явно заданные поля остаются явными, и вывод говорит об этом («задано явно, роль не влияет»).
  Смена роли меняет действующие значения всех полей «по роли» сразу — поэтому команда всегда
  печатает полное действующее состояние (ниже), а хук считает `--role test|dev` снижением защиты.
- Вывод — в стиле `base list`: строка «база <имя> (<подпись>)», таблица изменённых полей с
  колонками `поле`, `было`, `стало`, где у значения в скобках источник (`по роли <роль>` или
  `явно`), затем строка «действует:» с ролью, уровнем гейта, записью, тремя разрешениями и лимитом,
  и строка о том, что демон перечитает файл перед следующим вызовом тула, а смена уровня гейта
  придёт модели строкой `warnings`. `url`, `user`, `password` не печатаются ни в одной ветке,
  включая ошибки.
- Коды возврата как у остальных команд `base`: `0` — выполнено или изменений нет, `1` — отказ с
  сообщением (`ConfigError`).
- **Вывод в канале — UTF-8.** Теперь команды CLI читает не только человек в консоли, но и модель
  через канал инструмента Bash. На Windows поток Python в канале кодируется кодовой страницей
  (`cp1251`), и кириллица вывода дошла бы до модели искажённой. `cli.main` переводит `stdout` и
  `stderr` в UTF-8 тем же приёмом, что хук (`reconfigure`, в `contextlib.suppress`): в настоящей
  консоли Windows поток и так UTF-8, в канале — становится им. Касается всех команд, не только
  `base set`: `policy hide`/`set`/`show` модель теперь тоже запускает сама.

### 3.2 Правка файла

Новая функция рядом с `append_base` в `config/writer.py` (имя публичного API по образцу соседей —
`set_base_fields(path, name, changes)`); CLI вызывает её и печатает результат. Алгоритм:

1. Файл читается текстом; окончание строк (`\n` или `\r\n`) определяется по первой строке и
   сохраняется при записи.
2. Текст разбирается `yaml.compose` — узлы PyYAML несут номера строк и колонок (`start_mark`).
   По узлам находятся раздел `bases`, запись базы и её диапазон строк: от строки ключа базы до
   строки следующего ключа того же уровня (или следующего ключа верхнего уровня, или конца файла).
   Из узлов же берутся отступ ключей записи и строки активных ключей, в том числе вложенных
   (`gate`, `permissions`).
3. Запись в поточной форме (`{…}`), значение `gate`/`permissions` в одну строку, ключ слияния `<<`
   или повторный ключ — отказ «запись базы в нестандартной форме, поправьте вручную». Комментарии
   между записями относятся к предыдущей записи; это безвредно: внутри диапазона правятся только
   строки, совпавшие с ключом по регулярному выражению и отступу.
4. Для каждого поля одно правило. Есть активная строка — переписывается на месте: значение
   меняется, отступ и строчный комментарий сохраняются дословно (комментарий владельца — его).
   Активной нет, но в диапазоне есть закомментированная строка того же ключа с тем же отступом
   (`# write: false`, `#   mode: …`) — она раскомментируется и переписывается так же. Нет ни той ни
   другой — новая активная строка вставляется после строки `role`, а если её нет — после последней
   из строк `label`, `url`, `user`, `password`. Строки рисуются теми же помощниками, что у
   `base add`: `render_base` разбирается на построчные функции (строка поля с комментарием в
   колонке `КОЛОНКА_КОММЕНТАРИЯ`), и обе команды пользуются ими.
5. Вложенные поля сначала активируют родителя: `# gate:` → `gate:`, `# permissions:` →
   `permissions:`; затем правится дочерняя строка (`#   mode:` → `mode:` с отступом на два пробела глубже
   родителя). Прочие дети родителя
   остаются комментариями — это допустимо в YAML и сохраняет самодокументированность. Родитель
   активен, а дочерней строки нет ни в каком виде — дочерняя вставляется сразу под родителем.
6. `default` делает обратное: активная строка становится закомментированным образцом с умолчанием
   роли и стандартным комментарием шаблона; родитель без единого активного ребёнка тоже
   комментируется, иначе он остался бы пустым ключом (`gate:` без значения — `null`, отказ
   загрузки).
7. `--role` переписывает значение строки `role`, затем перерисовывает закомментированные образцы
   зависящих от роли ключей (`write`, `independent_register_delete`, `commit_limit`, `gate.mode`)
   значениями новой роли и обновляет заголовки-комментарии вида «умолчание роли prod» и
   «умолчание роли prod: identifiers+names», если они есть в записи. Активные строки не трогаются.
8. Новый текст записывается во временный файл рядом (`<путь>.yaml.new`), перечитывается
   `yaml.safe_load` и проверяется той же моделью настроек, которой пользуется демон (`AppConfig`
   через загрузчик). Неудача проверки — временный файл удаляется, исходный не тронут, поднимается
   `ConfigError` (`config_invalid`) с путём и строкой, без значений из файла — тем же форматом,
   что у загрузчика. Успех — `os.replace` поверх исходного и `закрыть_права_файла`, как у
   `append_base` и конструктора политики.
9. Результат функции — для каждого поля «было» и «стало» с источником, плюс действующее состояние
   записи после правки, вычисленное наложением умолчаний роли (`УМОЛЧАНИЯ_РОЛЕЙ` загрузчика).
   Строки, не затронутые правкой, в новом тексте совпадают с исходными байт в байт — это свойство
   проверяется тестом.

### 3.3 Хук

Правило 4 в `plugin/hooks/pretooluse.py` для `Bash` и `PowerShell`, после правила 3 (его `deny`
старше):

- Команда ищется в тексте в любой форме запуска по образцу правила `reveal`:
  `\bodata1c(\.exe)?\b[\s'"]*base[\s'"]+set\b` и `\bodata1c(\.exe)?\b[\s'"]*policy[\s'"]+open\b`;
  `uvx --from odata1c-gate odata1c base set …` и `uv run odata1c base set …` совпадают, потому что
  слово `odata1c` стоит перед `base set`.
- Хвост команды после `set` до разделителя (`&&`, `||`, `;`, `|`, перевод строки) разбирается на
  ключи в обеих формах (`--gate off` и `--gate=off`). Снижают защиту: `--gate` с любым значением,
  кроме `identifiers+names`; `--write on`; `--role test|dev`; `--post-documents on`,
  `--mark-deletion on`, `--register-delete on`; `--commit-limit` с любым значением; `default` у
  любого ключа. Хук не знает ни текущих значений, ни роли базы, поэтому `identifiers`, `default` и
  любой лимит трактуются как снижение — цена одного лишнего диалога. Не удалось разобрать хвост —
  тоже снижение.
- Снижающая команда получает `ask` с причиной: «`odata1c base set` снижает защиту базы `<имя>`:
  `<ключи>` — подтвердите, что это просьба владельца». Несколько `base set` в одной команде —
  один `ask` с объединённой причиной. Остальные формы `base set` проходят без решения.
- `policy open` получает `ask` всегда: «открывает поле модели». `policy hide`, `policy set`,
  `policy show`, `policy check`, `base list`, `base test` проходят без решения.
- По документации Claude Code хук `PreToolUse` срабатывает до проверки разрешений в любом режиме,
  решение `ask` показывает диалог и в автоматическом режиме, причина (`permissionDecisionReason`)
  видна пользователю в диалоге. Поведение `ask` в режимах `bypassPermissions` и `dontAsk` в
  документации не описано — проверяется живой приёмкой (§5) и записано в пределы (§4).

### 3.4 Навыки и плагин

- **Новый навык `plugin/skills/odata1c-base/SKILL.md`** — «настройки базы: уровень гейта, запись,
  подпись, роль, разрешения, лимит». Срабатывает на просьбы вида «сделай базу только для чтения»,
  «выключи / включи гейт», «переименуй подпись», «запрети проведение», «сколько коммитов». Шаги:
  текущее состояние через `odata1c_bases` (уровень, запись, роль, подпись); перевод просьбы в
  ключи команды, одна команда на базу; если хоть один ключ снижает защиту — одним сообщением
  назвать, что именно ослабнет (например, «гейт `trade_dev` будет выключен: названия, ИНН и
  телефоны пойдут открытыми»), и ждать явного согласия владельца в его следующем сообщении, затем
  запуск; диалог разрешения от хука — ожидаемое подтверждение, отказ в нём — остановиться и
  сообщить. Команда запускается через Bash: `odata1c base set …`, а если `odata1c` не найдена —
  `uvx --from odata1c-gate odata1c base set …`. Вывод команды показывается владельцу как есть
  (реквизитов в нём нет), результат проверяется повторным `odata1c_bases`. Запрещено по-прежнему:
  читать и править файлы домашнего каталога, передавать команде адрес, учётку или пароль (их у
  команды и нет), придумывать значения за владельца. Что команда не умеет — адрес, пользователь,
  пароль, списки сущностей и полей, новая база — отдаётся человеку: `odata1c base add` в его
  терминале или ручная правка файла по закомментированным строкам шаблона.
- **`odata1c-policy`**: раздел «Правило» переписывается. Модель сама запускает `policy hide` и
  `policy set` после того, как согласовала с владельцем, что изменится; `hide` — с ключом `--yes`,
  потому что у Bash модели нет терминала и вопрос команды некому прочитать (подтверждение числа
  дочерних сущностей переезжает в сообщение модели владельцу до запуска). `policy open` — только
  после явного согласия владельца в отдельном сообщении, с ожидаемым диалогом разрешения от хука.
  `show` и `check` — свободно. В файлы политики модель не пишет, `reveal` не запускает. Строки 9,
  18, 47, 59 и 75 текущего навыка, говорящие «одна команда для терминала владельца», меняются
  соответственно.
- **`odata1c-setup`**: без изменений по сути — `base add` остаётся у человека из-за пароля; в
  конце добавляется отсылка: дальнейшие изменения настроек базы делает навык `odata1c-base`.
- **`odata1c`** (основной): строка 118 («навык `odata1c-policy` даёт ему ровно одну строку для
  терминала») переписывается; добавляется указатель на `odata1c-base`.
- **Тема `odata1c_info("policy")`** (`tools/info.py`, абзац «Тула MCP, который правит политику,
  нет…»): тул по-прежнему не вводится, но команды выполняет модель по навыку; `open` — после
  согласия и с подтверждением.
- Манифест плагина и агент `odata1c-investigator` не меняются (агент — только чтение).
  `claude plugin validate plugin/` зелёный.

### 3.5 ADR и документы

- **ADR-0017 «Команды владельца выполняет модель через CLI; снижение защиты — через подтверждение
  человека»** (`accepted`, поправляет ADR-0015). Рассмотрено: оставить терминал владельца
  (отвергнуто владельцем — неудобно, цель диалога не достигается); тул MCP с подтверждением по
  `_meta`, как у `commit` (отвергнуто: демону не нужен путь записи в собственную конфигурацию,
  конструктор политики остался бы отдельным механизмом, решение ADR-0015 «тула MCP нет» остаётся
  в силе); собственное интерактивное подтверждение команды в терминале (отвергнуто: у Bash модели
  нет терминала, а `--yes` или `yes |` обходят его одной строкой — человеческий барьер должен лежать
  вне канала модели). Выбрано: CLI запускает модель, человеческий барьер — диалог разрешения
  клиента по `ask` хука на снижающих командах, согласие владельца в отдельном сообщении — протокол
  навыка. Следствия и пределы — §4.
- **ADR-0015**: `status: amended`, `amended_by: 0017` во frontmatter (у ADR-0017 — `amends: 0015`,
  по образцу `extends` в ADR-0016) и датированная поправка в тексте: пункт «политику меняет только
  команда CLI в терминале владельца» снят, остальное в силе.
- **SPEC**: §3.1 — абзац «Поправка 2026-10-01 (ADR-0017)» о `base set`, явном значении и `default`;
  §3.5 — строка команды; §6.9 — кто запускает конструктор; §11.2 — пятый навык и правило 4 хука.

## 4. Цена и пределы

- **Хук — защита в глубину, не барьер** (SPEC §11.2, CONTEXT.md «Хук»). Поведение `ask` в режимах
  `bypassPermissions` и `dontAsk` документацией не описано; клиент без хуков (не Claude Code) и
  вовсе не покажет диалога — там, впрочем, обычно нет и Bash. Последняя линия — согласие владельца
  в отдельном сообщении по навыку и разрешения Claude Code на запуск Bash; полноценная защита —
  аутентификация человека (M4). Согласие в сообщении подтверждением по CONTEXT.md не является —
  подтверждение здесь только диалог разрешения.
- **Повышающие и нейтральные команды модель выполняет без диалога.** Ошибочная, но защитная правка
  (скрыла не ту сущность, выключила запись не той базе) обратима той же командой (`open`, `set`,
  `default`, `--write on` — уже с диалогом) и видна владельцу в стенограмме сессии.
- **`uvx` без закрепления ставит последнюю версию пакета**, а плагин закрепляет версию демона.
  `base set` пишет только давно существующие поля записи, поэтому расхождение версий файл не
  портит; `odata1c doctor` показывает расхождение версий демона и пакета. Навык предпочитает
  `odata1c` с PATH (`uv tool install odata1c-gate` из README).
- **Записи в нестандартной форме** (поточные, с ключом слияния, с одностроковыми `gate`/`permissions`)
  команда не правит — отказ с подсказкой поправить вручную.
- **`--role` действует широко**: у базы без явных полей `--role dev` разом выключает гейт и включает
  запись. Это по замыслу роли (SPEC §3.2); команда печатает полное действующее состояние, хук
  требует подтверждения.
- **`policy hide --yes` под моделью** переносит вопрос о числе дочерних сущностей из терминала в
  сообщение модели: навык велит назвать их до запуска.
- **Инструмент PowerShell** Windows PowerShell 5.1 декодирует вывод программ кодировкой консоли
  (`[Console]::OutputEncoding`, обычно OEM) и может исказить UTF-8. Навык велит запускать команды
  через Bash; хук перехватывает обе формы одинаково.
