# Приёмка правил гейта и рецептов для ЗУП на живой базе

Дата: 2026-09-28. Второй шаг этапа «гейт и рецепты для ЗУП»; разведка — `ZUP-recon.md`, правки —
ветка `worktree-gate-zup`.

## Условия

- База: `zup_test` — «ЗУП КОРП 3.1 (тестовая)», уровень гейта `identifiers+names`, запись
  выключена. В отличие от `bp_test`, в базе есть кадровые данные: сотрудники, физлица, документы
  физлиц, справки НДФЛ, заявления о пособиях, больничные.
- Проба: `tools/probes/zup_live_check.py`, только чтение. Настоящий лаунчер `odata1c mcp`
  поднимает демон во временном домашнем каталоге на порту 7198; рабочий дом владельца не
  затрагивается. Авторазметка во временном доме пересобрана проверяемым кодом, словарь пустой.
  Ключ `--owner-gate` кладёт во временный дом каталог правил владельца для доработок базы; сам
  каталог и проверки нетиповых объектов (`--extra-checks`) в репозитории не хранятся.
- Что проверено: 19 сущностей, названных в разведке, проверки нетиповых объектов и все прочие
  сущности ЗУП, где правка дала полю защищаемый класс (сверка с эталоном `class_diff.py`), —
  461 проверка, по каждой до 60 строк одним и тем же запросом напрямую из 1С и через шлюз.
- Критерии — те же, что у приёмки БП (`BP-live-check.md`): оракул (реальное значение
  защищаемого поля от четырёх символов не встречается в ответе шлюза), открытые формы (в
  защищаемом поле вне токенов нет двух цифр подряд и слова из букв), инвариант 6 (открытые поля
  совпадают с ответом 1С). В открытые поля включены прежние ложные срабатывания — основание
  подписи и поле `Имя` нетиповых настроек: после правки их значение должно прийти как есть.
- Положительный контроль: те же 461 проверка на коде `dev` без правок (`--checks-from`).

таблице — его. Проверок стало 461 против 137 до ревью за счёт `КомуВыданСертификат` в 316
сущностях.

## Чего живая база не показала

Из 461 проверки данные нашлись в 50 сущностях. Без данных остались, в частности, анкеты
кандидатов и сами кандидаты, собеседники чат-бота, пачки АДВ, заявки на командировку, заявление
о назначении пенсии, данные застрахованных ДМС и их контактная информация: правила для них
проверены только по метаданным и тестами классификатора.

## Рецепты ЗУП

`tools/probes/zup_recipes_check.py`: запись базы `config: zup` без собственного файла рецептов,
книга — ровно шаблон пакета. Все 9 рецептов выполнены с образцами параметров, ошибок нет, пустых
нет: `staff` — 162 строки, `accruals` — 304, `salary_debt` — 102, `salary_settlements` — 352,
`hires` — 152, `dismissals` — 81, `vacations` — 200, `sick_leaves` — 159, `payroll_documents` — 92.
`masked_fields` у всех пуст: рецепты отдают только ссылки, даты и суммы, а человека в отборе
принимают ссылкой `Ref_Key` сотрудника.

Отбор `staff` (`ВидСобытия ne 'Увольнение'`) проверен отдельно, потому что неверный литерал 1С не
отвергла бы, а вернула бы всех: срез последних кадровой истории на 01.09.2026 напрямую из 1С —
1549 строк (1387 «Увольнение», 127 «Перемещение», 35 «Прием»), рецепт через шлюз — 162 строки,
ровно работающие.

## Воспроизведение

    uv run python tools/probes/class_diff.py --save build/classes-before.json   # на dev, до правок
    uv run python tools/probes/zup_live_check.py --classes-before build/classes-before.json \
        --owner-gate <каталог владельца> --extra-checks <проверки доработок> --out build/zup-live.json
    uv run python tools/probes/zup_live_check.py --checks-from build/zup-live.json   # контроль
    uv run python tools/probes/zup_recipes_check.py

Пароль 1С читается скриптом из рабочего `bases.yaml` и в вывод не попадает; печатаются только
счётчики, имена сущностей и полей, формы значений (цифра → 9, буква → a).
