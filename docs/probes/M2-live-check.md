Дата: 2026-09-13. Закрывает задачу 10 плана `docs/plans/2026-09-12-m2-write.md` в части, которую
можно проверить скриптом. Первая настоящая запись шлюза в живую 1С.

Приёмка пройдена дважды: первая — на `90059e0` (163 проверки, разделы ниже), **повторная — на

## Условия

- База: `trade_dev` — УТ 11 с доработками, база разработки; роль `dev` (запись разрешена ролью),
  гейт `identifiers+names` явно в записи базы. Владелец разрешил запись.
- Код: рабочая копия на `90059e0`, лаунчер (`python -m odata1c mcp`) — отдельным процессом через
  `stdio_client`, демон он поднимает сам (Планировщик заданий, как у владельца).
- Временный домашний каталог: три записи базы — копия `trade_dev` и две её копии для отказов
  (`trade_dev_ro` с `write: false`, `trade_dev_deny` с `deny_fields: [Catalog_Номенклатура.Описание]`),
  у каждой — копия индекса (резервным копированием SQLite, рабочий индекс открыт демоном владельца в
  WAL) и политики. Словарь пуст, секрет гейта свой, `write_confirm_fallback: deny`, порт демона 7195.
  Ключ лаунчера создал сам лаунчер до подъёма демона (Ruling 59). Рабочий дом владельца не тронут:
  время изменения `bases.yaml` (11.09), `daemon.yaml` (10.09), `gate.sqlite` (12.09), `launcher.key`
  (13.09 12:42), индекса и политики — раньше всех прогонов (сверено после последнего); демон
  владельца на 7171 работал всё время, временных каталогов `odata1c-m2-*` не осталось, порты 7195
  и 7196 свободны.
- **Посредник 1С** на 127.0.0.1:7196 между демоном приёмки и публикацией: пропускает запросы как
  есть и считает их по методам — «в 1С ничего не ушло» проверяется счётом, а не журналом демона
  (адресов он не пишет, Ruling 31). Он же держит правило живой базы механически: POST — только
  создание в `Catalog_Номенклатура`/`Document_ПересчетТоваров` или `Post`/`Unpost` своего документа,
  PATCH — только объекты, созданные прогоном (Ref_Key из ответа `commit`), DELETE и PUT — никогда;
  нарушение — HTTP 403, в 1С не уходит. Нарушений нет. За прогон через него прошло GET 66, POST 7,
  PATCH 14 — ровно 21 запрос записи на 21 строку журнала.
- Клиенты: основной — `odata1c-m2-acceptance` с elicitation, отвечает «yes» и запоминает текст
  вопроса (механизм `elicitation`, клиент не Claude Code); `odata1c-m2-no-elicitation` — без
  elicitation; `claude-code` 2.1.267 — через настоящий лаунчер; прямые HTTP-клиенты без лаунчера —
  подписанный ключом дома и назвавшийся `claude-code` в `initialize` без подписи.
- Объекты — по пробе P8: элемент `Catalog_Номенклатура` (маркер в `Description`, поле класса `org` —
  `см_НаименованиеКонтрагента`), документ `Document_ПересчетТоваров` (маркер в `Комментарий`).
  Маркер — `odata1c-приёмка M2 <дд.мм чч-мм-сс>`: наименование номенклатуры уникально и среди
  помеченных (P8). Существующие объекты только читались: 300 контрагентов (выбор источников токена),
  контактная информация восьми из них (иглы сценария 7).
- Реальные значения скрипт не печатает: только счётчики, коды, имена полей, формы (цифра → 9, буква
  → a) и GUID объектов приёмки (инвариант 6). Учётные данные — из рабочего `bases.yaml`, во
  временный пишутся и удаляются с каталогом.

## Сценарии

### 0. Тулы записи сквозь лаунчер

Семь тулов записи видны клиенту за лаунчером; у `odata1c_commit` — `_meta
["anthropic/requiresUserInteraction"] = true` и `destructive_hint`, у `odata1c_journal` —
`read_only_hint`. Лаунчер и демон поднялись за 2,7 с.

### 1. Создать элемент справочника

Токен названия контрагента-источника взят **чтением через шлюз приёмки** (`odata1c_get` по
`Ref_Key`; токены — свои у каждого домашнего каталога). `odata1c_create` с `Description` = маркер и
`см_НаименованиеКонтрагента` = этот токен:

- подготовка не отправила в 1С ни одного запроса записи; превью несёт токен, не значение;
- `commit` — один вопрос elicitation, один POST, ответ с `Ref_Key` и тем же токеном в поле `org`;
- прямой GET: объект есть, `Description` — маркер, в поле `org` — **реальное название
  контрагента-источника** целиком (1С не обрезала);
- журнал временного дома: механизм `elicitation`.

`token_ambiguous` не встретился ни разу (оба первых кандидата разрешились однозначно).

### 2. Найти → изменить по токену → перечитать

`odata1c_query` с `substringof(<маркер>, Description)` находит ровно созданный объект, поле `org` в
выборке — тот же токен, что у контрагента. `odata1c_update` поля `org` токеном второго
контрагента: превью «было — токен первого, станет — токен второго»; после `commit` в 1С —
реальное название второго контрагента, перечитанное шлюзом — тот же токен, что у второго
контрагента. Откат: превью «было — токен второго, станет — токен первого» (прежнее значение из
журнала маскируется, а не отдаётся как есть), после `commit` объект совпал с `before_json` журнала
(3 поля из 3, кроме `DataVersion`), исходная запись отмечена откаченной (`undone_by`).

### 3. Пометка удаления и её снятие

Пометка → `DeletionMark=true`, снятие (`mark=false`) → `false`; откат снятия → `true`, откат
пометки → `false`; каждый — совпадение с `before_json`. У отката пометки (объект к тому времени
уже изменён откатом снятия) превью несёт предупреждение «объект изменён после коммита» — откат
разрешён, пользователь предупреждён.

### 4. Документ

`create` с одним `Комментарий` → документ есть, не проведён. `Post` → `Posted=true`, `Unpost` →
`false`. Откат `Unpost` проводит документ, откат `Post` распроводит (откат действия — по
`before.Posted`, Н8-1); каждый совпал с `before_json` (4 поля из 4). Откат `create` — пометка
удаления, документ не проведён.

Предвидимые отказы 1С (решение 12 плана) — при подготовке, а не 500 на `commit` после
подтверждения: пометка проведённого документа — `params_invalid` с подсказкой «сначала Unpost»;
проведение помеченного — `params_invalid`. В обоих случаях в 1С не ушло ни одной записи. Поэтому
предложенный контролёром способ спровоцировать ошибку 1С на `commit` («Post помеченного») до 1С не
доходит — для Ruling 52 взят другой (6в).

### 5. Откат каждой операции

Из 20 выполненных записей 10 — исходные операции и 10 — их откаты: откачена каждая выполненная
операция, кроме самих откатов. Каждый откат прошёл тот же `commit` с подтверждением. Сверка состояния после отката — прямым GET с
`before_json` журнала временного дома: все поля совпали (кроме `DataVersion` — счётчик растёт на
любой записи, P8). У `create` состояния «до» нет — его откат проверен пометкой удаления.
`odata1c_journal`: 21 строка (`committed` 20, `failed` 1), откаченных 10 и откатов 10 — цепочки видны с
обеих сторон (`undone_by`, `undo_of`).

### 6. Отказы

| Отказ | Как спровоцирован | Итог |
|---|---|---|
| `pending_stale` | подготовлены две операции над одним объектом, выполнена вторая, затем `commit` первой | `pending_stale`, в 1С ни одной записи, в объекте значение второй |
| `field_write_denied` | `update` поля `Описание` в `trade_dev_deny` | код верный, к 1С **ни одного** запроса (и GET тоже) |
| `base_read_only` | `update`, `create`, `mark_for_deletion` в `trade_dev_ro` | код верный у всех трёх, к 1С ни одного запроса |
| ошибка 1С на `commit` (Ruling 52) | `create` второго элемента с тем же `Description` — 1С отклоняет в `ПередЗаписью` (уникальность, P8) | см. ниже |
| `write_unsupported_client` | клиент без elicitation, `write_confirm_fallback: deny`: подготовка есть, `commit` — отказ | в 1С ни одной записи, `DataVersion` объекта не изменилась |
| подпись (Ruling 59) | см. ниже | |

**Ruling 52 на живой.** `commit` дубля: запрос дошёл до 1С (один POST), ответ модели —
`odata_error`, «1С отказала в записи: HTTP 500, код ошибки платформы …, категория …; текст ошибки
1С на уровне гейта identifiers+names не показывается», и номер коммита для журнала. В
`journal.sqlite` временного дома — строка `failed` с полным текстом 1С (146 символов); ни одно его
вхождение (первые 40 символов сообщения платформы) не встретилось ни в одном ответе тула.
`odata1c_journal` показывает эту строку со статусом, HTTP 500, кодом и категорией, `text: null` и
пояснением. Второго элемента в 1С нет — по-прежнему один с этим наименованием.

**Подпись лаунчера.**

- Настоящий лаунчер, клиент назвался `claude-code` 2.1.267: `update` → `commit` выполнен **без
  вопроса демона**, в журнале `claude_code`; откат из той же сессии — тоже без вопроса. Значит,
  лаунчер подписал заголовки ключом, который сам создал, а демон, поднятый им после этого, ключ
  прочитал (ловушки Р59-1 нет).
- Прямой клиент с заголовками `claude-code`, подписанными ключом временного дома (так делает
  лаунчер): положительный контроль — `commit` выполнен, механизм `claude_code`. Идентификатор его
  сессии известен; в ту же сессию — запросы **без подписи** одним POST, как `curl`: `update`,
  `create`, `mark_for_deletion`, `undo` и `commit` уже подготовленного подписанным клиентом отката —
  все `write_unsupported_client` (Р59-А), в 1С ни одной записи; `odata1c_journal` без подписи
  отвечает (чтение). Затем подписанный `commit` того же отката выполнен, объект совпал с
  `before_json`.
- Прямой клиент назвался `claude-code` в `initialize`, без заголовков и подписи, без elicitation:
  подготовка есть, `commit` — `write_unsupported_client`, в 1С ни одной записи.

Журнал временного дома по механизмам: `elicitation` 17 (16 выполненных и 1 отклонённая 1С),
`claude_code` 4 — два коммита настоящего лаунчера и два прямого подписанного клиента.

### 7. От класса данных

Реальные значения, которые приёмка знает из прямых GET: у восьми контрагентов-кандидатов —
названия и полные названия (12, `org`), варианты названий без формы собственности (15), ИНН (6),
КПП (4), их контактная информация — адреса (7), почта (3), телефон (1), строка без типа (1); плюс значения полей `org` объектов приёмки после всех записей. Каждое искалось во
**всех** ответах, которые видела бы модель (65: `commit` 25, `undo` 11, `update` 10, `create` 5,
`mark_for_deletion` 5, `action` 3, `get` 3, `journal` 2, `query` 1 — в том числе отказы, ошибки 1С и
неподписанные запросы), по сырому тексту и по строкам после разбора JSON (кавычки названий в JSON
экранированы), и в 18 текстах вопросов elicitation (перехвачены в клиенте). **Вхождений — ноль.**
Положительный контроль: в сыром ответе 1С на элемент приёмки (прямой GET) игла находится — поиск
не пустой.

### 8. Уборка

`finally` скрипта: объекты прогона и найденные по маркеру прогона прямым GET; проведённым —
`Unpost`, всем — `DeletionMark=true`, сначала через шлюз, при его сбое — напрямую. В итоговом
прогоне уборке делать было нечего: откаты уже пометили оба объекта. Отдельный прогон `--only
уборка` по общему маркеру `odata1c-приёмка M2` нашёл все объекты всех прогонов этого дня — таблица
ниже.

## Находки и наблюдения

1. **Дефект посредника приёмки, не шлюза.** В первом поэтапном прогоне заголовок `Location` ответа
   POST 1С (адрес объекта с кириллицей в UTF-8) уронил `http.server` посредника (заголовки он кодирует
   в latin-1): 1С документ создала, а ответ до демона не дошёл. Шлюз отдал модели ошибку
   `odata_error`, объект остался бы неучтённым, если бы не поиск по маркеру: уборка нашла его и
   пометила через шлюз. Посредник исправлен (заголовки — сырыми байтами). Вывод для проб: поиск по
   маркеру в уборке обязателен — он поймал ровно тот случай, ради которого написан.
2. **Дефект скрипта приёмки.** В первом итоговом прогоне все сценарии прошли, но сценарий 7 читал
   объект прямым клиентом после его закрытия — проверка утечек не выполнилась, прогон повторён
   целиком. Объекты первого прогона убраны откатами.
3. **Вопрос подтверждения задаётся раньше сверки отпечатка.** `commit` устаревшей операции сначала
   спросил пользователя («yes»), и только потом перечитал объект и отказал `pending_stale`. Так
   задумано (`WriteService.commit`: перечитывание — как можно ближе к записи), но пользователь
   подтверждает операцию, которая не выполнится. Не дефект; стоит знать при ручной проверке.
4. **`odata1c_journal` не показывает механизм подтверждения** (`client` есть в `journal.sqlite`,

5. `token_ambiguous` на живых названиях не встретился: варианты названия без формы собственности

### Табличная часть (И-3): первая запись табличной части в живую 1С

`odata1c_create` документа `Document_ПересчетТоваров` с табличной частью `Товары`, строка —
ссылка на элемент приёмки (`Номенклатура_Key`), `Количество` и `КоличествоФакт`.

**Факт живой базы: строку без `LineNumber` 1С не принимает.** Тело без `LineNumber` → HTTP 500,
текст платформы «Произошла внутренняя ошибка OData сервиса. Дополнительные сведения можно найти в
технологическом журнале» — ни поля, ни причины; объект не создан (проверено поиском по маркеру).
Та же строка с `LineNumber: 1` → создан: в 1С ровно одна строка табличной части, `Номенклатура_Key`
— элемент приёмки, `Количество` и `КоличествоФакт` равны отправленным (1С вернула их числом),
предупреждений о расхождении нет. Откат `create` — пометка удаления, документ не проведён.

Шлюз `LineNumber` не требует и не подставляет: в превью строка показана как прислана (GUID и числа
— как есть, литерал комментария — пометкой, Ruling 63). Модель, не знающая этого правила 1С,
получает после подтверждения пользователем невнятный 500. Кандидат на правку продукта (проверка
или автонумерация строк при подготовке) — решение владельца.

### Числовые поля (И-8)

Гипотеза ревьюера проверена на элементе приёмки: `update` числом → `commit` → прямой GET → откат.

| Поле | Тип по индексу | Как 1С отдаёт | Записано | Предупреждение шлюза | Откат |
|---|---|---|---|---|---|
| `СрокГодности` | `Edm.Int64` | **строкой** (`"0"`) | нет | есть | `undo_unsupported` |
| `Крепость` | `Edm.Double` | числом | нет | есть | `undo_unsupported` |
| `ВесЧислитель` | `Edm.Double` | числом | нет | есть | `undo_unsupported` |
| `см_ГарантийныйСрок` | `Edm.Int16` | числом | **да** | нет | вернул точно, в PATCH ушёл `int` |
| `Количество` строки табличной части | `Edm.Double` | числом | **да** (при создании) | нет | — |

Что из этого следует.

1. **Шлюз ни разу не сказал «записано», когда 1С не записала.** Каждый раз, когда значение не
   изменилось, `commit` вернул предупреждение о расхождении (перечитывание после записи, задача 7),
   а подготовка отката ответила `undo_unsupported` «откатывать нечего». Это и есть страховка против
   молчаливого отказа 1С (P8: 1С отвечает 200 и не пишет).
2. **`Edm.Int64` в этой публикации приходит строкой** — так его и сериализует JSON OData v3. Шлюз
   же на запись требует JSON-число (`_проверить_тип`) и строку отвергает. Значит, поле `Edm.Int64`
   через шлюз не записывается вовсе: отправленное число 1С молча игнорирует. Здесь это видно только
   по предупреждению. Отдельный риск того же корня: если бы 1С число приняла, «до» в журнале
   осталось бы строкой, и откат отправил бы строку — 1С снова молча не записала бы (предупреждение
   было бы, восстановления — нет). Отсюда **гипотеза**, а не вывод: посылать `Edm.Int64` (и
   `Edm.Decimal`) строкой, как их сериализует OData v3. Приёмка доказала только половину — что 1С
   **отдаёт** такое поле строкой и **молча игнорирует** присланное число; принимает ли эта
   публикация строку, не проверял никто, а поля `Edm.Decimal` в проверенных сущностях не
   встретилось вовсе. Прежде чем менять продукт, гипотезу нужно проверить отдельной пробой в духе
   P8 (прямой PATCH строкой мимо шлюза — приёмке это запрещено правилами, пробе разрешено).
3. **Незаписанные `Edm.Double` — логика конфигурации, а не типы:** `Количество` строки и
   `см_ГарантийныйСрок` записались, а `Крепость` и `ВесЧислитель` типовая конфигурация при записи
   сбрасывает (эти реквизиты зависят от вида номенклатуры и единиц измерения).

Проверяет то, чего не может скрипт: настоящий Claude Code — имя клиента `claude-code`, протокол,

     `daemon.yaml → claude_code_parents`), механизм будет `elicitation` — это работа правила, а не
     дефект.
   Если все три причины исключены, а форма есть — имя клиента или подпись не распознаны: это
   находка Н9-1, запишите версию Claude Code.
5. Ответьте **«Нет»**. Проверьте: `odata1c_get` того же объекта с `select: ["НаименованиеПолное"]` —
   значение прежнее; `odata1c_journal` — новой строки нет.
6. Попросите вызвать `odata1c_commit` того же `pending_id` ещё раз и ответьте **«Да»**. `odata1c_get`
   — новое значение; `odata1c_journal` — строка `committed`. Если вместо этого пришёл отказ 1С (500)
   — смотрите шаг 2: запись обычного поля в помеченный объект может отклонять сама конфигурация;
   снимите пометку и повторите.
7. Механизм — чтением журнала мимо модели, в терминале (печатает только номер, операцию, статус и
   механизм, без значений):

   ```bash
   uv run python -c "import pathlib; from odata1c.write.journal import Journal; j = Journal(pathlib.Path.home() / '.claude/odata1c/journal.sqlite'); [print(e.commit_id, e.op, e.status, e.client) for e in j.recent('trade_dev', 5)]; j.close()"
   ```

   Ожидается `claude_code` у строки из шага 6.
8. Повторите шаги 3–6 в автоматическом режиме (Shift+Tab до режима auto): диалог на `commit` должен

## Воспроизведение

```bash
PYTHONUTF8=1 uv run python tools/probes/m2_live_check.py --out итог.json   # всё, ~3 мин
PYTHONUTF8=1 uv run python tools/probes/m2_live_check.py --only часть,числа # отдельные разделы
PYTHONUTF8=1 uv run python tools/probes/m2_live_check.py --only уборка      # уборка по общему маркеру
```

Каждый полный прогон создаёт один элемент номенклатуры и два документа (один с табличной частью);
все они откатываются и помечаются на удаление, наименование уникально по времени прогона. Разделы:
`тулы`, `создание`, `токен`, `пометка`, `устаревание`, `числа`, `запреты`, `документ`, `часть`,
`регистр`, `литерал`, `исход`, `ошибка_1с`, `клиент`, `подпись`, `журнал`; разделы справочника
сами создают элемент, сценарий 7 и уборка выполняются всегда. Рабочий дом не трогается; порты 7195 (демон) и
7196 (прокси-счётчик) должны быть свободны.
