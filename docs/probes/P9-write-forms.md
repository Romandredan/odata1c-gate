# P9 — запись независимого регистра сведений, табличная часть, `Edm.Int64` на живой базе

**Дата:** 2026-09-20. **База:** `trade_dev` (УТ 11, платформа 8.3, публикация за IIS), роль `dev`.
**Зачем:** проба идёт ДО реализации задачи 6 плана M3b (§5.1–§5.3, §5.4) — без неё решения по
`LineNumber`, записи табличных частей через `update` и записи независимых регистров сведений были
бы гаданием, а Ruling 100 (независимые регистры сняты в M3b) прямо назвал причину: «в живую 1С ни
разу не уходило». Восемь вопросов (P9-1…P9-8) отвечают фактами платформы 1С — гейта здесь нет
вовсе, проба идёт мимо шлюза, как P8.

**Метод:** прямые запросы через `tools.probes.m2_live_check.Прямой1С`, пароль — из рабочего
`bases.yaml` (`load_config`), в скрипте и в этом отчёте его нет. Пишущие запросы идут через
`tools.probes.m2_live_check.Посредник1С` (порт 7196) — тот же прокси-счётчик и белый список, что у
приёмки M2: POST/PATCH — только по объекту(-ам) этого прогона, DELETE — только по записи регистра
с маркером этого прогона в ключе, PUT — никогда. Скрипт: `tools/probes/p9_write_forms.py`.

Независимый регистр сведений вне фиксированного набора `Посредник1С`
(`Catalog_Номенклатура`/`Document_ПересчетТоваров`), поэтому задача 5 добавила в
`Посредник1С.__init__` (`tools/probes/m2_live_check.py`) второй, симметричный параметру `удалять`,
предикат `доп_разрешено(метод, хвост)` — проверяется для POST и PATCH, только когда обычный белый
список отказал; по умолчанию `None`, поведение приёмки M2 не меняется. Это отклонение от буквы
брифа задачи (там описан только параметр `удалять` для DELETE) — без него POST создания записи
регистра и PATCH по её составному ключу отклонялись бы посредником: регистр в принципе не входит
в набор, для которого посредник M2 знает готовые правила POST/PATCH. `удалять` реализован ровно
так, как описано (DELETE — только по пути `InformationRegister_ШтрихкодыНоменклатуры(...)` с
маркером этого прогона в ключе; без предиката DELETE по-прежнему не пропускается никогда).

Создаётся ровно два объекта: элемент `Catalog_Номенклатура` с маркером `odata1c-приёмка P9
<время>` в `Description` и запись `InformationRegister_ШтрихкодыНоменклатуры` со
штрихкодом-маркером `ODATA1C-PROBE-<время>`, ссылающаяся на него. Табличная часть, которую правит
проба, — `Представления`: `ДополнительныеРеквизиты` тоже непустая у существующих элементов, но её
строка требует ссылку на элемент плана видов характеристик (`Свойство_Key`); `Представления`
собирается из двух простых строковых полей (`КодЯзыка`, `НаименованиеПолное`) без внешней ссылки —
выбор сделан по этому критерию (задача разрешает выбор, брифу это не противоречит).

## Уборка

Порядок в `finally`: сначала запись регистра, потом пометка удаления элемента (в этом прогоне
запись регистра к моменту уборки уже была убрана вопросом P9-4 — уборка нашла «остатков по маркеру
нет» и перешла к пометке элемента). Подтверждено чтением после прогона:

- поиск по маркеру `Catalog_Номенклатура` (`substringof('odata1c-приёмка P9 …', Description)`) —
  находит элемент, `DeletionMark = true`;
- поиск по маркеру регистра (`Штрихкод eq 'ODATA1C-PROBE-…'`) — 0 строк.

Счётчик посредника за весь прогон: `{"POST": 3, "GET": 15, "PATCH": 9, "DELETE": 1}`, нарушений
белого списка — 0 (POST — создание элемента и дважды регистр [P9-1, P9-2 отклонённый]; DELETE —
ровно один, запись регистра по маркеру, P9-4). Воспроизведение:
`PYTHONUTF8=1 uv run python tools/probes/p9_write_forms.py --out C:/Temp/p9.json`.
