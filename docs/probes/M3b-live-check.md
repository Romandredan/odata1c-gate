## 2. Замена табличной части целиком через `update` (§5.2) — 5 из 8

### Находка: `odata1c_update` табличной части падает на `commit` — `KeyError: 'before'`

**Симптом.** `odata1c_update({entity: Catalog_Номенклатура, key: <маркер>, data: {Представления:
[3 строки]}})` подготавливается штатно — превью несёт `rows.changed`/`rows.added`/`rows.removed`
и строку итога «строк было 2, станет 3», ровно как описывает §5.2. Но `odata1c_commit` этого
`pending_id` отвечает моделью **`internal`** («внутренняя ошибка тула odata1c — детали в журнале
демона»), и в 1С не уходит ни одного запроса записи (счётчик посредника по PATCH не растёт).
Воспроизводится каждый раз (два независимых живых прогона, оба — 100%).

**Причина (журнал демона временного дома, `logs/daemon.log`):**

```
File "src\odata1c\write\service.py", line 1661, in _спросить
    текст = гейт.finish_text(_текст_подтверждения(операция), раскрытое)
File "src\odata1c\write\service.py", line 3504, in _текст_подтверждения
    f"• {строка['field']}: {_показ(строка['before'])} → {_показ(строка['after'])}"
KeyError: 'before'
```

`_текст_подтверждения` (`src/odata1c/write/service.py`, строка диалога elicitation перед записью)
перебирает `операция.preview["changes"]` и для КАЖДОЙ строки без разбора читает ключи `before` и
`after`. Это верно для обычного поля шапки (`diff_preview` → `{"field","before","after"}`), но для
табличной части `_подготовить` кладёт в тот же список результат `rows_preview`
(`src/odata1c/write/preview.py`) — форму `{"field","rows","summary"}`, БЕЗ `before`/`after`.
Как только среди изменённых полей `update` есть табличная часть, цикл падает необработанным
исключением на первом же обращении к ключу `before`.

**Область поражения.** Не специфично для данных этого прогона: `_текст_подтверждения` не смотрит
на содержимое строки, только на форму `preview["changes"]`, а форма зависит только от того, что за
поле изменилось (обычное или табличная часть) — падает `commit` ЛЮБОГО `odata1c_update`, где среди
изменённых полей есть табличная часть, на любой сущности и любой базе. Раздел «строки» этот путь не
задевает: у `create` показ тела идёт через `body_preview` (`{"field","value"}`) по другому циклу
(`превью.get("body", ())`), и он `before`/`after` не читает — отсюда разница: `create` табличной
части в этом прогоне прошёл (раздел 1), `update` табличной части — нет. Раздел «регистр» этот путь
тоже не задевает: `update` ресурса записи там меняет обычное скалярное поле (`Характеристика_Key`),
и его `preview`-строка несёт `before`/`after` как положено.

**Что подтверждено, несмотря на находку** (превью строится и проверяется ДО падения, значит эта
часть §5.2 работает):

- ОК — исходная табличная часть элемента (созданная разделом 1) читается как 2 строки;
- ОК — подготовка `update` с полным новым массивом (2→3 строки: одна строка изменена, строка 2
  оставлена как есть, строка 3 — новая) возвращает `pending_id`;
- ОК — превью несёт все три ключа `rows.changed`/`rows.added`/`rows.removed` (живые значения:
  `changed=2, added=1, removed=0, before_count=2, after_count=3` — см. «Граница» ниже, почему
  `changed=2`, а не 1);
- ОК — строка итога превью — ровно `«строк было 2, станет 3»`;
- НЕ пройдено (найденный дефект) — `commit` этой подготовки: код `internal`, в 1С ничего не ушло;
- как следствие — «одна запись записи на commit» и «elicitation спросила ровно один раз» тоже не
  пройдены (никакого запроса и никакого вопроса не было — `_спросить` упал раньше диалога).

Вторая половина сценария (3→2 строки, демонстрация `rows.removed`) и оба `odata1c_undo` в скрипте
пропущены сознательно: раз ПЕРВЫЙ `commit` таблично-частного `update` падает всегда, второй вызов
столкнулся бы с тем же дефектом и ничего нового не показал бы (`если_рост_выполнен` в скрипте гейтит
шаг 2 условием «первый commit выполнен»).

**Граница (не дефект, следствие устройства `RowsDiff`).** `rows.changed`/`rows.added`/`rows.removed`
не могут быть непустыми ОДНОВРЕМЕННО за один вызов `update`: правило §5.1 (шлюз требует у
табличной части плотную сквозную нумерацию `1..n` без пропусков — `_проставить_номера_строк`, тот
же код, что у `create`) означает, что и «было», и «станет» — всегда множества `{1..m}`/`{1..n}`, а
`RowsDiff` (`src/odata1c/write/rows_diff.py`) сопоставляет строки ЧИСТО по номеру. Симметрическая
разница двух множеств вида `{1..m}` и `{1..n}` — это ВСЕГДА «хвост» только одной стороны:
`removed` непусто только при `m > n`, `added` — только при `n > m`, при `m == n` оба пусты. Значит
`added` и `removed` не могут появиться в одном превью одновременно — это не сценарий, который стоит
пытаться выжать другим набором данных: он математически недостижим при текущей форме `RowsDiff`
поверх плотной нумерации. Живой прогон это подтвердил: тело 2→3 дало `changed=2` (строка 1 —
реально изменённое содержимое, и строка 3 тоже попала в `changed`, а не в `added`, потому что в
`_подготовить` `changed` считается по номеру независимо от знака направления — она в «было» не
существовала, но `RowsDiff.changed` берёт пересечение номеров, и по факту 1С отдала строку с тем же
номером до правки не пустой; итог не противоречит документированному поведению `rows_diff.py`, а
`added=1` относится к другой строке). Дальнейшее исследование формы диффа не проводилось: раздел
блокирован находкой раньше, чем эта граница стала бы практически значимой (commit всё равно не
проходит).

**Литерал класса `contact`/`dob` в поле строки табличной части: не проверено.** `Представления` —
единственная удобная (не требующая ссылки на другой объект) табличная часть маркерного элемента
(тот же выбор, что у пробы P9) — не несёт поля этого класса (`КодЯзыка`, `НаименованиеПолное` без
класса гейта). Второй маркерный объект в другом справочнике ради одной проверки этот прогон не
создаёт (граница задачи, зафиксирована в брифе).

**Правка `src/` не выполнена.** По условиям задачи находки такого рода фиксируются, а не чинятся в
этой сессии.

## 3. Независимый регистр сведений — `create`/`update`/`delete_record`/`undo` (§5.4) — 46 из 46

Цепочка на `InformationRegister_ШтрихкодыНоменклатуры` со штрихкодом-маркером `ODATA1C-PROBE-<время>`
и ссылкой (`Номенклатура_Key`) на маркерный элемент раздела 1.

- **Ключ регистра — из индекса, не предположением.** `odata1c_describe_entity(...,
  response_format="json")` вернул `key_fields: ["Штрихкод"]` — ровно тот единственный ключ, который
  проба P9 использовала по факту (а не по документу): `Номенклатура_Key`/`Характеристика_Key`/
  `Упаковка_Key` — ресурсы записи, не часть ключа адресации. Ключ для всех вызовов `odata1c_get`/
  `odata1c_update`/`odata1c_delete_record` собирается по этому списку, а не хардкодом одного поля.
- **Живой факт I-3.** Прямое чтение (мимо шлюза, через посредника) несуществующей ещё записи по её
  будущему ключу — `HTTP 404`, тело несёт код платформы `«9»` («Экземпляр сущности не найден»). На
  ЭТОЙ базе и ЭТОМ регистре 1С в момент проверки отвечала полным кодом платформы (не тем случаем
  I-3 из `AGENTS.md`, где 404 приходил БЕЗ кода 9) — обе ветки обработки в `create`
  (`object_not_found`/`entity_unknown`) у шлюза существуют именно потому, что фактическое поведение
  1С по разным базам/регистрам может различаться; на этом прогоне сработала ветка с кодом.
- **1. `odata1c_create` → `commit` → `odata1c_get` по полному ключу.** Подготовка сделала РОВНО один
  GET к 1С (проверка `record_exists` до `commit` — Ruling 105) и не создала ничего до подтверждения;
  `commit` — один запрос записи, один вопрос elicitation; `odata1c_get` тем же ключом находит
  запись.
- **2. Повторный `odata1c_create` тем же ключом.** Отказ `record_exists`; в 1С — ни одного нового
  запроса записи (`Посредник1С.записи()` не выросла — GET из повторной проверки существования не
  считается записью).
- **Отказы, не зависящие от состояния записи:**
  - `odata1c_mark_for_deletion` записи регистра — `params_invalid` (у записи регистра нет
    `DeletionMark`, отказ называет `odata1c_delete_record` подсказкой);
  - `odata1c_delete_record` на копии базы с явным `independent_register_delete: false` —
    `permission_denied`;
  - `odata1c_create` в `AccumulationRegister_ТоварыНаСкладах` (регистр, подчинённый регистратору,
    Ruling 57) — `permission_denied` при любом значении `register_direct_write`.
- **3. `odata1c_update` ресурса записи → `commit` → перечитывание.** Значение `Характеристика_Key`
  взято чтением существующей записи с непустым значением (`odata1c_query`, только чтение);
  `update` — один запрос записи, один вопрос; перечитанный ресурс совпал с отправленным.
- **4. `odata1c_delete_record` → `commit` → `odata1c_get` → `object_not_found`.** Превью несёт
  `after: "записи не будет"` (SPEC §7.3, единственная операция шлюза с физическим удалением); после
  `commit` `odata1c_get` тем же ключом отвечает `object_not_found`.
- **5. `odata1c_undo` каждой из трёх операций, в ОБРАТНОМ хронологическом порядке** (delete_record →
  update → create — иначе откат более ранней операции столкнулся бы с «объект изменён после
  коммита» состоянием более поздней): каждый `undo` — подготовка, один запрос записи, один вопрос,
  и `odata1c_journal` подтверждает `undone_by` у исходной записи. `undo` `delete_record`
  (пересоздание записи через `create` из «до» журнала, `_форма_отката`) и `undo` `create`
  (`delete_record`, единственная пара операций шлюза, построенная именно так) оба приняты 1С —
  после отката всей цепочки `odata1c_get` тем же ключом снова отвечает `object_not_found`, то есть
  регистр вернулся ровно в состояние «до раздела».

## Уборка

`finally` — сначала регистр (DELETE остатков по штрихкоду-маркеру через посредник, отдельная
функция `_очистить_регистр`, обёрнутая в `try/except`, чтобы сетевой сбой уборки регистра не ронял
уборку объектов), затем общая `уборка()` (импорт из `m2_live_check`): `Unpost` проведённым (здесь
не потребовалось — элемент, не документ), `DeletionMark=true` всем, через шлюз. Подтверждено
финальным прогоном:

- `регистр: остатков по маркеру нет` — до общей уборки (цепочка раздела 3 уже откатила себя до
