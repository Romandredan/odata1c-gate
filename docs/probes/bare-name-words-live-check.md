# Ruling 115 — одиночное слово в свободном тексте не название: приёмка на `trade_dev`

Дата: 2026-09-28. Задача 7 плана «Одиночное слово в свободном тексте — не название». Живая база
`trade_dev`. Код «после» — `HEAD` перед этим отчётом = `0a56c45` («docs: Ruling 115 — одиночное
слово в свободном тексте не название»); код «до» — `origin/dev` = `d19fd7b` («Слияние PR №7:
версия dev — 0.3.0.dev0»).

Реальных значений данных 1С (названий, ИНН, телефонов, ФИО, текстов) в этом отчёте нет — только
счётчики, коды и формы.

## Что проверялось

1. Граница слова (Ruling 115, задачи 1–5): собственно правка — ушедшая из замены запись обязана
   быть формой «одиночное слово», обратных участков (текст → токен) быть не должно, токенов внутри
   слова быть не должно ни «до», ни «после».
2. Регрессии смежных приёмок при уровне гейта `identifiers+names`: контактная информация и адреса
   (Ruling 33–37) и запись (M2) — без утечек реальных значений.

### Сверка единиц счёта (334 → 245): дополнительная проверка

Occurrence-level счётчик токенов (334 «до») и record-level сумма блока «сравнение»
(224 ушедших + 21 устойчивый = 245) не обязаны совпадать: 334 считает каждое вхождение токена во
всех страницах ответа (14458 запрошенных строк, с повтором строки при дрейфе `skip`-окна без
`$orderby` на общей живой базе), а 245 — по уникальному ключу записи (13369 ключей, `0`
несопоставленных в обе стороны). Расхождение единиц счёта само по себе не свидетельствует о
пропущенной находке.

Чтобы исключить это как объяснение, написана точечная сверка (`<scratchpad>/reconcile.py`,
использует функции `ушедшие_из_замены` и `_токен_в_токен` из самого скрипта пробы без изменения
их кода): для каждой сопоставленной пары значений поля отдельно проверено тождество
`steady + ушли == токенов_до` и `steady + обратных == токенов_после`, где `токенов_до`/
`токенов_после` — число токенов `org`/`person`, найденных прямым regex-поиском в значении поля
(независимо от посимвольного `diff`). Прогон дал собственный, более скромный по объёму снимок
живой базы (изменчивость общей `trade_dev` между независимыми прогонами):

```
вызовов сверить_пару: 13369
сопоставлено ключей: 13369
сумма токенов «до» (по парам): 21
сумма токенов «после» (по парам): 21
сумма steady (токен-в-токен): 21
сумма ушедших (токен→текст): 0
сумма обратных (текст→токен): 0
пар, где до не сходится: 0
пар, где после не сходится: 0
```

Тождество сошлось на всех 13369 сопоставленных парах без исключений. Расхождение 334 vs 245 в
основном прогоне объясняется occurrence-level дублями страниц (симметричными в обоих
прогонах — иначе «не сопоставлено» не было бы нулевым), а не потерянной или неверно
классифицированной находкой. Критерий подтверждён дважды, на двух независимых снимках живой базы.

## Приёмки контактной информации и M2 — уровень гейта во временном доме

`odata1c base list` в рабочем доме показал у `trade_dev` уровень `off` (умолчание роли `dev`, без
явного `gate.mode` в записи базы) — при этом уровне `contact_info_live_check.py` и
`m2_live_check.py` не проверяют маскировку вовсе, так как копируют запись базы во временный дом
как есть (в отличие от `word_boundary_live_check.py`, который принудительно выставляет
`identifiers+names`). Пробный прогон это подтвердил эмпирически (`masked_fields: []` во всех
разделах, телефоны и адреса открыты почти полностью).

По решению контролёра (вариант «б») собственный `собрать_дом` обоих скриптов приёмки правится в
одном коммите — `d3ce698` («probes: приёмки контактной информации и M2 — уровень гейта
identifiers+names во временном доме»): копия записи базы во временном доме принудительно получает
`gate: {mode: identifiers+names}`, тем же способом, каким это уже делает
`word_boundary_live_check.py`; у `m2_live_check.py` — у всех трёх копий (основная, только для
чтения, с запретом поля), так как копии наследуются от основной записи через распаковку словаря.
Рабочая конфигурация владельца (`bases.yaml`) не менялась. `ruff check`/`ruff format --check` по
обоим файлам не показали новых нарушений (шесть уже существовавших до правки замечаний E501/SIM117
в `contact_info_live_check.py` и одно форматирование одной строки — вне диффа этой задачи;
каталог `tools/probes` внесён в `[tool.ruff] exclude` в `pyproject.toml`, то есть ruff его не
проверяет и в непрерывную проверку эти файлы не входят).

«ни одного реального значения в ответах тулов» и «ни одного реального значения в текстах

приёмки и ни одного `DELETE`/`PUT`.

Оба расхождения — не регрессия Ruling 115 и не следствие правки уровня гейта в пробе (задача не
трогает логику табличных частей и независимых регистров, только гейт-масштаб): это разрыв между
скриптом приёмки и двумя более поздними изменениями слоя записи, вошедшими в выпуск `0.2.0`
(2026-09-21), уже после того как `m2_live_check.py` в последний раз проверялся целиком:

- **«часть», 18 из 19** — тест ожидает, что 1С отклонит строку табличной части без `LineNumber`
  (старое поведение, актуальное на момент `M2-live-check.md`, 2026-09-13). С 0.2.0 шлюз сам
  проставляет `LineNumber` по порядку тела (`_проставить_номера_строк`,
  `src/odata1c/write/service.py:152`) — 1С получает уже пронумерованную строку и принимает её
  («1С приняла» вместо ожидавшегося отказа). Это документированное поведение 0.2.0, не дефект.
- **«регистр», 1 из 7** — тест Ruling 60 ожидает, что запись независимого регистра сведений
  отклоняется безусловно кодом `permission_denied`. С 0.2.0 запись независимых регистров сведений
  открыта (`create`/`update`/восьмой тул `odata1c_delete_record`, флаг
  `independent_register_delete`, `src/odata1c/write/service.py:830,861,1864`), и код отказа стал
  специфичнее по инструменту: подготовка `create` прошла без ошибки (не была закоммичена — тест
  не вызывает `commit`, реальной записи не произошло), `update` вернул `object_not_found` (пустой
  GUID не существует в регистре — потребовалось обращение к 1С для проверки, отсюда и
  несовпадение счётчика «к 1С ни одного запроса»), `mark_for_deletion` вернул `params_invalid`
  (регистр не поддерживает пометку удаления как понятие — для регистров используется
  `odata1c_delete_record`). Ни одна из трёх попыток не привела к реальной записи в `trade_dev`
  (создание не закоммичено, обновление не нашло объект, пометка отклонена до 1С) — тот же вывод
  подтверждает счётчик посредника из раздела 7 (0 несанкционированных `POST`/`PATCH`).

Обновление `m2_live_check.py` под текущие возможности записи (раздельные позитивные тесты для
`LineNumber`-автонумерации и открытой записи независимых регистров, с явным разрешением
`independent_register_delete` во временном доме) — отдельная задача вне рамок Ruling 115;
рекомендуется владельцу.

## Вывод по критерию 4 проекта

Критерий Ruling 115 (граница слова: голое ядро названия внутри другого слова не заменяется)
подтверждён на живой базе `trade_dev` дважды независимыми снимками данных, без единого исключения.
Цена решения (раздел 4 проекта, `task-6-extra.md`, п. 5) не изменилась: одиночное название и
часть ФИО без кавычек и формы собственности в свободном тексте остаются открытыми — это ожидаемое,
принятое владельцем поведение, а не находка. Регрессий инварианта 1 (реальные значения не выходят
через MCP) не найдено ни в приёмке контактной информации, ни в приёмке записи M2 при уровне гейта
`identifiers+names`. Расхождения в приёмке M2 (7 из 249) относятся к устаревшим относительно
выпуска 0.2.0 ожиданиям самого скрипта приёмки, а не к правке этой задачи.
