### Сверка единиц счёта (334 → 245): дополнительная проверка

Occurrence-level счётчик токенов (334 «до») и record-level сумма блока «сравнение»
(224 ушедших + 21 устойчивый = 245) не обязаны совпадать: 334 считает каждое вхождение токена во
всех страницах ответа (14458 запрошенных строк, с повтором строки при дрейфе `skip`-окна без
`$orderby` на общей живой базе), а 245 — по уникальному ключу записи (13369 ключей, `0`
несопоставленных в обе стороны). Расхождение единиц счёта само по себе не свидетельствует о
пропущенной находке.

Чтобы исключить это как объяснение, написана точечная сверка (`<scratchpad>/reconcile.py`,
использует функции `ушедшие_из_замены` и `_токен_в_токен` из самого скрипта пробы без изменения
их кода): для каждой сопоставленной пары значений поля отдельно проверено тождество
`steady + ушли == токенов_до` и `steady + обратных == токенов_после`, где `токенов_до`/
`токенов_после` — число токенов `org`/`person`, найденных прямым regex-поиском в значении поля
(независимо от посимвольного `diff`). Прогон дал собственный, более скромный по объёму снимок
живой базы (изменчивость общей `trade_dev` между независимыми прогонами):

### Разбор находки «рядом кавычка» (без реальных значений)

По инструкции контролёра код не менялся — только разбор по форме окна. Дополнительный скрипт
`<scratchpad>/reconcile_r2.py` (использует `_вид_ушедшего`, `ТОКЕН_НАЗВАНИЯ`, `ЛЮБОЙ_ТОКЕН`,
`форма`, `_голое_слово`, `normalize_text_with_map` из самого `word_boundary_live_check.py` без
изменения их кода) для видов, отличных от «одиночное слово», печатает `форма(слева + стало +
справа)` — окно в 40 символов по обе стороны от ушедшего слова, буквы → `a`, цифры → `9`, токены
→ `T`, прочие символы как есть. Единственная находка дала (одинаково во всех трёх прогонах):

```
99 aa 99 aaa 9999 a. aa aaaaaa "aaaaaa" aaaaaaaa aaaaa, a aaa aaaaa aaa 99 % - 9999.99 a
```

Структура формы — число, короткое слово, число, короткое слово, дата-подобная группа `9999 a.`,
слово, слово, **слово в прямых двойных кавычках без пробела с обеих сторон** (это и есть ушедшее
одиночное слово — кавычки прямые, не угловые и не обратный апостроф), ещё слово, слово с запятой,
короткие слова, число с `%` и денежная сумма в конце — форма типична для `НазначениеПлатежа` или
похожего текста с указанием НДС.

Кавычки в находке — прямые двойные (входят в покрытый Ruling 115 набор написаний), а не угловые
`‹›`/`«»` и не обратный апостроф (это остаётся в «Остатке Ruling 115», SPEC §6.5, п. 2, и в эту
находку не попадает). Правдоподобное объяснение — не дефект ключа, а документированный останов
правила приоритета полного написания (`task-6-extra.md`, п. 3; SPEC §6.5 «неоднозначный вариант не
заменяется ни одним токеном»): если голое ядро в кавычках совпадает с ключом сразу двух кандидатов
токенов (например, название без формы и то же название в кавычках у другого юридического лица),
ключ остаётся неоднозначным и текст не заменяется — то есть попадает в п. 3/4 «Остатка Ruling 115»
(чужая форма или полная форма разных юридических лиц с общим ядром), а не в п. 2 (нераспознанные
виды кавычек). Это предположение по форме, не по значению — окончательное решение (входит ли
конкретно этот случай в принятую цену раздела 4 проекта или это точечный дефект приоритетного
правила) требует владельца с доступом к реальным данным записи; в код изменений не вносилось.

свободного текста трёх типов сущностей просто не содержит написаний новых видов на этом снимке).

### Методологическая заметка (не влияет на официальный результат)

Первый черновой прогон `<scratchpad>/reconcile_r2.py` дал вырожденный результат (0 расхождений,
29 токенов «до» и «после» одинаково) — путь к каталогу «до» был передан в формате Git Bash
(`/c/Temp/...`), а скрипт сам (не через argv, а изнутри уже запущенного Python) прокидывает его в
`PYTHONPATH` дочернего процесса; такой путь не резолвится нативным Windows-python, и «до»-прогон
молча выполнился на коде `HEAD` вместо `origin/dev`. Путь исправлен на нативный формат
(`C:\Temp\...`), после чего оба независимых повторных прогона совпали с официальным
`--compare`-прогоном (`итог_r2.json`) до последней цифры. Официальный вызов
`word_boundary_live_check.py --compare` этой ошибке не подвержен: Git Bash конвертирует
POSIX-путь в аргументе командной строки перед запуском процесса, а не после.

## Приёмки контактной информации и M2 — уровень гейта во временном доме

Эти два раздела относятся к первой приёмке (код «после» `0a56c45`) и не переигрывались для

Рабочая конфигурация владельца (`bases.yaml`) не менялась. `ruff check`/`ruff format --check` по
обоим файлам не показали новых нарушений (шесть уже существовавших до правки замечаний E501/SIM117

скриптом приёмки и двумя более поздними изменениями слоя записи, вошедшими в выпуск `0.2.0`
(2026-09-21), уже после того как `m2_live_check.py` в последний раз проверялся целиком:

- **«часть», 18 из 19** — тест ожидает, что 1С отклонит строку табличной части без `LineNumber`
  (старое поведение, актуальное на момент `M2-live-check.md`, 2026-09-13). С 0.2.0 шлюз сам
  проставляет `LineNumber` по порядку тела (`_проставить_номера_строк`,
  `src/odata1c/write/service.py:152`) — 1С получает уже пронумерованную строку и принимает её
  («1С приняла» вместо ожидавшегося отказа). Это документированное поведение 0.2.0, не дефект.
- **«регистр», 1 из 7** — тест Ruling 60 ожидает, что запись независимого регистра сведений
  отклоняется безусловно кодом `permission_denied`. С 0.2.0 запись независимых регистров сведений
  открыта (`create`/`update`/восьмой тул `odata1c_delete_record`, флаг
  `independent_register_delete`, `src/odata1c/write/service.py:830,861,1864`), и код отказа стал
  специфичнее по инструменту: подготовка `create` прошла без ошибки (не была закоммичена — тест
  не вызывает `commit`, реальной записи не произошло), `update` вернул `object_not_found` (пустой
  GUID не существует в регистре — потребовалось обращение к 1С для проверки, отсюда и
  несовпадение счётчика «к 1С ни одного запроса»), `mark_for_deletion` вернул `params_invalid`
  (регистр не поддерживает пометку удаления как понятие — для регистров используется
  `odata1c_delete_record`). Ни одна из трёх попыток не привела к реальной записи в `trade_dev`
  (создание не закоммичено, обновление не нашло объект, пометка отклонена до 1С) — тот же вывод
  подтверждает счётчик посредника из раздела 7 (0 несанкционированных `POST`/`PATCH`).

Обновление `m2_live_check.py` под текущие возможности записи (раздельные позитивные тесты для
`LineNumber`-автонумерации и открытой записи независимых регистров, с явным разрешением
`independent_register_delete` во временном доме) — отдельная задача вне рамок Ruling 115;
рекомендуется владельцу.

## Вывод по критерию 4 проекта

Критерий Ruling 115 (граница слова: голое ядро названия внутри другого слова не заменяется)
подтверждён на живой базе `trade_dev`: токенов внутри слова — 0 на обоих кодах («до» и «после»,
в первой и повторной приёмке), обратных участков — 0. На коде первой приёмки (`0a56c45`) все 224
ушедшие записи — чистое «одиночное слово», без исключений. На коде после итогового ревью
(`350e8e0`), с расширенной классификацией пробы по окну, 223 из 224 — по-прежнему чистое
«одиночное слово»; 1 запись классифицирована как «одиночное слово, рядом кавычка» — устойчивая
на трёх независимых прогонах находка, разобранная по форме окна в разделе выше и правдоподобно
относимая к документированному «Остатку Ruling 115» (SPEC §6.5, п. 3/4 — неоднозначность
приоритета полного написания между двумя кандидатами токена), но не подтверждённая на реальных
значениях (агенту они недоступны) — **требует решения владельца**: принять как известную цену
раздела 4 проекта или завести отдельную задачу на уточнение правила приоритета для кавычечного
ключа. Код по указанию контролёра не менялся.

Регрессий инварианта 1 (реальные значения не выходят через MCP) не найдено ни в приёмке контактной
информации, ни в приёмке записи M2 при уровне гейта `identifiers+names` (обе — по состоянию первой
приёмки, слой записи и контактной информации итоговым ревью не затронут). Расхождения в приёмке M2
(7 из 249) относятся к устаревшим относительно выпуска 0.2.0 ожиданиям самого скрипта приёмки, а не
к правке этой задачи.
