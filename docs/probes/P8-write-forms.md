# P8 — формы записи OData 1С на живой базе

**Дата:** 2026-09-12. **База:** `trade_dev` (УТ 11, платформа 8.3, публикация за IIS), роль `dev`,
владелец разрешил запись. **Зачем:** записи в OData 1С в проекте ещё не делал никто, а заглушка 1С
дважды оказывалась мягче настоящей платформы (пробел `+` в `$filter`, Job Object клиента). Задачи
5–7 плана M2 опираются на факты этой пробы: форма URL проведения, частичный PATCH, `DataVersion` и
оптимистическая блокировка, ответ POST, эхо переданного значения в ошибке записи.

**Метод:** прямые запросы `httpx` к публикации, без шлюза — поэтому проба ничего не пишет в словарь
`gate.sqlite` (в отличие от приёмки M1d). Кодирование — как у `Client1C`: путь через
`_экранировать_путь`, строка запроса через `_собрать_запрос` (пробел — `%20`), `$format=json` в
каждом запросе, тело ответа — UTF-8 из байтов. Учётные данные — из рабочего `bases.yaml`, в вывод и
отчёт не попадают. Скрипт: `tools/probes/p8_write_probe.py`.

Правила живой базы: проба меняет только созданные ею объекты — у каждого маркер
`odata1c-приёмка P8 2026-09-12` в `Description` (у документа — в `Комментарий`); существующие
объекты только читаются ради ссылок. Каждый созданный объект сразу пишется в журнал созданного;
уборка — `Unpost` проведённых, `DeletionMark=true` всем, плюс поиск по маркеру (`substringof`) на
случай объекта, которого нет в журнале. Физического удаления нет (инвариант 3).

Эхо проверяется меткой, как в P7: в запрос подставляется заведомо чужое базе буквенное значение
`ZZP8…`, в тексте ответа ищется сама метка.

_Отчёт пишется по ходу прогона; разделы ниже заполняются по мере получения фактов._

## 1. Справочник для приёмки

**Факт: `Catalog_Номенклатура` принимает элемент с одним полем `Description`; группу — нет.**

| Запрос | HTTP | Время | Результат |
|---|---|---|---|
| `POST Catalog_Номенклатура?$format=json` `{"Description": "<маркер> группа", "IsFolder": true}` | 500 | 11,0 с | отказ обработчика конфигурации, объект не создан |
| `POST Catalog_Номенклатура?$format=json` `{"Description": "<маркер> элемент"}` | 201 | 4,9 с | элемент создан, `Code` выдан автоматически (`УТ-00009311`) |

Текст отказа группы (код `-1`): «Ошибка при выполнении обработчика - 'ПриЗаписи'
{ОбщийМодуль.ОбщегоНазначения.Модуль(180)}: Неверный первый параметр Ссылка в функции
ОбщегоНазначения.ЗначенияРеквизитовОбъекта: Значение должно быть ссылкой или именем
предопределенного элемента.» — обработчик `ПриЗаписи` конфигурации ждёт заполненной ссылки,
которой у голой группы нет. Переданных значений в тексте нет. Поиск по маркеру после прогона
лишних объектов не нашёл — отказ в `ПриЗаписи` откатывает запись целиком.

Проверку заполнения (`ОбработкаПроверкиЗаполнения`) OData при записи не выполняет: элемент без
вида номенклатуры и единицы измерения записан. Реквизиты со значениями по умолчанию заполнились
(`ТипНоменклатуры = "Товар"`, `ВариантОформленияПродажи = "РеализацияТоваровУслуг"`).

## 4. PATCH: частичное тело, `DataVersion`, оптимистическая блокировка

Всё — на своём элементе `Catalog_Номенклатура`, `PATCH Catalog_Номенклатура(guid'…')?$format=json`.

- **Частичное тело принимается.** `{"Description": …}` → HTTP 200; по сравнению GET до и после
  изменились ровно `Description` и `DataVersion`, остальные 125 полей не тронуты.
- **Ответ PATCH — объект целиком** (127 полей, совпадает с последующим GET), HTTP 200, не 204.
- **`DataVersion` — счётчик записей**, 8 байт в base64: `AAAAAAAAAAA=` (0) после создания →
  `AAAAAAAAAAE=` (1) → … Растёт **на каждой записи, даже без изменения значения** (PATCH тем же
  `Description`: 1 → 2) и на пометке удаления.
- **Оптимистической блокировки у OData 1С нет.** Все варианты с устаревшей версией применены,
  HTTP 200:

  | Вариант | HTTP | Применено | `DataVersion` |
  |---|---|---|---|
  | `"DataVersion": "<устаревший>"` в теле | 200 | да | 2 → 3 |
  | заголовок `If-Match: <устаревший>` | 200 | да | 3 → 4 |
  | `If-Match: "<устаревший>"` | 200 | да | 4 → 5 |
  | `If-Match: W/"<устаревший>"` | 200 | да | 5 → 6 |
  | `If-Match: <текущий>` | 200 | да | 6 → 7 |

  Заголовка `ETag` нет ни в ответе GET, ни в ответе PATCH. Значит, отпечаток `DataVersion` в
  `commit` (задача 7, шаг 5) — единственная защита от записи поверх чужого изменения, и держит её
  сам шлюз: перечитать, сравнить, только потом PATCH. Окно между перечитыванием и PATCH остаётся —
  платформа его не закрывает.
- **Длина строки молча обрезается.** `Description` из 238 символов → HTTP 200, сохранено 100
  (предел реквизита), без ошибки и предупреждения.

## 5. Пометка удаления

**Факт: работает в обе стороны обычным PATCH.** `{"DeletionMark": true}` → HTTP 200 (2,8 с),
в GET `DeletionMark=True`; `{"DeletionMark": false}` → HTTP 200 (1,8 с), `DeletionMark=False`.
`DataVersion` растёт на каждом шаге (9 → 10 → 11). Ответ — объект целиком.

## 6. Ответ POST

**Факт: POST возвращает созданный объект целиком.** HTTP 201, в теле все 127 полей, включая
`Ref_Key`, `DataVersion` (`AAAAAAAAAAA=`), выданный `Code`, значения по умолчанию; сравнение с
последующим GET — расхождений нет. Заголовок `Location` — полный адрес объекта
(`…/Catalog_Номенклатура(guid'…')`). Для документа — то же: `Location` и объект с `Ref_Key`.

## 7. Ошибки записи и эхо

Метки — буквенные `ZZP8…` (метод P7). «Изменились поля» — сравнение GET до и после запроса.

| Форма | HTTP | Текст 1С | Эхо метки | Запись |
|---|---|---|---|---|
| строка в поле `Edm.Guid` (`Parent_Key`) | 400 | `[код 1] Не удалось разобрать строку '<значение>' как значение типа Edm.Guid!` | **да** | нет |
| строка в поле `Edm.Boolean` | 400 | `[код 1] Не удалось разобрать строку '<значение>' как значение типа Edm.Boolean!` | **да** | нет |
| строка в поле `Edm.Int64` (`СрокГодности`) | **200** | — | нет | **молча**: поле осталось `0`, выросла только `DataVersion` |
| массив в строковом поле | 500 | `[код -1] Произошла внутренняя ошибка OData сервиса…` | нет | нет |
| несуществующее поле | **200** | — | нет | **молча игнорируется**, выросла `DataVersion` |
| несуществующее поле рядом с настоящим | 200 | — | (значение настоящего поля — в теле успешного ответа) | настоящее поле записано, лишнее игнорируется |
| битый JSON | 500 | `[код -1] Непредвиденный символ при чтении JSON` | нет | нет |
| `Ref_Key` в теле PATCH | 200 | — | нет | игнорируется, ключ прежний |
| ссылка на несуществующий объект (`ЕдиницаИзмерения_Key`) | **200** | — | (в теле успешного ответа) | **записана «битая» ссылка** (возвращена обратно) |

**Отказ по правам не воспроизведён.** У пользователя публикации права на чтение всех 64
проверенных наборов, а менять права пользователя проба не может. Ближайший доступный аналог —
дата запрета изменения — отказа не дал: `POST Document_ОприходованиеИзлишковТоваров` датой
2026-03-02 (до общей даты запрета 2026-07-31), без организации → **HTTP 201**, объект создан (и
убран). Либо у пользователя публикации своя дата запрета, либо проверка БСП для непроведённого
документа без организации не срабатывает. Текст отказа по правам для задачи 2 остаётся
неизвестным — ожидать конкретную формулировку в коде нельзя.
