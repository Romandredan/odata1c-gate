# P8 — формы записи OData 1С на живой базе

**Дата:** 2026-09-12. **База:** `trade_dev` (УТ 11, платформа 8.3, публикация за IIS), роль `dev`,
владелец разрешил запись. **Зачем:** записи в OData 1С в проекте ещё не делал никто, а заглушка 1С
дважды оказывалась мягче настоящей платформы (пробел `+` в `$filter`, Job Object клиента). Задачи
5–7 плана M2 опираются на факты этой пробы: форма URL проведения, частичный PATCH, `DataVersion` и
оптимистическая блокировка, ответ POST, эхо переданного значения в ошибке записи.

**Метод:** прямые запросы `httpx` к публикации, без шлюза — поэтому проба ничего не пишет в словарь
`gate.sqlite` (в отличие от приёмки M1d). Кодирование — как у `Client1C`: путь через
`_экранировать_путь`, строка запроса через `_собрать_запрос` (пробел — `%20`), `$format=json` в
каждом запросе, тело ответа — UTF-8 из байтов. Учётные данные — из рабочего `bases.yaml`, в вывод и
отчёт не попадают. Скрипт: `tools/probes/p8_write_probe.py`.

Правила живой базы: проба меняет только созданные ею объекты — у каждого маркер
`odata1c-приёмка P8 2026-09-12` в `Description` (у документа — в `Комментарий`); существующие
объекты только читаются ради ссылок. Каждый созданный объект сразу пишется в журнал созданного;
уборка — `Unpost` проведённых, `DeletionMark=true` всем, плюс поиск по маркеру (`substringof`) на
случай объекта, которого нет в журнале. Физического удаления нет (инвариант 3).

Эхо проверяется меткой, как в P7: в запрос подставляется заведомо чужое базе буквенное значение
`ZZP8…`, в тексте ответа ищется сама метка.

## Что известно из `$metadata` до записи

Разбор сохранённого `$metadata` публикации (`tests/fixtures/edmx/probe.full.edmx`, 16,8 МБ):

- **Двух кандидатов плана в публикации нет:** `Catalog_ДополнительныеРеквизитыИСведения` и
  `Document_ВнутреннееПотреблениеТоваров`. Публикация OData выборочная (P4), и задача 10 не может
  опираться на них. Есть: `Catalog_Номенклатура` (127 полей, три табличные части),
  `Catalog_ВидыКонтактнойИнформации` (38), `Document_ПересчетТоваров` (24, без `Организация_Key`),
  `Document_ОприходованиеИзлишковТоваров` (27).
- **Действия документов** — элементы `FunctionImport` в `EntityContainer`: `Post` и `Unpost` по 296
  штук (по одному на опубликованный документ), у каждого `IsBindable="true"
  IsSideEffecting="true"`, параметры `bindingParameter` (тип документа) и
  `PostingModeOperational: Edm.Boolean`. Кроме них в публикации объявлены `SliceLast`/`SliceFirst`
  (849), `Turnovers` (121), `Balance`/`BalanceAndTurnovers` (81), `Start` (9, бизнес-процессы) и

Только чтение перед записью: права на чтение у пользователя публикации есть на всех 64 проверенных
наборах (63 — HTTP 200, один — HTTP 500 от СУБД «joins can have at most 32767 columns», не права).
Общая дата запрета изменения базы (`InformationRegister_ДатыЗапретаИзменения`) — 2026-07-31.

## 1. Справочник для приёмки

**Факт: `Catalog_Номенклатура` принимает элемент с одним полем `Description`; группу — нет.**

| Запрос | HTTP | Время | Результат |
|---|---|---|---|
| `POST Catalog_Номенклатура?$format=json` `{"Description": "<маркер> группа", "IsFolder": true}` | 500 | 11,0 с | отказ обработчика конфигурации, объект не создан |
| `POST Catalog_Номенклатура?$format=json` `{"Description": "<маркер> элемент <время>"}` | 201 | 4,9 с (повтор — 0,6 с) | элемент создан, `Code` выдан автоматически (`УТ-00009311`, `УТ-00009312`) |

Текст отказа группы (код `-1`): «Ошибка при выполнении обработчика - 'ПриЗаписи'
{ОбщийМодуль.ОбщегоНазначения.Модуль(180)}: Неверный первый параметр Ссылка в функции
ОбщегоНазначения.ЗначенияРеквизитовОбъекта: Значение должно быть ссылкой или именем
предопределенного элемента.» — обработчик `ПриЗаписи` конфигурации ждёт заполненной ссылки,
которой у голой группы нет. Переданных значений в тексте нет. Поиск по маркеру после прогона
лишних объектов не нашёл — отказ в `ПриЗаписи` откатывает запись целиком.

Проверку заполнения (`ОбработкаПроверкиЗаполнения`) OData при записи не выполняет: элемент без
вида номенклатуры и единицы измерения записан. Реквизиты со значениями по умолчанию заполнились
(`ТипНоменклатуры = "Товар"`, `ВариантОформленияПродажи = "РеализацияТоваровУслуг"`).

**Наименование номенклатуры уникально — в том числе среди помеченных на удаление.** Второй
прогон того же дня с тем же `Description` получил HTTP 500: «Ошибка при выполнении обработчика -
'ПередЗаписью' {Справочник.Номенклатура.МодульОбъекта(141)}: Значение поля "Рабочее
наименование" не уникально» (значения в тексте нет). Первый элемент к этому моменту был помечен на
удаление — проверка его всё равно видит. Скрипт добавляет к наименованию время прогона; приёмке
M2 нужно то же.

Для задачи 10 у справочника есть поле класса гейта: `Catalog_Номенклатура.см_НаименованиеКонтрагента`
(строка, класс `org` в `auto` политики `trade_dev`) — на нём проверяется сценарий 2 «изменить по
токену».

## 2. Документ для приёмки проведения

**Факт: `Document_ПересчетТоваров` создаётся одним полем `Комментарий` и проводится.**

| Запрос | HTTP | Время | Результат |
|---|---|---|---|
| `POST Document_ПересчетТоваров?$format=json` `{"Комментарий": "<маркер> минимум"}` | 201 | 0,4–1,0 с | `Date` — текущее время сервера, `Number` выдан (`УТ-00000218`, `УТ-00000220`), `Статус = "Выполнено"` |
| `POST Document_ПересчетТоваров(guid'…')/Post?$format=json` | 200 | 0,4–2,7 с | `Posted=True` — без склада и без строк товаров |
| `POST …` `{"Date": <сейчас>, "Склад_Key": <склад>, "Комментарий": …}`, затем `Post` | 201, 200 | 0,3 и 0,4 с | то же |

Склад взят ссылкой из последнего проведённого пересчёта базы (`3098a574-04bc-11f0-a7a3-fd74626404b7`,
только чтение). Проверку заполнения OData не выполняет и при проведении: документ без склада
проведён. Были ли движения по регистрам, проба не проверяла — у пересчёта с пустыми «Товарами»
их, по всей видимости, нет, и для приёмки это плюс: проведение и отмена не оставляют следов в
учёте. У документа нет `Организация_Key`, поэтому организационные даты запрета и учётная политика
его не касаются.

Запасной кандидат `Document_ОприходованиеИзлишковТоваров` создаётся полями `Date` и
`Комментарий` (HTTP 201, вопрос 7); проводить его не понадобилось.

## 3. Форма вызова действия (`Post` / `Unpost`)

**Факт: работают все проверенные формы, включая GET.** Один документ, формы подряд; «было → стало»
— чтение GET до и после. `DataVersion` — счётчик (см. вопрос 4).

| Запрос | HTTP | `Posted` | `DataVersion` |
|---|---|---|---|
| **`GET …/Unpost`** | 200 | **True → False** | 1 → 2 |
| `POST …/Unpost` (уже не проведён) | 200 | False → False | 2 → 3 |
| `POST …/Post` | 200 | False → True | 3 → 4 |
| `POST …/Unpost()` | 200 | True → False | 4 → 5 |
| `POST …/Post()` | 200 | False → True | 5 → 6 |
| `POST …/Unpost?PostingModeOperational=false` | 200 | True → False | 6 → 7 |
| `POST …/Post?PostingModeOperational=false` | 200 | False → True | 7 → 8 |
| `POST …/Unpost` | 200 | True → False | 8 → 9 |
| `POST …/Post?PostingModeOperational=true` | 200 | False → True | 9 → 10 |
| `POST …/Post(PostingModeOperational=false)` (уже проведён) | 200 | True → True | 10 → 11 |
| **`GET …/Post`** (уже проведён) | 200 | True → True | 11 → 12 |

Здесь `…` — `Document_ПересчетТоваров(guid'…')`, к каждому запросу добавлен `$format=json`.

- **Скобки не нужны, параметр не обязателен.** `…/Post` и `…/Post()` равнозначны;
  `PostingModeOperational` принимается и строкой запроса, и в скобках. Оперативное проведение
  (`true`) прошло — дата документа текущая.
- **Ответ — HTTP 200 с пустым телом**, из заголовков только `DataServiceVersion: 3.0`. Результат
  виден лишь повторным чтением `Posted`. `Client1C.post` пустое тело уже обрабатывает (возвращает
  `{}`).
- **Повтор не ошибка.** `Unpost` непроведённого и `Post` проведённого — HTTP 200, `DataVersion`
  растёт: второе — перепроведение.
- **GET выполняет действие.** `IsSideEffecting="true"` в `$metadata` публикация не соблюдает:
  `GET …/Unpost` отменил проведение, `GET …/Post` перепровёл документ. Последствия для шлюза —
  в разделе «Находка вне вопросов» ниже.

## 4. PATCH: частичное тело, `DataVersion`, оптимистическая блокировка

Всё — на своём элементе `Catalog_Номенклатура`, `PATCH Catalog_Номенклатура(guid'…')?$format=json`.

- **Частичное тело принимается.** `{"Description": …}` → HTTP 200; по сравнению GET до и после
  изменились ровно `Description` и `DataVersion`, остальные 125 полей не тронуты.
- **Ответ PATCH — объект целиком** (127 полей, совпадает с последующим GET), HTTP 200, не 204.
- **`DataVersion` — счётчик записей**, 8 байт в base64: `AAAAAAAAAAA=` (0) после создания →
  `AAAAAAAAAAE=` (1) → … Растёт **на каждой записи, даже без изменения значения** (PATCH тем же
  `Description`: 1 → 2) и на пометке удаления.
- **Оптимистической блокировки у OData 1С нет.** Все варианты с устаревшей версией применены,
  HTTP 200:

  | Вариант | HTTP | Применено | `DataVersion` |
  |---|---|---|---|
  | `"DataVersion": "<устаревший>"` в теле | 200 | да | 2 → 3 |
  | заголовок `If-Match: <устаревший>` | 200 | да | 3 → 4 |
  | `If-Match: "<устаревший>"` | 200 | да | 4 → 5 |
  | `If-Match: W/"<устаревший>"` | 200 | да | 5 → 6 |
  | `If-Match: <текущий>` | 200 | да | 6 → 7 |

  Заголовка `ETag` нет ни в ответе GET, ни в ответе PATCH. Значит, отпечаток `DataVersion` в
  `commit` (задача 7, шаг 5) — единственная защита от записи поверх чужого изменения, и держит её
  сам шлюз: перечитать, сравнить, только потом PATCH. Окно между перечитыванием и PATCH остаётся —
  платформа его не закрывает.
- **Длина строки молча обрезается.** `Description` из 238 символов → HTTP 200, сохранено 100
  (предел реквизита), без ошибки и предупреждения. В `$metadata` публикации атрибута `MaxLength`
  нет, то есть заранее шлюз предел не знает.

**PATCH проведённого документа** (`Document_ПересчетТоваров`, проведён):

| Тело PATCH | HTTP | `Posted` после | Вывод |
|---|---|---|---|
| `{"Комментарий": …}` | 200 | True | документ остаётся проведённым |
| `{"Posted": false}` | 200 | **False** | **PATCH поля `Posted` отменяет проведение** |
| `{"Posted": true}` | 200 | **True** | **и проводит** — то же, что действие `Post` |

## 5. Пометка удаления

**Факт: работает в обе стороны обычным PATCH.** `{"DeletionMark": true}` → HTTP 200 (2,8 с),
в GET `DeletionMark=True`; `{"DeletionMark": false}` → HTTP 200 (1,8 с), `DeletionMark=False`.
`DataVersion` растёт на каждом шаге (9 → 10 → 11). Ответ — объект целиком.

**На документе порядок обязателен.**

| Запрос | HTTP | Текст 1С |
|---|---|---|
| `PATCH {"DeletionMark": true}` проведённого документа | 500 | `[код -1] Проведенный документ не может быть помечен на удаление!` |
| `POST …/Unpost`, затем `PATCH {"DeletionMark": true}` | 200, 200 | помечен |
| `POST …/Post` помеченного на удаление | 500 | `[код -1] Помеченный на удаление документ не может быть проведен!` |

Платформа не снимает проведение сама, как при интерактивной пометке, а отказывает.

## 6. Ответ POST

**Факт: POST возвращает созданный объект целиком.** HTTP 201, в теле все 127 полей, включая
`Ref_Key`, `DataVersion` (`AAAAAAAAAAA=`), выданный `Code`, значения по умолчанию; сравнение с
последующим GET — расхождений нет. Заголовок `Location` — полный адрес объекта
(`…/Catalog_Номенклатура(guid'…')`). Для документа — то же: `Location` и объект с `Ref_Key`.

## 7. Ошибки записи и эхо

Метки — буквенные `ZZP8…` (метод P7). «Изменились поля» — сравнение GET до и после запроса.

| Форма | HTTP | Текст 1С | Эхо метки | Запись |
|---|---|---|---|---|
| строка в поле `Edm.Guid` (`Parent_Key`) | 400 | `[код 1] Не удалось разобрать строку '<значение>' как значение типа Edm.Guid!` | **да** | нет |
| строка в поле `Edm.Boolean` | 400 | `[код 1] Не удалось разобрать строку '<значение>' как значение типа Edm.Boolean!` | **да** | нет |
| строка в поле `Edm.Int64` (`СрокГодности`) | **200** | — | нет | **молча**: поле осталось `0`, выросла только `DataVersion` |
| массив в строковом поле | 500 | `[код -1] Произошла внутренняя ошибка OData сервиса…` | нет | нет |
| несуществующее поле | **200** | — | нет | **молча игнорируется**, выросла `DataVersion` |
| несуществующее поле рядом с настоящим | 200 | — | (значение настоящего поля — в теле успешного ответа) | настоящее поле записано, лишнее игнорируется |
| битый JSON | 500 | `[код -1] Непредвиденный символ при чтении JSON` | нет | нет |
| `Ref_Key` в теле PATCH | 200 | — | нет | игнорируется, ключ прежний |
| ссылка на несуществующий объект (`ЕдиницаИзмерения_Key`) | **200** | — | (в теле успешного ответа) | **записана «битая» ссылка** (возвращена обратно) |

**Отказ по правам не воспроизведён.** У пользователя публикации права на чтение всех 64
проверенных наборов, а менять права пользователя проба не может. Ближайший доступный аналог —
дата запрета изменения — отказа не дал: `POST Document_ОприходованиеИзлишковТоваров` датой
2026-03-02 (до общей даты запрета 2026-07-31), без организации → **HTTP 201**, объект создан (и
убран). Либо у пользователя публикации своя дата запрета, либо проверка БСП для непроведённого
документа без организации не срабатывает. Текст отказа по правам для задачи 2 остаётся
неизвестным — ожидать конкретную формулировку в коде нельзя.

**Выводы по эху.** Эхо в ошибке записи есть — ровно в форме разбора значения: «Не удалось
разобрать строку '<значение>' как значение типа Edm.Guid|Edm.Boolean!» (HTTP 400, код `1`). Это
та же природа, что в P7 (строковый ключ, число в `$filter`): платформа повторяет то, что не
смогла разобрать. Бизнес-ошибки конфигурации (`ПриЗаписи`, `ПередЗаписью`, пометка и проведение)
приходят HTTP 500 с кодом `-1`, путём модуля и номером строки; в проверенных случаях значений в
них нет, но текст пишет конфигурация, и гарантии нет никакой. Кроме того, **успешный ответ POST и
PATCH — объект целиком, то есть все реальные значения записанного объекта**: ранний проход гейта
нужен и телу успешного ответа записи, а не только тексту ошибки.

## Находка вне вопросов: GET вызывает действие, и `raw_get` это пропускает

Факт пробы (вопрос 3): `GET Document_X(guid'…')/Unpost` отменяет проведение, `GET …/Post` проводит
— публикация 1С исполняет действие независимо от метода. Шлюз уже сейчас, на этапе M1 (чтение),
пропускает такой путь через тул чтения: `odata1c_raw_get(path="Document_X(guid'…')/Post")`.
`_проверить_путь` (`src/odata1c/tools/service.py`) запрещает `..`, `?`, `%`, `$metadata`,
`$value`, но не сегменты действий; `_цель_пути` считает `Post` неразрешённым хвостом и включает
строгую маску — а запрос уходит.

Проверено временным юнит-тестом на `respx` (в коммит не входит): `сервис.raw_get(…,
path="Document_РеализацияТоваровУслуг(guid'…')/Post")` отправляет ровно один
`GET …/Document_РеализацияТоваровУслуг(guid'…')/Post?$format=json`; тул возвращает `internal`
(пустое тело не разбирается как JSON), но на живой базе документ к этому моменту уже проведён.

Последствия: проведение и отмена проведения **мимо двухфазной записи** (инвариант 2), мимо
`write: false` базы, флага `post_documents` и роли `prod`; то же, по всей видимости, для `Start`
бизнес-процессов и `ExecuteTask` задач (не проверялось). Лечение — в `_проверить_путь`: отказ,
если сегмент пути (без скобок) — имя действия с `side_effecting` из индекса, а при неразрешённом
пути — любое из известных имён действий (`Post`, `Unpost`, `Start`, `ExecuteTask`). Это дефект
закрытого этапа M1, а не задача P8; вынесено оркестратору.

## Выводы для задач 5–7 и 10

**Задача 5 (`update`, `mark_for_deletion`).**

1. Частичный PATCH работает — решение 8 плана (в теле только изменённые поля) реализуемо как есть.
2. **Проверка полей по индексу обязательна, а не вежлива:** несуществующее поле и `Ref_Key` 1С
   молча игнорирует и отвечает 200 — без проверки модель получила бы «успех», не записав ничего.
3. **В перечень запрещённых для `update` полей добавить `Posted`** (к `Ref_Key`, `DataVersion`,
   `Predefined`, `PredefinedDataName`): `PATCH {"Posted": true|false}` проводит и отменяет
   проведение — это обход `post_documents` и тула `action`. По той же логике `DeletionMark` в
   `update` должен отклоняться с подсказкой на `mark_for_deletion` — иначе обходится флаг
   `mark_deletion`.
4. Тип и длину значения 1С не проверяет сама: строка в поле `Edm.Int64` принимается без записи,
   лишняя длина обрезается молча (предела в `$metadata` нет), ссылка на несуществующий объект
   записывается. Что можно — проверять по индексу при подготовке (тип `Edm.*`, формат GUID);
   остальное покажет только перечитывание в `commit` (задача 7).
5. `mark_for_deletion` на проведённом документе: 1С отказывает HTTP 500. Подготовка должна видеть
   `Posted=true` в текущем состоянии и отказывать с подсказкой «сначала `Unpost`», а не молча
   отменять проведение.

**Задача 6 (`create`, `action`).**

1. **Форма URL действия — `POST <Document_X>(guid'<ref>')/Post`** (и `/Unpost`), без скобок и без
   параметров; `PostingModeOperational` — необязательный параметр строки запроса. Ответ — HTTP 200
   с пустым телом; итог — повторным чтением `Posted`.
2. Повторное проведение не ошибка (перепроведение, `DataVersion` растёт) — предупреждение
   «повторное проведение» в превью оправдано. `Unpost` непроведённого — тоже 200.
3. `Post` помеченного на удаление — HTTP 500; подготовка может отказать заранее по `DeletionMark`.
4. `create`: POST → HTTP 201, объект целиком с `Ref_Key`, `DataVersion`, выданным кодом/номером и
   `Location`. `Ref_Key` для журнала берётся из ответа; `Date` документа, если не задана, ставит
   1С (время сервера).
5. Перечень действий для `action_unknown` — `FunctionImport` с `bindingParameter` типа сущности
   (у документов — ровно `Post`, `Unpost`).

**Задача 7 (`commit`).**

1. **Оптимистической блокировки у OData 1С нет** — ни `DataVersion` в теле, ни `If-Match` (любой
   формы) не мешают записи поверх, `ETag` не отдаётся. Отпечаток `DataVersion` в `commit` —
   единственная защита, и держит её шлюз. Между перечитыванием и PATCH остаётся окно, которое
   закрыть нечем; в журнале стоит писать `DataVersion` «до» и «после», чтобы чужая запись в окне
   была видна по разрыву счётчика.
2. `DataVersion` — счётчик записей (8 байт, base64), растёт на **любой** записи: PATCH без
   изменения значения, пометка удаления, `Post`, `Unpost`. Подготовленный `update` устаревает
   (`pending_stale`) после любого проведения объекта — это верное поведение, а не ложная тревога.
3. Ранний проход гейта обязателен для тела **успешного** ответа POST/PATCH (объект целиком с
   реальными значениями) и для текста ошибки (эхо «Не удалось разобрать строку '…'»).
4. После выполнения — перечитывание и сравнение с отправленным: обрезка длины и молчаливо
   отброшенное значение видны только так. Расхождение стоит показать модели предупреждением.
5. Ошибки конфигурации приходят HTTP 500 с кодом `-1` и путём модуля — `odata_error` с текстом
   после раннего прохода.

**Задача 10 (приёмка M2).**

- Справочник — **`Catalog_Номенклатура`, элемент** с одним `Description`, уникальным на прогон
  (маркер + время): наименование уникально и среди помеченных. Поле класса гейта для сценария 2
  — `см_НаименованиеКонтрагента` (`org`).
- Документ — **`Document_ПересчетТоваров`** с одним `Комментарий` (маркер); `Post`/`Unpost`
  переключают `Posted`, организации у документа нет.
- Уборка: `Unpost`, затем `DeletionMark=true` — в обратном порядке 1С откажет.
- Время: первая запись после простоя — до 11 с, дальше 0,3–0,7 с на запрос.
- Сценарий «отказ по правам» воспроизвести на `trade_dev` нечем — у пользователя публикации
  полные права; для задачи 2 это значит, что текст отказа 1С по правам остаётся неизвестным.
