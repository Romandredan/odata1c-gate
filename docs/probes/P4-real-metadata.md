# P4 — поведение реального `$metadata` 1С

Дата: 2026-09-10. Отвечает на SPEC §15, проверка 3.

## Условия

- База: `TradeDev` — Управление торговлей (УТ) с доработками, база разработки; публикация
  `https://1c.example.local/TradeDev/odata/standard.odata/` за IIS 10.
- Проба: `tools/probes/p4_metadata_probe.py` (учётные данные из рабочего `bases.yaml`, не из
  репозитория); образец для тестов собирает `tools/probes/p4_trim_fixture.py`.
- Записи в базу не было: `DELETE` проверялся по заведомо несуществующему ключу.

## Ответ

Интерфейс OData ведёт себя так, как описано в SPEC §9, с одним исключением: сеанс `IBSession`
этой публикацией не поддерживается. Модель описания в SPEC §4.2 расходится с фактом в четырёх
местах, и индекс метаданных (план M1b) на реальной базе строится неверно. Всё это воспроизводится
на образце `tests/fixtures/edmx/ut-real.edmx`.

## Факты

### Описание

| Показатель | Значение |
|---|---|
| размер `$metadata` | 16,8 МБ, загрузка 23 с |
| `DataServiceVersion` | 3.0 |
| `EntityType` / `EntitySet` | 4237 / 4237 |
| `ComplexType` | 1701 (строки наборов записей `_RowType`, результаты виртуальных таблиц) |
| `EnumType` | 1007 |
| `FunctionImport` | 2584 |
| `Association` / `NavigationProperty` | 9358 / 9358; `AssociationSet` нет |

Виды по префиксу: `Document` 1109, `Constant` 995, `Catalog` 904, `InformationRegister` 877,
`AccumulationRegister` 242, `ExchangePlan` 57, `ChartOfCharacteristicTypes` 23,
`BusinessProcess` 16, `DocumentJournal` 11, `Task` 3. Перечисления наборами не публикуются —
только как `EnumType`.

### Виртуальные таблицы — действия, а не наборы

Ни один `EntitySet` не оканчивается на суффикс виртуальной таблицы. Виртуальные таблицы объявлены
как `FunctionImport` с `IsBindable="true"`, `IsSideEffecting="false"`; привязку к регистру задаёт
тип параметра `bindingParameter`, а не атрибут `EntitySet` (его у действий 1С нет вовсе):

| Действие | Кол-во | Параметры | Результат |
|---|---|---|---|
| `SliceLast`, `SliceFirst` | 849 / 849 | `Condition`, `Period` | тип записи регистра |
| `Balance` | 81 | `Condition`, `Dimensions`, `Period` | `Collection(<регистр>_Balance)` — `ComplexType` |
| `Turnovers` | 121 | `Condition`, `Dimensions`, `StartPeriod`, `EndPeriod` | `…_Turnover` |
| `BalanceAndTurnovers` | 81 | те же | `…_BalanceAndTurnover` |
| `Post`, `Unpost` | 296 / 296 | `PostingModeOperational` | — (`IsSideEffecting="true"`) |
| `Start` | 9 | `RoutePoint` | — |
| `ExecuteTask` | 2 | — | — |

Вызов: `AccumulationRegister_X/Balance(Period=datetime'…')`. У регистра оборотов `Balance()`
отвечает `400`, код 6 «Метод не найден» — набор действий регистра определяется только описанием.
Время на базе разработки: `Balance` на дату — 12,5 с; `Turnovers` за месяц — 3,5 с, с `Condition`
— 0,5 с; `Turnovers()` без параметров — 24,6 с (`$top=1` не сокращает расчёт); `SliceLast` — 0,1 с.

### Ключи

- Справочник, документ, бизнес-процесс, задача: `Ref_Key` (`Edm.Guid`); табличная часть и
  `_RecordType` регистра накопления — плюс `LineNumber` (`Edm.Int64`).
- Регистр, подчинённый регистратору, публикуется двумя наборами: `InformationRegister_X` — набор
  записей с ключом `Recorder` + `Recorder_Type` (несколько типов регистратора) или `Recorder_Key`
  (один тип); `InformationRegister_X_RecordType` — отдельные записи. У части подчинённых регистров
  сведений ключ `_RecordType` **не содержит** `Recorder` (`СтоимостьТоваров_RecordType`: `Period` и
  измерения).
- Независимый регистр сведений — один набор, ключ из измерений (+ `Period` у периодического), до
  25 полей; составные измерения — парой `Поле` + `Поле_Type`.
- Константа: `SurrogateKey` (`Edm.Int16`). Журнал документов: `Ref` + `Ref_Type`.
- Формат составного ключа в URL подтверждён:
  `InformationRegister_X(БанковскийСчет_Key=guid'…')` → `404`, код 9 «Экземпляр сущности не найден».

### Составные поля

Поле составного типа — `Edm.String` с парным `Поле_Type`, а не `Edm.Guid`. Значение ссылки
приходит строкой GUID, в `_Type` — имя набора (`StandardODATA.Catalog_Контрагенты`); для
примитивного типа в поле само значение. Поле-перечисление — тоже `Edm.String` без ссылки на
`EnumType`; связь восстанавливается только по имени (`ХозяйственнаяОперация` ↔
`ХозяйственныеОперации`).

### Имена

В именах объектов встречаются подчёркивания и цифры: `InformationRegister_см_ОчередьДействий`,
`Constant_SbSh_…`, `ExchangePlan_Удалить_ОбменУправлениеТорговлей_11_0_РозничнаяТорговля_1_0`.
Отделить имя объекта от табличной части по `_` нельзя.

### Запросы

| Проверка | Результат |
|---|---|
| `$inlinecount=allpages` | `200`, `"odata.count": "1103"` — **строка**, не число |
| `allowedOnly=true` | `200`, параметр принят |
| без `$format` | Atom XML — `$format=json` обязателен |
| `substringof` в `$filter` | `200` |
| `$expand` глубиной 1–4 | `200`; раскрытие только если навигационное поле есть в `$select` (`Контрагент/Description`), иначе связь молча не раскрывается |
| синтаксическая ошибка `$filter` | `400`, код 14 «Ошибка при разборе опции запроса $filter» |
| неизвестное поле в `$select` | `400`, код 6 «Сегмент пути НетТакогоПоля не найден!» — текст ошибки повторяет ввод |
| `DELETE` записи независимого регистра по несуществующему ключу | `404`, код 9 — метод принят и дошёл до поиска записи |
| `IBSession: start` | ни заголовка, ни cookie сеанса в ответ: публикация сеансы не переиспользует |
| Basic-аутентификация с логином кириллицей | только UTF-8; в cp1251 — IIS `401.5` |
| первый запрос после простоя | больше 30 с (подъём сеанса 1С), дальше 0,1–2 с |

Полный цикл «создать запись независимого регистра → удалить» не выполнялся: это запись в базу
владельца. Отказа от метода нет, остаток проверки — интеграционный тест записи в M2.

## Индекс на реальной базе (`odata1c reindex trade_dev`)

Индекс строится за 35 с вместе с загрузкой; повтор отвечает «без изменений». Ошибки:

1. **Действий 0 из 2584.** Разбор ищет привязку в атрибуте `EntitySet`, у действий 1С его нет —
   все действия отбрасываются: нет `Post`/`Unpost` для записи M2 и нет виртуальных таблиц.
2. **Виртуальных таблиц 0.** Суффиксов в именах наборов нет (см. выше); поля результатов лежат в
   `ComplexType`, который разбор не читает.
3. **379 ложных табличных частей.** `parse_entity_name` делит имя по `_`:
   `InformationRegister_см_ОчередьДействий` становится табличной частью несуществующего
   `InformationRegister_см`; `_RecordType` регистров тоже помечен табличной частью.
4. **21 подчинённый регистр помечен независимым** — это открывает им `delete_record`, нарушение
   инварианта 3. Причины: регистратор ищется только как `Recorder` (нет `Recorder_Key`), а набор
   `_RecordType` оценивается сам по себе, без родительского набора.
5. **Составные поля не распознаны как ссылки.** Признак ссылки — только `Edm.Guid`; поле
   `Контрагент` + `Контрагент_Type` (`Edm.String`) получает `is_ref=0` и авто-класс `org` — гейт
   заменил бы GUID ссылки токеном названия.
6. **Номер документа классифицирован как счёт:** `НомерСчетаФактуры…` → `acc` (23 поля `acc`, из них
   большая часть — номера счетов-фактур). Нарушение инварианта 6.
7. **Перечисления не индексируются** — модели неоткуда взять допустимые значения для `$filter`.

## Решения

- SPEC §4.2 — поправка: виртуальные таблицы и действия — привязанные `FunctionImport`; табличная
  часть — набор, чьё имя продолжает имя другого набора; регистратор — `Recorder` или
  `Recorder_Key`; независимость регистра — по основному набору.
- SPEC §9 — поправка: `IBSession` необязателен (клиент работает и без cookie сеанса); форма вызова
  виртуальных таблиц; `$expand` требует навигационное поле в `$select`; `odata.count` — строка;
  составные поля.
- SPEC §10 — глубина `$expand` 2 оставлена как лимит продукта (платформа принимает 4).
- Исправления индекса и правил полей — отдельный план `M1b-fix`, до M1d: слой тулов строится на
  индексе.
