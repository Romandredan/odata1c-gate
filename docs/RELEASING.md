# Порядок выпуска

Пользователь получает шлюз по двум каналам, и выпуск — это момент, когда оба начинают указывать на
одну и ту же версию:

- **дистрибутив `odata1c-gate` на PyPI** — код шлюза; его публикует `.github/workflows/publish.yml`
  по тегу `v<версия>`;
- **плагин из маркетплейса** — навыки, хук, агент и `plugin/.mcp.json`, который запускает
  `uvx --from odata1c-gate==<версия>`. Маркетплейс отдаёт плагин из **ветки по умолчанию**
  репозитория на GitHub, без закрепления на тег.

Отсюда два правила, на которых держится весь порядок ниже.

1. **Ветка по умолчанию — `main`, и `main` двигается только выпусками.** Любой коммит в `main`
   немедленно доходит до всех, кто обновляет плагин. Разработка идёт в рабочей ветке `dev`: задачи
   ответвляются от неё и в неё же сливаются. Между выпусками `dev` живёт с версией
   `X.Y.Z.devN` во всех четырёх местах поставки, и эта версия на PyPI не публикуется.
2. **`main` двигается только после того, как версия появилась на PyPI.** Плагин закрепляет точную
   версию дистрибутива; если `main` уже указывает на неё, а PyPI ещё нет, `uvx` у пользователя не
   находит пакет и шлюз не стартует.


## Нумерация

Номер отвечает на вопрос: **что меняется для того, кто уже пользуется шлюзом**. Пользователей у
шлюза двое, и у каждого свой договор со шлюзом:

- **владелец** — файлы настроек `bases.yaml`, `daemon.yaml`, `policy.yaml`, домашний каталог,
  команды `odata1c`;
- **модель** — тулы MCP, их параметры, поля ответа и коды ошибок, формат токенов, рецепты.

Гейт отдельной осью нумерации не является: он входит в оба договора — в то, что модель видит в
ответе тула, и в политику, которую настраивает владелец.

| Часть | Когда меняется |
|---|---|
| MAJOR | ломающее изменение договора (см. ниже) — после выхода `1.0` |
| MINOR | новая возможность в прежнем договоре: тул, операция записи, навык, команда CLI, класс гейта, раздел настроек с умолчанием, набор рецептов; до `1.0` — также ломающее изменение |
| PATCH | исправление в прежнем договоре: ошибка, утечка значения, которое гейт должен был закрывать и раньше, документация, зависимости |

**Ломающее изменение** — то, после которого перестаёт работать то, что работало, и нужно что-то
поправить:

- у владельца — схема файлов настроек без умолчания для нового поля, расположение домашнего
  каталога, переименование или удаление команды CLI либо её ключа;
- у модели — переименование или удаление тула, параметра, поля ответа, кода ошибки; смена формата
  токена или схемы его вычисления (токены в сохранённых рецептах и заметках перестанут совпадать).

Пока версия `0.x`, семантическое версионирование разрешает ломать договор в MINOR: так и делаем,
а раздел «Ломающие изменения» в описании выпуска говорит, что именно поправить.

## Чеклист

1. Работа влита в рабочую ветку, непрерывная проверка зелёная на Windows и Ubuntu.
2. Выбрать номер по таблице выше. Дальше он записан как `X.Y.Z`.
3. Раздел в [CHANGELOG.md](../CHANGELOG.md): `## X.Y.Z — ГГГГ-ММ-ДД`, подразделы Keep a Changelog
   (`Added`, `Changed`, `Fixed`, `Removed`), ссылки на отчёты приёмки в `docs/probes/`.
4. Переписать версию в четырёх местах поставки разом:

   ```text
   uv run python tools/bump_version.py X.Y.Z
   ```

   Меняются `src/odata1c/__about__.py`, `plugin/.claude-plugin/plugin.json`, `plugin/.mcp.json`
   (пин `odata1c-gate==X.Y.Z`) и `.claude-plugin/marketplace.json`.
5. Прогнать локально:

   ```text
   uv run pytest -q                # включая test_versions_agree: все четыре версии равны
   uv run ruff check .
   uv run ruff format --check .
   claude plugin validate plugin/
   ```

   Если выпуск меняет гейт, запись или навыки — прогнать приёмку на живой базе, затронутую
   выпуском (скрипты `tools/probes/`, отчёты `docs/probes/`), и evals плагина
   (`plugin/evals/README.md`). Результат приёмки называется в описании выпуска одной строкой.
6. Коммит на рабочей ветке: `release: X.Y.Z`. Тег на этот коммит: `git tag vX.Y.Z`.
7. Отправить **рабочую ветку и тег, но не `main`**:

   ```text
   git push origin dev vX.Y.Z
   ```

   Тег запускает `publish.yml`: сборка, публикация на PyPI, выпуск на GitHub с колесом и sdist.
8. Дождаться зелёного `publish` и убедиться, что версия на PyPI есть:

   ```text
   gh run watch
   curl -s -o /dev/null -w '%{http_code}\n' https://pypi.org/pypi/odata1c-gate/X.Y.Z/json    # 200, не 404
   ```

   Не прошла публикация — `main` не трогать: пользователи остаются на прежнем выпуске, чинить и
   выпускать следующий номер (см. «Откат»).
9. Только теперь сдвинуть `main` на коммит выпуска и проверить ветку по умолчанию:

   ```text
   git push origin vX.Y.Z^{commit}:main
   gh repo view --json defaultBranchRef -q .defaultBranchRef.name    # должно быть main
   ```

10. Описание выпуска на GitHub. `publish.yml` создаёт выпуск с автоматическим перечнем коммитов;
    заменить его текстом по шаблону ниже:

    ```text
    gh release edit vX.Y.Z --notes-file release-notes.md
    ```

11. Проверить установку так, как её получит пользователь:

    ```text
    claude plugin marketplace update odata1c-gate
    claude plugin update odata1c@odata1c-gate
    claude mcp list                        # plugin:odata1c:gate … ==X.Y.Z … Connected
    uv tool install odata1c-gate@latest    # командная строка владельца
    odata1c daemon stop                    # следующий лаунчер поднимет демон новой версии
    odata1c doctor                         # строка «демон» — OK, версия X.Y.Z
    ```

    `uv tool upgrade` не поднимает версию, если командная строка ставилась с точным пином; тогда
    нужен `install …@latest`. На Windows установка падает с «файл занят другим процессом», пока
    работают лаунчеры открытых сессий Claude Code: закрыть сессии или остановить процессы
    `odata1c.exe` из каталога `uv\tools`.
12. Вернуть рабочую ветку на следующую версию разработки:

    ```text
    uv run python tools/bump_version.py X.Y.(Z+1).dev0
    git commit -am "chore: рабочая ветка на X.Y.(Z+1).dev0"
    ```

13. Обновить статус выпуска в [AGENTS.md](../AGENTS.md), если выпуск закрывает этап или меняет
    описанное там поведение.

## Шаблон описания

Читатель — тот, кто поставил плагин, а не его автор. Описание отвечает на три вопроса: что
изменилось в работе с 1С, изменилось ли то, что видит модель, и нужно ли что-то делать. Устройство
тестов, ход рассуждений и промежуточные варианты остаются в коммитах, планах и отчётах приёмки.

Правила языка:

1. **Вступление говорит, что изменилось для пользователя**, а раздел «Новое» — как теперь выглядит
   его путь: что он просит, что делает модель, где он подтверждает.
2. **Термин проекта поясняется при первом упоминании** или заменяется описанием того, что
   происходит («токен — замена реального значения, которую видит модель»). Словарь — `CONTEXT.md`.
3. **Одна мысль на предложение, связная речь.** Перечень из трёх и более пунктов — списком.
4. **Пути, команды и поля настроек остаются, только если пользователь их вводит или правит.**
   Имена внутренних функций, номера решений (Ruling) и хеши коммитов в описание не попадают.

Номер версии в текст не пишется: он уже стоит в заголовке выпуска.

```markdown
<Одно-два предложения: что изменилось для пользователя, меняется ли то, что видит модель, нужны
ли действия.>

## Новое

**<Что появилось, одной фразой.>** <Путь пользователя: что он просит или делает, что происходит в
ответ, где подтверждает; где это включается.>

## Исправлено

**<Симптом, как его видел пользователь.>** <Причина, последствие, что сделано, чем подтверждено.>

## Проверено

<Приёмка на живой базе: что прогонялось и с каким итогом, одной-двумя строками.>

## Совместимость

| | |
|---|---|
| Гейт открывает | <«ничего» либо что теперь уходит модели открытым> |
| Ломающие изменения | <«нет» либо перечень> |
| Действия после обновления | <перезапуск демона `odata1c daemon stop` — всегда; плюс правки `bases.yaml` / `policy.yaml`, реиндекс, если нужны> |
| Python / Claude Code | <«без изменений» либо минимальные версии> |
```

Разделы «Новое», «Исправлено» и «Проверено» опускаются, если им нечего сказать. Таблица
«Совместимость» есть в каждом выпуске, все четыре строки заполнены; «нет» и «ничего» пишутся явно.
Если значение не помещается в ячейку — «см. ниже» и одноимённый подраздел `###` под таблицей.

Строка «Гейт открывает» называет всё, что после обновления уходит модели открытым, хотя прежде
закрывалось: новое умолчание, пересмотренный класс поля, поле, выведенное из политики. Номер от
этого не зависит — это раскрытие, а не нумерация: владелец, у которого на гейте держится
допуск модели к базе, должен узнать о таком изменении из описания выпуска, а не из ответа тула.

## Откат

Пока тег не отправлен, он снимается локально: `git tag -d vX.Y.Z`.

Отправленный тег, чья публикация на PyPI не прошла, — удалить тег (`git push origin :vX.Y.Z`),
починить и выпустить заново: `main` не двигался, пользователи этого не заметили.

Версия, опубликованная на PyPI, неизменна: номер нельзя выпустить повторно даже после удаления.
Неисправный выпуск помечается на pypi.org как отозванный (yank) — `uvx` с точным пином его всё ещё
поставит, а новые установки без пина обойдут, — и выпускается следующий PATCH. Если `main` уже
указывает на неисправный выпуск, его сдвигает следующий выпуск, а не откат `main` назад: тем, кто
уже обновил плагин, откат не поможет, а понижает ли Claude Code версию плагина при обновлении, не
проверено.

## Что в выпуск не кладётся

Рабочие `bases.yaml` и `daemon.yaml`, словарь `gate.sqlite`, журнал `journal.sqlite`, полные
выгрузки `$metadata` (`*.full.edmx`), выводы проб с данными баз — их закрывает `.gitignore`, но
перед тегом стоит посмотреть `git status` и состав sdist (`uv build`, затем список файлов архива).
В репозиторий и в выпуск идут только шаблоны `*.example.yaml`.
