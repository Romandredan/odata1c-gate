# Планы реализации odata1c-gate

Планы пишутся по [SPEC.md](../../SPEC.md) v0.2 и разбиты по поставляемым частям, а не по
ярлыкам этапов из SPEC §13: каждый план заканчивается работающим и проверяемым куском, задачи
внутри плана не ссылаются на интерфейсы, которых ещё нет.

Порядок исполнения: M0 → M1a → (M1b и задачи 1–8 M1c параллельно) → задача 9 M1c → M1b-fix → M1d → M2 → M3 → M3b.
M1b-fix появился после пробы P4 (2026-09-10): реальный `$metadata` 1С устроен иначе, чем
предполагала синтетика, на которой писались M1b и M1c.
M1b и M1c не зависят ни от живой базы 1С, ни от открытых вопросов SPEC §15 — это единственные
части, которые пишутся полностью до любых внешних ответов. Оговорка про параллельность одна:
задача 9 плана M1c (политика при реиндексе) правит функцию, написанную задачей 5 плана M1b, и
поэтому идёт после неё; задачи 1–8 M1c от M1b не зависят вовсе.

Что осталось за границами планов M1a–M1c и уходит в M1d, чтобы исполнитель не искал этого зря:
построение запросов к 1С — `$top` и его предел, глубина `$expand` с автоматическим `$select` на
раскрытых сущностях, `allowedOnly`, формы URL составных ключей и виртуальных таблиц (SPEC §9).
Класс `Client1C` из задачи 5 плана M1a — только транспорт: соединение, сеанс, семафор, повторы и
перевод ошибок. Складывать из параметров тула путь и строку запроса будет слой тулов.

## Правило синхронизации

Если проба или задача даёт результат, меняющий принятое решение, порядок действий по
[CLAUDE.md](../../CLAUDE.md): новый ADR в [docs/adr/](../adr/) (нумерация с 0015) или поправка
существующего (`amended`) → правка затронутого раздела `SPEC.md` → правка `AGENTS.md`, если задет
описанный там раздел. Молча расходиться документам нельзя.

## Как исполнять план

Каждый план — файл с задачами и шагами-флажками (`- [ ]`). Исполнение: скилл
`superpowers:subagent-driven-development` (свежий субагент на задачу с ревью между задачами) либо
`superpowers:executing-plans` (пакетно в текущей сессии с контрольными точками).
