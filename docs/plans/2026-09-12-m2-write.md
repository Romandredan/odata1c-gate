# M2 — запись в 1С: изменение, проведение, пометка удаления, создание

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** модель в Claude Code меняет данные базы 1С — изменяет реквизит, проводит и отменяет
проведение документа, ставит и снимает пометку удаления, создаёт объект, — причём каждое изменение
проходит через превью в токенах, явное подтверждение пользователя, журнал и может быть откачено.

**Architecture:** двухфазная запись (SPEC §7.3): пишущие тулы (`create`, `update`,
`mark_for_deletion`, `action`, `undo`) в 1С ничего не отправляют — проверяют разрешения, читают
текущее состояние, раскрывают токены через гейт, строят превью в токенах и кладут pending-операцию
в хранилище демона (TTL 10 мин, привязка к MCP-сессии, отпечаток `DataVersion`). Выполняет её только
`odata1c_commit` после подтверждения механизмом клиента (ADR-0012): у Claude Code — диалог
разрешения через `_meta["anthropic/requiresUserInteraction"]`, у клиентов с elicitation — запрос
демона. Выполнение пишет «до» и «после» в `journal.sqlite` (реальные значения, файл локальный);
модель видит результат только через гейт. Логика записи — пакет `src/odata1c/write/`, тулы — тонкие
обёртки в `daemon.py`, как у чтения.

**Tech Stack:** Python 3.12, `mcp` 2.2 (`MCPServer`, `Context`, `_meta` тула, `elicit_form`),
`httpx` (клиент 1С), SQLite WAL (журнал), `pytest`, `respx`.

**Spec:** `SPEC.md` §7 (протокол записи: 7.1 разрешения, 7.2 подтверждение по клиенту, 7.3
двухфазность, 7.5 журнал, 7.6 откат), §5 (тулы записи, §5.2 коды ошибок), §3.2 (роли и лимит
коммитов), `docs/adr/0012-write-confirmation-by-client-capabilities.md`; инварианты 2–4 `AGENTS.md`.
Факты о записи 1С — проба P8 (задача 1 этого плана).

**Зависит от:** этап M1 (read) закрыт; **раунд блокеров M2** (`.superpowers/sdd/2026-09-10-m1d-mcp-surface/task-m2-blockers.md`)
принят ревью — он даёт контракт гейта для записи (раздел «Контракт гейта» ниже). Задачи 5–7 без
него не стартуют.

## Global Constraints

- Язык комментариев, docstring, сообщений коммитов, текстов ошибок и подсказок — русский;
  идентификаторы — как в коде. Код документируется в манере проекта: почему принято решение, а не
  только что делает строка.
- **Инвариант 1**: реальные значения защищаемых классов не выходят через MCP никогда — ни в превью,
  ни в ответе `commit`, ни в `journal`, ни в ошибке 1С на запись, ни в elicitation-сообщении. Превью
  строится в токенах. Реальные значения живут только внутри демона (тело запроса к 1С, pending-операция
  в памяти) и в `journal.sqlite` на диске владельца.
- **Инвариант 2**: пишущие тулы ничего не отправляют в 1С — только готовят pending-операцию;
  выполнение — только `odata1c_commit` после подтверждения. `commit` идемпотентен по `pending_id`.
- **Инвариант 3**: нет `PUT`; физического удаления объектов нет — только пометка удаления.
  `odata1c_delete_record` (удаление записей независимых регистров) в этот план не входит.
- **Инвариант 4**: разрешения проверяются до создания pending-операции в строгом порядке SPEC §7.1.
- **Инвариант 5**: один токен — одно значение. Неоднозначный токен при записи — отказ
  `token_ambiguous`, а не молчаливый выбор написания.
- **Инвариант 6**: суммы, количества, даты, GUID, коды, номера документов не защищаются и в превью
  показываются как есть.
- Каждое обращение к 1С на запись и каждое чтение состояния для записи идёт с ранним проходом гейта
  (`scrub=`), как чтение: ошибка 1С на запись повторяет значение (проба P7).
- Ошибка тула — текст с JSON `{"error": {"code", "message", "hint"}}` (SPEC §5.2), не исключение.
  Тулы — `structured_output=False`, сериализация — `ensure_ascii=False`.
- Каждый ответ пишущего тула несёт роль базы (`role`, SPEC §3.2) и имя базы.
- **Живая база**: пишем в `trade_dev` (владелец разрешил, база разработки). Приёмка и пробы
  **изменяют только объекты, созданные ими самими**, с маркером `odata1c-приёмка` в наименовании или
  комментарии, и откатывают их. Существующие документы и справочники не трогаются. Учётные данные
  читаются из `~/.claude/odata1c/bases.yaml` и никуда не выводятся; реальные значения защищаемых
  классов в вывод, отчёты и тесты не печатаются — только формы. Демон владельца на порту 7171 не
  останавливается: свои демоны — на временном домашнем каталоге.
- Команды: `uv run pytest -q`, `uv run ruff check .`, `uv run ruff format --check .` — чисто перед
  каждым коммитом; коммит заканчивается строкой `Co-Authored-By:` исполнителя.

## Контракт гейта для записи (от раунда блокеров M2)

**Раунд блокеров исполнен 2026-09-12.** Авторитетный контракт — раздел 1 «Интерфейс для M2» его
отчёта (`.superpowers/sdd/2026-09-10-m1d-mcp-surface/task-m2-blockers-report.md`): там порядок вызовов
в одном пишущем туле (1.1), лестница разрешения токена при записи (1.2) и обязательные правила (1.5).
Исполнители задач 5–9 читают этот раздел целиком. Два правила, которые легче всего нарушить:

- **Маскировать один раз и никогда повторно.** Токен, пришедший в маскировщик как данные, считается
  строкой из базы и получает свой токен (`lit`). Превью строится маской **сырого** `current` и **сырого**
  тела, каждое по одному разу; замаскированное обратно в `mask` не подаётся.
- **`current` передаётся в `inbound_write` как пришло** из `client.get(..., scrub=gate.scrubber(revealed))` —
  гейт сам разворачивает переписанные ранним проходом строки. Если в поле уже лежит значение токена,
  подставляется оно дословно (иначе запись молча сотрёт, например, краевой пробел). Пишущий тул
  вызывает `inbound_write`, а не `Unmasker.body`.

```python
# src/odata1c/gate/pipeline.py
BaseGate.inbound_write(data: dict, *, entity: str, shape: Shape,
                       current: dict | None, revealed: RevealedValues) -> dict
# Тело PATCH/POST: токены → реальные значения. current — текущее состояние объекта с реальными
# значениями (update) или None (create). Токен с одним написанием → оно; с несколькими и одно из них
# лежит в current[поле] → оно; иначе GateError("token_ambiguous"). Классовые и анти-оракульные
# правила — те же, что у inbound_value.

# src/odata1c/client1c/client.py
Client1C.post(path: str, json: dict, *, scrub: Scrub | None = None) -> dict
Client1C.patch(path: str, json: dict, *, scrub: Scrub | None = None) -> dict
Client1C.delete(path: str, *, scrub: Scrub | None = None) -> None

# Сторож: BaseGate.finish отказывает (internal, без значения), если в конверте есть ScrubbedText.
```

Остальное из гейта — как в M1: `BaseGate.mask(...)`, `finish(...)`, `scrubber(revealed)`,
`inbound_key(...)`, `is_hidden(...)`, `is_protected(entity, field, shape=, strict=)`,
`RevealedValues`, `ToolService._run(...)` — общая точка входа (создаёт набор раскрытого на вызов).

## Решения, принятые планом (и поправки SPEC, которые вносит исполнитель)

1. **`odata1c_delete_record` не входит** — владелец не выбрал эту операцию для первой поставки.
   `independent_register_delete` в разрешениях остаётся, тула нет. Запись в «Вне плана».
2. **Запрет записи поля — только `deny_fields` базы** (`bases.yaml`). Упомянутый в SPEC §7.1
   «`write: deny` из политики» в коде не существует; второй механизм того же запрета не вводим.
   Поправка SPEC §7.1 — задача 2.
3. **Pending-операции хранятся в памяти демона.** Перезапуск демона их теряет — это безопасно (TTL
   10 мин, подготовка повторяется дёшево) и проще, чем файл с реальными значениями ещё в одном месте.
   Журнал — `journal.sqlite` в домашнем каталоге, персистентный.
4. **Чужая сессия и несуществующий `pending_id` — один код `pending_unknown`.** Иначе ответ сообщал
   бы, что у другой сессии есть операция с таким номером. Новый код — поправка SPEC §5.2, задача 2.
5. **Ключ сессии** — `ctx.headers["mcp-session-id"]` (устойчив, проверено в M1d). Без заголовка
   (тесты в памяти) — `local:{id(ctx.session)}`: реальный клиент через лаунчер всегда идёт по HTTP и
   заголовок имеет.
6. **Механизм подтверждения выбирается на сессию** (ADR-0012) по `clientInfo.name` и
   `capabilities.elicitation` первого пишущего вызова и запоминается. Как SDK 2.2 отдаёт эти поля
   серверу — проверяется исполнением в задаче 9 (опора — пробы P2, P3).
7. **Лимит коммитов** — скользящее окно 10 минут на сессию, предел по роли (§3.2: `prod` 20,
   `test` 50, `dev` без лимита), считается в `commit`, не в подготовке.
8. **Превью `update` — только изменённые поля**, «было → станет», оба значения в токенах; неизменное
   поле в теле PATCH не отправляется (1С не получает лишнего, откат точнее).
9. **Откат — сам pending-операция** и проходит `commit` с подтверждением (§7.6).
11. **`update` не принимает `Posted` и `DeletionMark`** (факт P8): для них есть свои операции
    со своими флагами (`action` — `post_documents`, `mark_for_deletion` — `mark_deletion`); через
    `update` оба флага обходились бы. Отказ `params_invalid` с подсказкой на нужный тул.
12. **Отказы 1С, которые можно предвидеть, ловятся при подготовке**: пометка удаления проведённого
    документа — «сначала Unpost»; проведение помеченного — «сначала снимите пометку». Иначе модель
    получит 500 от 1С уже на `commit`, после подтверждения пользователя.
10. **Новые коды ошибок** (задача 2, поправка SPEC §5.2): `pending_unknown`, `token_ambiguous`
    (от блокеров), `undo_unsupported` (уже упомянут в §7.6, в перечень §5.2 не внесён),
    `action_unknown` — действие не объявлено в `$metadata` сущности.

## Факты пробы P8 (задача 1 исполнена 2026-09-12) — обязательны для задач 5–7 и 10

Отчёт — `docs/probes/P8-write-forms.md`, раздел «Выводы для задач 5–7 и 10». Коротко:

- **Оптимистической блокировки у OData 1С нет**: ни `DataVersion` в теле, ни `If-Match` не мешают
  записи поверх чужого изменения, `ETag` 1С не отдаёт. Отпечаток `DataVersion` в `commit` —
  единственная защита, её держит шлюз (задача 7). `DataVersion` — счётчик, растёт на **любой**
  записи, включая `Post`, `Unpost`, пометку удаления. В журнал писать `DataVersion` «до» и «после».
- **1С молча принимает недопустимое**: несуществующее поле и `Ref_Key` в теле — 200 без записи;
  строка в `Edm.Int64` — без записи; лишняя длина обрезается; ссылка на несуществующий объект
  записывается. Проверка полей и типов по индексу при подготовке — обязательна, а не вежлива.
- **`PATCH {"Posted": …}` проводит и распроводит**, `PATCH {"DeletionMark": …}` ставит пометку —
  через `update` это обход флагов `post_documents` и `mark_deletion` (задача 5, решение 11).
- **Действие**: `POST <Document_X>(guid'<ref>')/Post` (и `/Unpost`), без скобок и параметров; ответ
  200 с пустым телом, итог — перечитыванием `Posted`. Повторное проведение не ошибка.
- **Отказы 1С**: пометка удаления проведённого документа — 500 (сначала `Unpost`); проведение
  помеченного — 500. Подготовка должна отказывать заранее с подсказкой, а не ловить 500.
- **`create`**: POST → 201, объект целиком (`Ref_Key`, `DataVersion`, код или номер) и `Location`.
- **Эхо**: ошибка записи повторяет переданное значение («Не удалось разобрать строку '<значение>'
  как значение типа Edm.Guid») — ранний проход на теле ошибки записи обязателен (контракт гейта).
- **Для приёмки** (задача 10): справочник — `Catalog_Номенклатура`, элемент с одним `Description`
  (наименование уникально, в том числе среди помеченных — включать время прогона); поле класса гейта
  для сценария «изменить по токену» — `Catalog_Номенклатура.см_НаименованиеКонтрагента`; документ —
  `Document_ПересчетТоваров` с одним `Комментарий` (дату и номер ставит 1С, проводится без склада
  и товаров).
- **Отдельно найдено и исправлено до M2**: 1С выполняет `Post`/`Unpost`/`Start`/`ExecuteTask` и
  по запросу GET — `raw_get` проводил документ в обход записи (коммит `4d9f567`, два слоя запрета).

  подтверждения — поле `"warning"` в ответе; при `commit` отката — обычный путь.
- Откат `update` берёт **реальные** значения из `before_json` — без токенов и без `inbound_write`:
  значение пришло из самой базы и не проходило через модель.
- После успешного `commit` отката — `journal.mark_undone(исходный, undone_by=новый)`.
- Откат недоступен для чужой базы вне области видимости сессии (`base_unknown`).

`journal`: `Journal.recent` → каждая запись через маску своей сущности (`before`, `after`, `request`
— токены), плюс `status`, `op`, `committed_at`, `undone_by`; через `gate.finish`.

Тесты: откат каждой операции из таблицы; `undo` откаченного → `undo_unsupported`; объект изменён
после коммита → `warning`; журнал от класса данных — ни одного реального значения фикстуры в тексте;
журнал другой базы вне области видимости — не виден.

- [ ] **Step 1–4** — тесты, FAIL, реализация, PASS.

что выбрала проба P8.

Сценарии:
1. **Создать** элемент справочника → превью в токенах → `commit` → объект есть в 1С (проверка GET).
2. **Найти → изменить по токену → перечитать**: найти созданный объект, изменить поле класса гейта
   (если у выбранного справочника такого поля нет — изменить `Description`, класс `org`/`person`
   по политике) значением-токеном, взятым из другого объекта; перечитать — в 1С реальное значение
   того объекта, в ответе модели — тот же токен.
3. **Пометка удаления** и её снятие.
4. **Документ**: создать → `Post` → проверить `Posted` → `Unpost`.
5. **Откат** каждой операции через `undo` → объект вернулся к состоянию «до» (сверка GET с
   `before_json` журнала).
6. **Отказы**: `write: false` на копии базы → `base_read_only` без обращения к 1С; поле из
   `deny_fields` → `field_write_denied`; изменённый в 1С объект между подготовкой и `commit` →
   `pending_stale`; клиент без elicitation → `write_unsupported_client`.
7. **От класса данных к полям** (урок M1d): все ответы пишущих тулов, `commit`, `journal`, `undo` и
   ошибки собираются, и в их тексте ищется **каждое реальное значение защищаемых классов**, какое
   приёмка знает (ИНН, КПП, названия, ФИО, телефоны, адреса затронутых объектов, прочитанные
   напрямую `httpx`), — не только в полях, помеченных защищаемыми. Ноль вхождений.
8. **Уборка**: всем созданным объектам `DeletionMark=true`, проведённые — `Unpost`; в отчёте —
   список созданного и подтверждение.

Подтверждение **диалогом Claude Code** (`requiresUserInteraction`) скриптом не проверить — владелец
проверяет руками: инструкция в отчёте (один `update` на объекте приёмки в своей сессии Claude Code,
диалог разрешения появляется на `commit`, отказ в диалоге — операция не выполнена).
