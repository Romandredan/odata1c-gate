# Точки управления владельца: `bases.yaml` на машину, `policy.yaml` на базу (проектная записка к ADR-0015)

Статус: черновик к обсуждению, решение не принято. Код, SPEC и CONTEXT не менялись.
Редакция 2 (2026-09-14): по решению владельца правила гейта остаются в отдельном файле политики
базы; переноса в `bases.yaml` и миграции нет. Добавлен конструктор политики.

Цель: владелец знает два файла. В `bases.yaml` он описывает базу и решает, как с ней работать:
сколько ждать, что можно писать, скрывать ли. В `policy.yaml` базы он решает, что именно скрывать и
что открыть. Оба файла самодокументированы, правки действуют сразу, правила в политику добавляет
конструктор, а не ручная правка по инструкции.

## 1. Три яруса настроек

| Ярус | Файл | Кто и когда открывает | Что там |
|---|---|---|---|
| 1. Решения владельца | `bases.yaml` (на машину) | При добавлении базы и когда хочет изменить её поведение | Реквизиты, роль, соединение, запись и разрешения, уровень гейта, путь к рецептам, база по умолчанию |
| 1. Решения владельца | `bases/<база>/policy.yaml` (на базу) | Когда авторазметка ошиблась или нужно закрыть своё | Что скрыть целиком, что открыть, какому полю какой класс, свои классы, у кого скрывать названия, искать ли в тексте |
| 2. Техника машины | `daemon.yaml` | Редко: порт занят, ответы велики, Claude Code под другим именем | Порт, лимиты ответа, срок жизни подготовленной операции, период сверки индекса, запасной механизм подтверждения, образы Claude Code |
| 3. Не трогать | `gate_secret`, `launcher.key`, `bases/<база>/policy.auto.yaml`, `gate.sqlite`, `journal.sqlite`, индекс, `daemon.pid`, `logs/` | Никогда вручную | Секреты, состояние, авторазметка |

Сегодня ярус 1 нарушен в одном месте: `policy.yaml` наполовину пишет реиндекс, и при каждой
перезаписи файла через YAML комментарии владельца стираются (SPEC §4.3). Самодокументированный
шаблон в таком файле жить не может. Отсюда разделение на `policy.yaml` владельца и
`policy.auto.yaml` машины.

## 2. Целевой вид записи базы в `bases.yaml`

Правило шаблона прежнее (SPEC §3.1): у каждого параметра комментарий с назначением и допустимыми
значениями; совпадающее с умолчанием роли закомментировано, но видно. От нынешнего шаблона
отличается тремя вещами: раздел `gate` сведён к `mode` со ссылкой на файл политики; ключи
`names_for` и `scan_free_text` ушли в политику; заголовок обещает действие без перезапуска.

```yaml
# odata1c: все базы 1С этой машины. Файл закрыт правами текущего пользователя ОС.
# Пароли открытым текстом (SPEC §3.4) либо `password: keyring`.
# Правки действуют сразу: демон перечитывает файл при изменении. Перезапуск не нужен.
# Что именно скрывает гейт в базе: bases/<имя>/policy.yaml (создаётся командой base add).

default: ut                          # база по умолчанию, если тул вызван без `base`

bases:
  ut:                                # имя базы: [a-z0-9_]{1,32}; это значение параметра `base` в тулах

    # --- кто это ---
    label: УТ 11, боевая, розница и опт   # подпись для модели: по ней она выбирает базу
    url: https://1c.corp.local/ut/odata/standard.odata/   # оканчивается на /odata/standard.odata/
    user: odata_claude               # пользователь ИБ 1С; лучше отдельная учётка с урезанными правами
    password: "…"                    # пароль ИБ; `keyring` = взять из хранилища ОС
    role: prod                       # prod | test | dev: профиль умолчаний (SPEC §3.2); любое поле ниже его перекрывает

    # --- соединение: сколько ждать ---
    # timeout_s: 60                  # ожидание ответа 1С на один запрос, чтение и запись
    # virtual_timeout_s: 180         # то же для виртуальных таблиц (остатки, обороты)
    # concurrency: 2                 # одновременных запросов к базе от всех сессий
    # verify_tls: true               # true | false | путь к CA-сертификату (PEM)
    # ib_session: true               # держать сеанс 1С между запросами

    # --- запись: что можно менять (умолчание роли prod: write: false) ---
    # write: false                   # пишущие тулы; commit всегда с подтверждением клиента
    # permissions:
    #   post_documents: true         # проведение и отмена проведения
    #   mark_deletion: true          # пометка на удаление
    #   allow_entities: []           # если не пусто: писать только сюда
    #   deny_entities: []            # сюда не писать, например [Catalog_Пользователи]
    #   deny_fields: []              # эти поля не пишутся ни одним тулом, например [Catalog_Контрагенты.ИНН]
    #   commit_limit: 20             # коммитов за 10 минут на сессию; 0 = без лимита

    # --- гейт: скрывать ли (умолчание роли prod: identifiers+names) ---
    # gate:
    #   mode: identifiers+names      # off | identifiers | identifiers+names (SPEC §6.2)
    #                                # что именно скрывать и что открыть: bases/ut/policy.yaml

    # --- рецепты ---
    # recipes: bases/ut/recipes.yaml # готовые запросы; создаётся из шаблона (base add --recipes ut)
```

## 3. Целевой вид `bases/<база>/policy.yaml`

Файл владельца. Создаётся при `base add` из шаблона, машиной не переписывается. Формат разделов
прежний (SPEC §6.9), поэтому существующие политики остаются пригодными; новое здесь: перечень
классов в шапке, примеры в каждом разделе, `names_for` и `scan_free_text` живут только здесь.

```yaml
# odata1c: политика гейта базы ut. Здесь владелец решает, ЧТО скрывать и что открыть.
# Скрывать ли вообще, задаёт bases.yaml → gate.mode; этот файл действует на уровнях identifiers
# и identifiers+names. Реиндекс его не переписывает; правки действуют сразу.
# Что машина отнесла к защищаемому сама: policy.auto.yaml рядом (не редактировать, пересобирается
# реиндексом). Итог по базе: odata1c policy show ut. Проверить этот файл: odata1c policy check ut.
# Добавить правило командой: odata1c policy hide | open | set | custom (см. odata1c policy --help).
version: 2

# Классы (SPEC §6.4). Класс назначается полю в fields или своему классу в custom.
#   inn      ИНН                          kpp    КПП                    ogrn   ОГРН, ОГРНИП
#   acc      расчётный, лицевой, казначейский счёт                      corr   корр. счёт (по умолчанию открыт)
#   bic      БИК (по умолчанию открыт)    iban   IBAN                   card   номер карты
#   snils    СНИЛС                        doc    паспорт, удостоверение: серия, номер, кем выдан
#   phone    телефон                      email  электронная почта      dob    дата рождения
#   addr     адрес                        org    название организации   person ФИО
#   custom:<имя>   свой класс из раздела custom
#   keep     оставить открытым
#   scan     значение целиком не скрывать, но реквизиты и названия в нём искать

scan_free_text: true        # искать реквизиты и известные названия в любом тексте ответа:
                            # комментарии, назначения платежей, XML внутри строк, ошибки 1С

# names_for:                # у каких справочников скрывать Description и ФИО (уровень identifiers+names).
#   - Catalog_Контрагенты   # Без раздела: все справочники организаций и людей, найденные в индексе;
#   - Catalog_Организации   # список печатает odata1c policy show ut.

defaults:                   # переключатель целого класса, для всех полей базы
  corr: keep                # корреспондентские счета банков открыты
  bic: keep                 # БИК открыты
  # addr:
  #   mask_for:             # адреса скрывать ещё и у этих справочников,
  #     - Catalog_Партнеры  # в дополнение к справочникам людей из авторазметки

entities: {}                # сущности, которых модель не видит вовсе:
# entities:                 # вместе с табличными частями, наборами записей и виртуальными таблицами
#   Catalog_ФизическиеЛица: { hide: true }

fields: {}                  # поле: класс. Главнее всего остального.
# fields:
#   Catalog_Контрагенты.КодПоОКПО: keep                    # авторазметка ошиблась: открыть
#   Document_ПлатежноеПоручение.НазначениеПлатежа: scan     # текст оставить, реквизиты в нём искать
#   Catalog_Контрагенты.ДопИдентификатор: inn               # авторазметка пропустила: закрыть как ИНН
#   Catalog_Сотрудники.ТабельныйНомер: custom:tab_number    # свой класс

custom: {}                  # свои классы: по имени поля в любой сущности и/или по виду значения
# custom:
#   tab_number:
#     fields: [ТабельныйНомер]   # поля с таким именем в любой сущности
#     regex: '\d{6}'             # и такие значения в любом тексте, если scan_free_text
```

## 4. Как собирается действующая политика

```text
bases/<база>/policy.auto.yaml       пишет только реиндекс: классы полей по индексу (SPEC §6.4, §6.5),
                                    справочники людей для адресов (Ruling 36)
bases/<база>/policy.yaml            пишет только владелец (руками или конструктором)
bases.yaml → bases.<база>.gate.mode уровень: что из собранного применяется (SPEC §6.2)
действующая политика (в памяти)   = правила владельца поверх авторазметки, суженные уровнем
приоритет                           fields > custom > defaults > авторазметка (как сегодня, SPEC §6.9)
```

- Реиндекс перестаёт беречь ручные разделы, потому что больше не касается файла владельца: он
  переписывает `policy.auto.yaml` целиком. Раздел `auto` из существующего `policy.yaml` он уносит
  туда при первом реиндексе новой версии, ручные разделы оставляет на месте. Владелец ничего не
  делает. Сравнение «старая авторазметка против новой» для списка «на проверку» (SPEC §4.3,
  находка П1) сохраняется.
- `names_for` для авторазметки реиндекс читает из `policy.yaml`; раздела нет, значит все
  справочники организаций и людей из встроенного списка (`DEFAULT_NAMES_FOR`).
- `odata1c policy show <база>` печатает действующую политику с источником каждой строки:
  `владелец` или `авто`, и список сущностей, у которых скрываются названия. Ресурс
  `odata1c://policy/{base}` отдаёт то же, с фильтрацией скрытых имён (Ruling 29).
- `hide` распространяется на дочерние объекты через индекс (Ruling 30), как сегодня.

## 5. Конструктор политики

Рядовой владелец не должен учить формат по SPEC. Путь: сказать, что хочется, получить правило.

**Команды CLI** (пишут в `policy.yaml` с сохранением комментариев, для этого нужен обратимый разбор
YAML, `ruamel.yaml`):

```text
odata1c policy show <база>                       действующая политика с источником строк
odata1c policy check <база>                      проверка файла по индексу: неизвестные сущности и поля,
                                                 неизвестные классы, битые regex, противоречия
                                                 (поле и keep, и hide), сколько полей затронет каждое правило
odata1c policy hide <база> <Сущность>            entities.<Сущность>.hide: true
odata1c policy open <база> <Сущность.Поле>       fields.<…>: keep
odata1c policy set  <база> <Сущность.Поле> <класс>   fields.<…>: <класс>, класс из перечня или custom:<имя>
odata1c policy custom <база> <имя> [--fields A,B] [--regex '…']   свой класс
odata1c policy copy <из> <в>                     политика второй базы той же конфигурации
```

Каждая команда после записи выполняет `check` и печатает, что изменилось: «поле … теперь открыто»,
«скрыто 14 сущностей: справочник и его табличные части». Неизвестное имя сущности или поля по
индексу отклоняется до записи с подсказкой ближайших имён из `find_entity`.

**Навык плагина `odata1c-policy`** ведёт владельца в диалоге с моделью:

1. Что нужно: скрыть, открыть, закрыть своё.
2. Найти сущность и поле тулами чтения (`odata1c_find_entity`, `odata1c_describe_entity`: там же
   видно, какой класс поле имеет сейчас и откуда он взялся).
3. Показать, что стоит за правилом: для «открыть» — что именно станет видно, для «скрыть» — какие
   дочерние объекты уйдут вместе с сущностью.
4. Дать одну команду CLI и попросить владельца выполнить её в терминале.
5. После выполнения проверить контрольным запросом через тул, что поведение изменилось.

Модель тула для изменения политики не получает: данные 1С могут подтолкнуть её открыть поле,
а команду в терминале выполняет человек, как `reveal`. Тема `odata1c_info("policy")` объясняет
классы и разделы модели теми же словами, что шаблон владельцу.

## 6. Перечитывание `bases.yaml` без перезапуска

| Событие | Поведение |
|---|---|
| Файл изменился (mtime или размер) | Перед вызовом тула демон разбирает файл заново и проверяет целиком, как при старте |
| Файл не разбирается или не проходит проверку | Все тулы отвечают `config_invalid` с путём и строкой, без значений из файла, пока владелец не починит. Прежняя конфигурация не используется: закрыть базу владелец мог как раз этой правкой |
| Изменились адрес, учётка, таймауты, `concurrency`, `verify_tls` | Пул соединений базы пересоздаётся на следующем запросе; начатые запросы доходят на старом |
| Изменились `write`, `permissions` | Действуют на следующий пишущий вызов. `commit` перепроверяет разрешения по текущему файлу: подготовлено при разрешённой записи, а к моменту `commit` запрещено, значит `permission_denied`, операция снята |
| Изменился `gate.mode` или `policy.yaml` | Действует на следующий вызов. В ответ добавляется строка `warnings`: «политика гейта изменилась», без имён полей, как при пересборке авторазметки реиндексом |
| Изменился `default`, добавлена или удалена база | Действует на следующий вызов; удалённая база даёт `base_unknown` |
| `daemon.yaml` | Как сегодня: только при старте демона. Порт и секрет на ходу не сменить |

Стоимость: один `stat` на вызов тула, разбор 7 КБ YAML при изменении.

## 7. Сценарии для проверки границ

1. Владелец правит `bases.yaml` в редакторе, сохраняет наполовину: следующий вызов тула получает
   `config_invalid`, модель говорит владельцу, что файл не читается; после сохранения всё работает.
2. Сессия подготовила `update` при `write: true`; владелец ставит `write: false`; `commit`
   отвечает `permission_denied`, в 1С ничего не уходит, операция снята.
3. Реиндекс нашёл новый справочник людей: он попадает в авторазметку; правило владельца
   `fields: {Catalog_X.Поле: keep}` по-прежнему главнее.
4. Владелец поднимает уровень базы с `identifiers` до `identifiers+names` посреди сессии: названия
   в следующих ответах приходят токенами, в `warnings` строка о смене политики.
5. `policy open ut Catalog_Контрагенты.КодПоОКПО` на файле с комментариями шаблона: правило
   дописано в `fields`, ни один комментарий не потерян, `check` проходит.
6. `policy hide ut Document_РеализацияТоваровУслуг` печатает список дочерних объектов, которые
   уйдут вместе с документом (табличные части, наборы записей), и просит подтвердить.
7. После обновления шлюза у базы `policy.yaml` с разделом `auto` и ручным `entities`: первый
   реиндекс уносит `auto` в `policy.auto.yaml`, `entities` остаётся, скрытая сущность не открывается
   ни на один вызов между обновлением и реиндексом.
8. В `bases.yaml` остался `gate.names_for` старого формата: загрузка отклоняет файл с сообщением,
   куда ключ переехал.

## 8. Что меняется синхронно при принятии ADR-0015

- SPEC §2.3 (состав каталога базы), §3.1 (шаблон `bases.yaml`), §3.5 (команды `policy`), §4.3
  (шаг 3 реиндекса), §6.5 (`names_for` в политике), §6.9 (шаблон политики, два файла, конструктор).
- `CONTEXT.md`: **Политика** становится действующим набором правил гейта базы (правила владельца из
  `policy.yaml` поверх авторазметки), а не файлом; новый термин **Авторазметка** (`policy.auto.yaml`:
  классы полей и умолчания, вычисленные реиндексом; _Avoid_: автополитика, auto-секция);
  **Конструктор политики** (команды `odata1c policy …` и навык, которыми владелец меняет политику;
  _Avoid_: редактор политики, мастер).
- `AGENTS.md`: раздел «Запуск и подключение» (перезапуск демона после правки `bases.yaml` больше не
  нужен; `base add` создаёт политику; правило про `defaults.addr.mask_for`), раздел про плагин.
- Код: модель `GateSettings` (только `mode`), `Policy` (чтение `names_for`, `scan_free_text` из
  политики), реиндекс (`policy.auto.yaml`, перенос `auto`), сборка действующей политики из двух
  источников, перечитывание `bases.yaml`, команды `policy check | hide | open | set | custom | copy`
  на `ruamel.yaml`, тема `info("policy")`, навык `plugin/skills/odata1c-policy/SKILL.md`, тесты на
  сценарии §7.
