# Установка и сопровождение odata1c-gate

Документ доводит машину от пустого места до работающего шлюза и разбирает сбои, с которыми
установка сталкивается чаще всего. Что такое шлюз и что он защищает — [README.md](../README.md).

Читатель — владелец машины: он описывает базы 1С, знает их пароли и может раскрывать токены.
Модель ничего из описанного здесь не делает и файлов домашнего каталога шлюза не касается.

## Что именно ставится

Два разных предмета, и путать их не нужно:

| Что | Чем ставится | Зачем |
|---|---|---|
| плагин Claude Code `odata1c` | `claude plugin install` | MCP-сервер шлюза в сессии, навыки, хук, агент |
| командная строка `odata1c` | `uv tool install odata1c-gate` | описать базу, собрать индекс, политика гейта, `reveal`, `doctor` |

Плагин закрепляет версию пакета в `plugin/.mcp.json` и запускает шлюз через `uvx`, поэтому сам
пакет отдельно ставить не обязательно — командная строка нужна владельцу для того, что модель не
делает. Обе части берут пакет `odata1c-gate` с PyPI; пакет Python и команда называются `odata1c`.

## Windows

1. **`uv`.** Установщик — по инструкции <https://docs.astral.sh/uv/getting-started/installation/>.
   Отдельно ставить Python не нужно: `uv` скачает подходящий сам. Проверка — `uv --version`.
2. **Claude Code.** Нужна версия не ниже 2.1.267 (плагины, `claude plugin validate|eval`,
   диалог разрешения по `_meta`). Проверка — `claude --version`.
3. **Плагин.**

   ```text
   claude plugin marketplace add Romandredan/odata1c-gate
   claude plugin install odata1c@odata1c-gate
   ```

4. **Командная строка.**

   ```text
   uv tool install odata1c-gate
   ```

   Если после этого `odata1c` не находится, `uv tool update-shell` допишет каталог утилит `uv` в
   `PATH` (нужен новый сеанс терминала). Без установки те же команды запускаются как
   `uvx --from odata1c-gate odata1c <команда>`.
5. **Домашний каталог и база.**

   ```text
   odata1c init
   odata1c base add ut_test --role test --recipes ut
   odata1c base test ut_test
   odata1c reindex ut_test
   odata1c doctor
   ```

   Порядок важен: `init` идёт первым, потому что домашнего каталога до него нет, а `doctor`
   последним — на пустом месте он честно ответит `FAIL` в строке домашнего каталога.
   Установка плагина домашнего каталога не создаёт: его делают `init` или лаунчер при первой
   сессии Claude Code.

   `init` создаёт `%USERPROFILE%\.claude\odata1c\` с шаблонами `bases.yaml` и `daemon.yaml` и
   закрывает их правами текущего пользователя через `icacls`. Другой домашний каталог — ключ
   `--home <путь>` у любой команды или переменная окружения `ODATA1C_HOME`.

   `base add <имя> --role prod|test|dev [--gate <уровень>] [--recipes ut|bp|zup]` спрашивает
   четыре вещи подряд:

   - адрес публикации 1С — тот же, по которому открывается веб-клиент, например
     `https://server/base`; окончание `/odata/standard.odata/` шлюз допишет сам, язык веб-клиента
     (`/ru_RU/`) отрежет;
   - подпись базы для модели — по ней она выбирает базу среди нескольких;
   - пользователя 1С (заводится отдельный, с правами только на нужное чтение, например
     `odata_user`);
   - пароль — вводится в терминале, на экране не отображается.

   Роль (`--role`) задаёт умолчания записи: `prod` — уровень гейта `identifiers+names` и только
   чтение, `test` — уровень `identifiers`, `dev` — гейт выключен (`off`) и запись разрешена;
   явно указанное поле перекрывает умолчание роли. Уровень гейта задаётся для каждой базы
   отдельно: `--gate off|identifiers|identifiers+names` пишет его в запись базы вместо умолчания
   роли (например, тестовая база с записью, но с названиями и ФИО токенами — `--role test --gate
   identifiers+names`). `--recipes ut|bp|zup` кладёт в базу шаблон
   готовых запросов той конфигурации — без него файл рецептов остаётся пустым.

   Поля уже описанной базы — подпись, роль, разрешение записи, уровень гейта, разрешения на
   проведение, пометку удаления и удаление записей регистров, лимит коммитов — меняет
   `odata1c base set <имя> …` без правки файла руками: комментарии файла сохраняются, значения
   проверяются, демон подхватывает изменение без перезапуска. То же умеет модель в Claude Code
   (навык `odata1c-base`); команду, снижающую защиту, она выполняет после вашего согласия, и
   Claude Code спросит подтверждение. Ключи всех команд `odata1c` пишутся полностью: сокращения
   (`--rol`) больше не принимаются ни одной командой.

   Пароль ложится в `bases.yaml` домашнего каталога открытым текстом под правами владельца —
   сознательное решение: файл не покидает диск владельца, это не сетевой секрет, и передавать его
   по сети или показывать модели незачем.

   Готовая запись в `bases.yaml` выглядит так (адрес, пользователь и пароль — плейсхолдеры;
   полный шаблон со всеми полями и комментариями к каждому — тот же файл `bases.yaml`, который
   `init` уже создал в домашнем каталоге):

   ```yaml
   bases:
     ut_test:
       label: УТ 11, тестовая
       url: https://server/base
       user: odata_user
       password: qwerty123
       role: test
       config: ut
   ```

   Кавычки вокруг пароля нужны, только если в нём есть `#`, двоеточие с пробелом, он начинается
   со спецсимвола или похож на число — `odata1c base add` расставит их сама.

   Руками в этой записи чаще всего правят: `label` (подпись для модели), `role`, `write`
   (разрешить пишущие тулы — умолчание роли перекрывается явным полем), `gate.mode` (уровень
   гейта: `off | identifiers | identifiers+names`), `permissions` (`post_documents`,
   `mark_deletion`, `allow_entities`, `deny_entities`, `deny_fields`, `commit_limit` — что именно
   разрешено писать) и `config` (библиотека рецептов конфигурации). Файл — обычный YAML, правится
   текстовым редактором.

   `base test <имя>` проверяет соединение, `reindex <имя>` скачивает `$metadata` и строит индекс
   метаданных (первый разбор у типовой УТ долгий — это около 17 МБ описания и больше семи тысяч
   сущностей; дальше индекс пересобирается, только если изменилась контрольная сумма `$metadata`),
   `doctor` проверяет всё окружение разом. Демон перечитывает `bases.yaml` сам по изменению файла
   — после правки перезапускать его не нужно (единственное исключение — `daemon.yaml`, см.
   «Типовые сбои» ниже).

   **Файл правит владелец, не модель.** Модель `bases.yaml` штатно не читает и не правит — хук
   плагина `PreToolUse` перехватывает такие обращения к домашнему каталогу шлюза и требует решения
   человека. Команды `odata1c base set` и `odata1c policy …` модель выполняет сама по навыкам
   плагина; команду, снижающую защиту (уровень гейта ниже `identifiers+names`, включение записи,
   роль `test` или `dev`, открытие поля), — только после вашего согласия в отдельном сообщении, и
   хук переводит её в диалог разрешения Claude Code. Это дополнительная защита, а не единственная:
   реальные значения защищаемых классов не выходят через MCP ни при каком обращении, а пароль 1С
   модели попросту не нужен — этого достаточно, даже если бы хука не было. Базу заводит владелец
   сам, командой `base add` в своём терминале; просить модель «пропиши базу» бессмысленно —
   пароль она не видит и не вводит.

## Linux

Порядок тот же; отличаются только детали окружения.

- Домашний каталог — `~/.claude/odata1c/`, права закрываются `chmod 700`.
- Демон отделяется от терминала своим сеансом процессов, потоки уходят в `logs/`, идентификатор
  процесса — в файл pid домашнего каталога; `odata1c daemon stop` останавливает его по этому файлу.
- Заверение родителя лаунчера ищет среди предков процесс нативного установщика Claude Code или
  `node` с его `cli.js`.

Linux проверяется прогонами GitHub Actions на `ubuntu-latest` для Python 3.12 и 3.13
(`.github/workflows/ci.yml`): весь набор тестов без живой 1С, включая интеграционные и заверение
родителя лаунчера. Настоящий Claude Code на Linux вручную не запускался — это записанное
ограничение, а не проверенный факт.

## Проверка окружения: `doctor`

```text
odata1c doctor
odata1c doctor --online
```

Печатает таблицу строк `OK | WARN | FAIL` и возвращает код 0, 1 или 2 по худшей строке. Проверяет
версию Python, наличие и версию `uv`, домашний каталог и его права, разбор `bases.yaml` и
`daemon.yaml`, секрет гейта, наличие `launcher.key`, по каждой базе — индекс и `policy check`,
работу демона и совпадение его версии с версией пакета, наличие и версию Claude Code. Ключ
`--online` дополнительно проверяет соединение с каждой базой, как `base test`.

Паролей, имён пользователей 1С и полных адресов публикации `doctor` не печатает (от адреса — только
схема и хост) и ни в один файл не пишет.

## Обновление

```text
claude plugin update odata1c
odata1c daemon stop
uv tool upgrade odata1c-gate
```

Версия пакета закреплена в `.mcp.json` плагина, поэтому обновление плагина обновляет и шлюз.
Демон живёт дольше сессии и после обновления остаётся прежней версии — его нужно остановить,
следующий лаунчер поднимет новый. В самом Claude Code: `/mcp` → переподключить `odata1c`, чтобы
перезапустился лаунчер.

Что изменилось в выпуске — [CHANGELOG.md](../CHANGELOG.md).

## Подключение без плагина

Плагин — не единственный способ подключить шлюз. Любой MCP-клиент со stdio запускает его одной и
той же командой:

```text
uvx --from odata1c-gate odata1c mcp
```

**Claude Code**, `.mcp.json` проекта (или тем же способом — `claude mcp add`):

```json
{ "mcpServers": {
    "odata1c": { "command": "uvx", "args": ["--from", "odata1c-gate", "odata1c", "mcp"] } } }
```

**Cursor**, `~/.cursor/mcp.json` (или `.cursor/mcp.json` проекта) — тот же блок `mcpServers`:

```json
{ "mcpServers": {
    "odata1c": { "command": "uvx", "args": ["--from", "odata1c-gate", "odata1c", "mcp"] } } }
```

**VS Code**, `.vscode/mcp.json` — ключ верхнего уровня `servers`, у сервера `"type": "stdio"`:

```json
{ "servers": {
    "odata1c": {
      "type": "stdio",
      "command": "uvx",
      "args": ["--from", "odata1c-gate", "odata1c", "mcp"]
    } } }
```

**Claude Desktop**, `claude_desktop_config.json` — блок `mcpServers`, та же форма, что у Cursor.

Ключи лаунчера сужают видимость сессии: `--bases trade_dev,bp_test` (видны только они),
`--default trade_dev` (база по умолчанию), `--url http://127.0.0.1:7171/mcp` (адрес демона явно,
если он не на умолчании порта или на другой машине сети — см. «Порт демона» ниже).

**Честная оговорка.** Шлюз проверен только с Claude Code. Cursor, VS Code и Claude Desktop
подключаются и читают данные тем же способом; но диалог разрешения Claude Code и elicitation
(вопрос демона внутри протокола) у части клиентов не реализованы — там, где механизма подтверждения
нет, запись по умолчанию выключена (`write_confirm_fallback: deny` в `daemon.yaml`), а не разрешена
без подтверждения. Навыки, хук и агент — часть плагина Claude Code, в других клиентах их нет.

При установке плагином тулы называются `mcp__plugin_odata1c_gate__odata1c_<тул>`, при ручной
регистрации — `mcp__odata1c__odata1c_<тул>`. **Выберите один способ.** Оба сразу дают модели два
набора одних и тех же тулов: она путается, какой вызывать, а лимиты и разрешения считаются по
каждому набору отдельно. Снять ручную регистрацию — `claude mcp remove odata1c`; удалить плагин —
`claude plugin uninstall odata1c`.

## Порт демона

Демон слушает по умолчанию `127.0.0.1:7171`. Порт меняется строкой `port:` в
`~/.claude/odata1c/daemon.yaml`; после правки нужен `odata1c daemon stop` и переподключение шлюза
в клиенте (в Claude Code — `/mcp` → переподключить `odata1c`). Лаунчер берёт адрес демона из того
же файла сам; явно назвать его — ключ `--url` у `odata1c mcp` (раздел выше).

## Типовые сбои

**Демон другой версии.** `doctor` говорит `FAIL` в строке демона: «после обновления нужен
`daemon stop`». Демон один на машину и переживает перезапуск Claude Code, поэтому после
обновления пакета он остаётся старым. Лечится `odata1c daemon stop` — следующий лаунчер поднимет
новый. Если `FAIL` остался и после этого, разошлись сами две установки: плагин обновился и
закрепил в своём `.mcp.json` новую версию, а командная строка осталась прежней, и `doctor`
сравнивает демон новой версии со старым пакетом. Лечится `uv tool upgrade odata1c-gate` — тогда
командная строка совпадёт с тем, что закрепил плагин.

**Два вопроса подряд на запись.** Claude Code показывает свой диалог разрешения, а следом вопрос
от шлюза. Значит, демон не признал лаунчер настоящим: механизм подтверждения Claude Code демон
выдаёт только клиенту, чьи заголовки подписаны ключом `launcher.key`, а ключ он читает при старте.
Если домашний каталог создан старой версией и ключ появился позже, демон о нём не знает.
Лечится `odata1c daemon stop` (ключ создадут `init` или лаунчер, новый демон его прочитает).

**`config_invalid` на каждый вызов тула.** `bases.yaml` не разбирается или не проходит проверку.
Демон перечитывает файл перед вызовом тула и при поломке закрывает все тулы этой ошибкой с путём и
номером строки — прежняя конфигурация не используется намеренно: работать по последней заведомо
верной версии файла, который владелец только что сломал, опаснее, чем остановиться. Лечится
правкой файла, перезапуск не нужен. Ту же ошибку с тем же текстом печатает `odata1c doctor`.

**Тул отвечает `404` на известную сущность.** Индекс отстал от базы: `odata1c reindex <база>`
или тул `odata1c_reindex`.

**Индекс почти пустой, нужного объекта в нём нет.** Объект не включён в состав стандартного
интерфейса OData: 1С публикует только то, что в этот состав внесено. Как его настроить — раздел
«Быстрый старт» → «Что нужно» в [README](https://github.com/Romandredan/odata1c-gate#быстрый-старт);
после настройки — `odata1c reindex <база>`. Если не открывается сам адрес
`…/odata/standard.odata/` (обычно ответ `404`), а веб-клиент по тому же адресу публикации работает,
при публикации базы на веб-сервере не отмечен «Публиковать стандартный интерфейс OData».

**Пустой перечень рецептов.** База заведена без `--recipes` — файл рецептов пуст, а поля `config`
у записи базы нет, поэтому библиотека рецептов конфигурации не подключается. Лечится правкой
записи базы в `bases.yaml` (`config: ut`) или повторным `base add` с ключом.

**`permission_denied` на запись.** Запись закрыта разрешениями базы: поле `write` или один из
флагов раздела `permissions` (`post_documents`, `mark_deletion`, `allow_entities`,
`deny_entities`, `deny_fields`, `commit_limit`). Модель называет флаг и не обходит его — решение
за владельцем. `odata1c base set <база> --write on --post-documents on` (или правка файла)
действует со следующего вызова тула, без перезапуска демона.

**`token_ambiguous` при записи по токену.** У токена несколько известных написаний (ИНН с
пробелом и без, название в разных кавычках), а туда, где нужно одно — ключ, параметр, тело
записи, — шлюз не подставляет ничего наугад. Лечится уточнением запроса так, чтобы написание
определялось однозначно.

**Порт 7171 занят или секрет сменился.** `daemon.yaml` — единственный файл, правка которого
требует перезапуска: порт и секрет на ходу не меняются. `odata1c daemon stop`, затем обычный
запуск сессии.
